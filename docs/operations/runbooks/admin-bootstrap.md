# ตั้งผู้ดูแลระบบนอกหน้าจอ (ผู้ดูแลกรมคนแรกขององค์กร · ผู้ดูแลแพลตฟอร์ม)

> ผู้รัน: operator หรือทีมปฏิบัติการที่ operator สั่ง · ทุกครั้งเริ่มด้วยการทดลอง (ค่าเริ่มต้น) แล้วจึงใส่ `--apply`
> ที่มา: fix/admin-role-split รอบ 2 (รีวิวข้อ I1, M1) · คำสั่ง 13 และ 34(2)

## ทำไมไม่มีปุ่มบนหน้าจอ

คำสั่ง 13 แยกผู้ดูแลเป็นสองฝั่ง ผู้ดูแลกรมตั้งได้เฉพาะบทบาทฝั่งกรม ผู้ดูแลแพลตฟอร์มตั้งได้เฉพาะบทบาทฝั่งบริษัท
ผลคือไม่มีประตูไหนในระบบที่
- ตั้งผู้ดูแลกรมคนแรกให้องค์กรใหม่ หรือกู้องค์กรที่ผู้ดูแลกรมทุกคนใช้งานไม่ได้
- ตั้งผู้ดูแลแพลตฟอร์ม (บทบาทข้ามองค์กร ไม่อยู่ในรายการของผู้ดูแลคนใด)

operator ยังไม่ได้ตัดสินว่าจะเปิดประตูยกเว้นในระบบหรือไม่ จนกว่าจะตัดสิน ทางเดียวคือสคริปต์ด้านล่าง
ทุกสคริปต์เขียนแถวบันทึกการตรวจสอบในธุรกรรมเดียวกับการเปลี่ยนบัญชี และพิมพ์แค่ชื่อกับคำตอบ ใช่/ไม่ ไม่มีอีเมล เลขบัตร หรือรหัสผ่าน

รันในคอนเทนเนอร์ backend ที่ build จาก commit ที่มีสคริปต์นี้แล้ว (ถ้ายังเป็น image เก่า ให้ deploy ก่อน)

```bash
docker exec -it <backend container> sh -c 'cd /app/apps/backend && node scripts/ops/bootstrap-dtam-admin.js --organization <slug>'
```

## 1. ผู้ดูแลกรมให้องค์กรที่ไม่มีผู้ดูแลกรมที่ใช้งานอยู่

สคริปต์: `scripts/ops/bootstrap-dtam-admin.js` ใช้บัญชี **เจ้าหน้าที่ฝั่งกรมที่มีอยู่แล้ว** ขององค์กรนั้น
(เช่น ผู้ตรวจเอกสาร หรือผู้ดูแลกรมที่ถูกปิดไป) ไม่สร้างบัญชีใหม่ และไม่ย้ายบัญชีข้ามฝั่ง

1. ดูรายชื่อผู้ที่ตั้งได้ (ไม่เขียนอะไร)
   ```bash
   node scripts/ops/bootstrap-dtam-admin.js --organization <id หรือ slug>
   ```
   ได้ชื่อ บทบาท ใช้งานอยู่หรือไม่ และ user id ในวงเล็บ
2. ทดลองกับคนที่เลือก (ไม่เขียนอะไร)
   ```bash
   node scripts/ops/bootstrap-dtam-admin.js --organization <slug> --user <user id> --reason "<เหตุผลตามหนังสือที่ขอ>"
   ```
   อ่านบรรทัด "จะตั้งเป็น system_admin_dtam / จะเปิดใช้งาน / จะเพิ่มกลุ่ม" ให้ตรงกับที่ต้องการ
3. เขียนจริง: คำสั่งเดิมเติม `--apply` (ต้องมี `--reason` อย่างน้อย 10 ตัวอักษร)
4. แจ้งผู้ดูแลคนนั้นให้เข้าสู่ระบบใหม่ (session เดิมถูกตัด) แล้วให้เขาตั้งผู้ดูแลกรมคนที่สองผ่านหน้าจอ
   องค์กรจะได้ไม่กลับมาติดที่เดิม

สิ่งที่สคริปต์ทำในธุรกรรมเดียว: บทบาท `system_admin_dtam` · สถานะใช้งาน · กลุ่ม `system_admin_dtam`
(คิวงานอ่านกลุ่มก่อนบทบาท และผู้ดูแลให้กลุ่มแก่ตัวเองไม่ได้) · ตัด session เดิม · แถวบันทึก `DTAM_ADMIN_BOOTSTRAPPED`
ในสายบันทึกขององค์กรนั้น พร้อมเหตุผล บทบาทและสถานะก่อนกับหลัง

สคริปต์ปฏิเสธ (ไม่เขียนอะไร) เมื่อ
- องค์กรมีผู้ดูแลกรมที่ใช้งานอยู่แล้ว (รันซ้ำจึงไม่เปลี่ยนอะไร ให้ผู้ดูแลคนนั้นทำผ่านหน้าจอ)
- บัญชีอยู่องค์กรอื่น เป็นบัญชีฝั่งบริษัท เป็นผู้ขอรับรอง หรือบทบาทอ่านไม่ออก
- สั่ง `--apply` โดยไม่มีเหตุผล

บัญชีที่ถูกล็อกจากการกรอกรหัสผิด สคริปต์บอกว่า "ถูกล็อก: ใช่" แต่ไม่ปลดล็อก ล็อกหมดเวลาเอง

## 2. ผู้ดูแลแพลตฟอร์ม

สคริปต์: `scripts/grant-platform-admin.js` เลื่อน **บัญชีเจ้าหน้าที่ฝั่งบริษัท** (การเงินบริษัท) เป็น `system_admin_platform`

```bash
node scripts/grant-platform-admin.js --id <user id>            # ทดลอง
node scripts/grant-platform-admin.js --id <user id> --apply    # เขียนจริง
```

- เขียนคำบทบาทปัจจุบันเท่านั้น (รุ่นก่อนเขียนคำเก่า `PLATFORM_ADMIN` ซึ่งเข้าสู่ระบบไม่ได้)
- ปฏิเสธบัญชีฝั่งกรม ผู้ขอรับรอง และบัญชีที่บทบาทเป็นคำเก่า (ถ้าเจอบัญชีที่ค้างคำเก่า ให้แจ้งทีมพัฒนา อย่าแก้ด้วย SQL)
- เขียนแถวบันทึก `USER_ROLE_GRANTED` และตัด session เดิม

## 3. นับกลุ่มบทบาทข้ามฝั่งที่ค้างอยู่ (อ่านอย่างเดียว)

สคริปต์: `scripts/ops/count-cross-side-group-memberships.js` นับแถวกลุ่มที่ใช้งานอยู่ แยกตาม (ฝั่งของกลุ่ม, ฝั่งของบัญชี)
พิมพ์ตัวเลขเท่านั้น ใช้แค่ `@prisma/client` จึงรันในคอนเทนเนอร์รุ่นเก่าที่ยังไม่มีไฟล์นี้ได้ โดยส่งไฟล์ทาง stdin

```bash
docker exec -i <backend container> sh -c 'cd /app/apps/backend && node -' \
  < apps/backend/scripts/ops/count-cross-side-group-memberships.js
```

บรรทัดที่มี `<- cross-side` คือกลุ่มที่อยู่คนละฝั่งกับบทบาทของบัญชี ตั้งแต่ fix/admin-role-split ระบบไม่นับแถวเหล่านี้เป็นอำนาจแล้ว
ถ้าผลไม่เป็นศูนย์ การลบแถวเป็นเรื่องที่ operator ต้องอนุมัติก่อน ห้ามลบเอง

## ตรวจหลังรัน

- `audit_logs` มีแถว `DTAM_ADMIN_BOOTSTRAPPED` หรือ `USER_ROLE_GRANTED` หนึ่งแถวต่อการรันหนึ่งครั้ง
- ผู้ที่ถูกตั้งเข้าสู่ระบบใหม่ได้ และเห็นเมนูผู้ดูแลของฝั่งตัวเอง
