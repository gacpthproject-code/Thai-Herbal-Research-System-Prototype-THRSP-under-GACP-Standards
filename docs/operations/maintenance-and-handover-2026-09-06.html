01 สิบนาทีแรกของทุก session

  2. ให้เครื่องพิมพ์สถานะ — branch, diff, สรุป probe bash scripts/session-check.sh
  3. อ่านสามไฟล์นี้ ก่อนเชื่ออะไร: ~/work/START-HERE.txt · ~/work/state/STATE.md (เขียนอัตโนมัติทุกครั้งที่ session หยุด) · memory ของโปรเจกต์ที่ .claude/.../memory/MEMORY.md
  4. รู้ว่าโค้ดอยู่คอมมิตไหนเทียบ main — git log --oneline origin/main..HEAD · งานที่ยังไม่ merge คือของที่ยังรอคำว่า "merge" จาก operator

03 เมื่อระบบมีปัญหา: วินิจฉัยตรงไหนก่อน

ลำดับการมอง— จากถูกที่สุดไปแพงที่สุด

  1. probe พูดว่าอะไร — bash scripts/ci/local-gate.sh รันด่านเบาทั้งหมด · ตัวที่แดงจะบอกชื่อ probe ตรง ๆ
  2. เทียบกับ baseline เสมอ — local-gate แดงบน main อยู่แล้ว (secret ในประวัติ ฯลฯ) เกณฑ์คือ "ไม่มีความล้มเหลวใหม่" ไม่ใช่ "เขียวหมด" bash evidence/appv2-B1-gate/compare-gate-vs-baseline.sh <baseline> <run>
  3. ถ้าเป็นเรื่อง flow/UI — อย่าเชื่อ unit test อย่างเดียว มัน เขียวได้ทั้งที่ feature พัง (ดูข้อ 6) · ต้องกดจริงบนเบราว์เซอร์ด้วย Playwright บน stack ที่รันจากต้นไม้จริง
  4. ดู log ของ backend — ถ้า endpoint ตอบ 200 พร้อมข้อมูลว่าง อย่าเชื่อว่า "ไม่มีข้อมูล" ทันที มี 4 จุดที่ตอบ 200 บนความล้มเหลว (ดูข้อ 7)
กับดักที่เจอซ้ำ probe หลายตัว "match รูปแบบ ไม่ใช่ค่าจริง" — คอมเมนต์ที่มีเลข 5000 เคยถูกนับเป็น hardcode, ตัวเลข ['5,535'] เคยถูกอ่านว่าเป็น 5xx · เมื่อ counter แดง ให้ดูก่อนว่าบรรทัดที่ match เป็นคอมเมนต์หรือตัวเลขจัดรูปแบบไหม ก่อนจะสรุปว่าโค้ดผิด

04 จะแก้อะไรให้ปลอดภัย ทำยังไง

เครื่องเป็นคนตัดสินความเสี่ยง ไม่ใช่คุณประเมินเอง

ชั้นงาน (tier)เครื่องตัดสินด้วยต้องทำอะไร
A — docs / tests / evidencescripts/probes/tier-check.sh
ห้ามประเมินเอง		local-gate ผ่าน + review 1 ชั้น
B — โค้ดทั่วไปCI เขียวจริง (full suite) + review 2 ชั้น · แนบผลรันจริง · งาน UI ต้องมี view-pack
C — เงิน / auth / identity / schema / migration / secretของ B ทั้งหมด + paste RED ก่อนขอ GREEN + evidence pack เต็ม + operator merge เท่านั้น

วินัยที่ทำให้แก้แล้วไม่พัง

  • RED ก่อนเสมอ — เขียนเทสที่ fail จริงก่อน แล้วค่อยแก้ให้เขียว · เทสที่ผ่านทันทีโดยไม่เคยแดง = ไม่ได้พิสูจน์อะไร
  • เทสวัดพฤติกรรม ไม่ใช่รูปร่าง — assert ผลลัพธ์ที่ผู้ใช้เห็น ไม่ใช่ว่า mock ถูกเรียก · check-green-mask-assertions.js คุมเรื่องนี้อยู่
  • แก้เทสที่ผิด อย่าผ่อนเทส — ถ้าเทสขวางเพราะมันปักค่าเก่า ให้แก้พร้อมเขียนเหตุผล ไม่ใช่ลด assertion
  • ratchet ลงทางเดียว — hardcode / todo / dup-source เพิ่มแม้ตัวเดียว = gate ไม่ผ่าน · baseline ขึ้นได้เฉพาะ operator สั่ง

05 เส้นที่ห้ามข้ามถ้าไม่มี operator

ไม่ว่าเหตุผลจะดีแค่ไหน — สี่เรื่องนี้หยุดแล้วถาม

ห้ามเด็ดขาด
  • เงิน — agent อ่าน / flag / เสนอ diff เท่านั้น · ห้ามแก้โค้ด path เงินแล้ว merge เอง · live payment key ห้ามตั้งจน G1 เขียวครบ (L3)
  • secret / กุญแจเซ็นใบรับรอง — ห้ามพิมพ์ secret ที่ไหนเลย · ห้ามแตะ apps/backend/keys/*.pem · npx jest เคยหมุนกุญแจจนใบรับรองจริงเสีย — เช็ค mtime ก่อนเสมอ (L2)
  • deploy + merge Tier C — operator เท่านั้น ตลอดไป · agent push main ได้เฉพาะเมื่อ operator พิมพ์คำว่า "merge" (L5)
  • ฐานข้อมูล Supabase — prod กับ preview ใช้ตัวเดียวกัน · อ่านได้ เขียนไม่ได้ · migration ไม่ apply จนถึง gate

ถ้า operator ยืนยันซ้ำหลังเราท้วง = เป็นการตัดสินใจของเขา ทำตามเต็มคำขอ · การย่อขอบเขตงานเป็นสิทธิ์ของ operator ไม่ใช่ของ agent

06 คลาสของบั๊กที่เจอซ้ำ — จำไว้จะได้รู้ทัน

ทุกตัวเคยเขียวในชุดเทสขณะที่ feature พังจริง

ชื่อคลาสอาการวิธีจับ
ประตูถามสิ่งที่จอไม่เคยเขียน (v1-hard-lock)ฟอร์มส่งฟิลด์ชื่อ A, validator ขอฟิลด์ชื่อ B ⇒ ปฏิเสธทุกใบ · Deep QA เจอ 16 ฟิลด์แบบนี้พร้อมกันกดยื่นจริงในเบราว์เซอร์ แล้วดูว่า 422 ชี้ฟิลด์ที่มีบนจอไหม
select gapคอลัมน์มีอยู่ query ไม่ได้ขอ ⇒ ได้ null เงียบ ๆเทสที่ส่ง object เต็มให้ mock มองไม่เห็น — ต้องเดินผ่าน DB จริง
guard match รูปแบบ ไม่ใช่การประกาศตัวตรวจติดที่ router แต่หา "ฟาร์มไหน" จากรูป payload ⇒ เส้นทางที่ payload ไม่มีฟาร์ม รอดไปเงียบ ๆเทียบ guard กับ projection จริงของทุก handler ไม่ใช่ fixture
สองฝั่งอ่านคนละคำประกาศประตูยื่นอ่านคำตอบ A, ตัวคิดเงินอ่าน B ⇒ ผ่านด่านแล้วคิดเงินขาด · Deep QA เจอคิดเงิน 1 รูปแบบทั้งที่ประกาศ 3 (−70,620)hop ระหว่างสอง module — unit test ที่แตะแค่ปลายทางมองไม่เห็น
คำปฏิเสธไปไม่ถึงผู้ใช้envelope ตัด message ทิ้ง ⇒ เกษตรกรเห็นรหัสดิบหรือหน้าว่างส่งข้อความไทยใน messageTh (ไม่ใช่ reserved key) และถามด้วย KIND ไม่ใช่ไล่รหัส
บทเรียนเดียวที่ครอบทั้งห้าคลาส ชุดเทสทดสอบ "สองปลาย" แต่ไม่เคยทดสอบ "ทางเชื่อมตรงกลาง" · เมื่อแก้บั๊กพวกนี้ ให้เพิ่ม (1) เทส pure-function ของทางเชื่อม และ (2) การกดจริงซ้ำบนเบราว์เซอร์ — วิธีที่ Deep QA ใช้จับทั้งสี่บั๊กในเซสชันนี้

07 Deploy: ลำดับที่ห้ามสลับ

คู่มือ recon เต็มอยู่ที่ ~/work/state/staging-recon-*.md

  1. migrate ก่อน image เสมอ — main ถือโค้ดที่อ่านตารางใหม่แล้ว ถ้าปล่อย image ก่อน migrate ประตูจะ 500 cd apps/backend && npx prisma migrate deploy
  2. ห้ามลืม STAGING_IMAGE_TAG= ตอน build staging — ลืม = ถอยกลับอิมเมจเก่าเงียบ ๆ
  3. ห้าม docker compose up -d เปล่า ๆ · ห้าม --remove-orphans — ทั้งสองเคยล้มบริการข้างเคียง
  4. verify ว่าได้ build ใหม่จริง ก่อนเปิดม่าน nginx — schema level ≠ build level, สามสภาพแวดล้อมรันคนละอิมเมจ
ค้างอยู่ตอนนี้ ฐานที่ prod+preview ใช้ร่วมกันตามหลัง migration ที่ยังไม่ apply · ก่อน deploy ครั้งถัดไป ต้องรัน migrate deploy ก่อน ไม่งั้นประตูตรวจเอกสาร, ประตูสแกน T&T และ ม.30 จะ 500 พร้อมกัน
