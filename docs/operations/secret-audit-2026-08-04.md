## 0. สองข้อที่ฉบับเดิมผิด และต้องไม่ถูกอ้างอีก

**(ก) path ของไฟล์ env ที่ compose อ่าน**

หลักฐานที่หนักกว่านั้นอยู่ในเอกสารเดียวกันอยู่แล้ว คือ `docs/operations/env-layering.md:47`
ที่เขียนว่ายืนยันจากสแตกที่รันอยู่จริงแล้ว และ `:51` ที่ยกค่า label ของ compose project มาแสดงตรง ๆ

แก้เลขบรรทัดเมื่อ 2026-08-04 หลัง operator สั่งให้แนบ `file:line` ตามมาตรฐานเดียวกับทุก claim
ฉบับแรกของข้อนี้อ้าง `:41` ซึ่งเป็นเส้นคั่นตาราง (`| --- | --- | --- |`) ไม่ใช่แถวที่มีเนื้อหา
คลาดไปหนึ่งบรรทัด — ตัวรายงานสรุปถูก แต่ตัวชี้ผิด ซึ่งตาม Law 3.9 ถือว่าใช้อ้างอิงไม่ได้

```

```

**(ข) คำสั่งชี้ขาดที่ให้เทียบ hash ของ `REDIS_URL`**
ฉบับเดิมเสนอให้รัน `docker exec ... printenv REDIS_URL | sha256sum` แล้วเทียบกับ hash ที่คำนวณจากค่าปริยายในไฟล์
**ยกเลิกคำสั่งนี้** เหตุผลสองข้อ
1. การประกอบสตริงเพื่อ hash ต้องตรงกันทุกไบต์รวมถึงอักขระขึ้นบรรทัด ต่างกันหนึ่งไบต์ก็ได้ผล "ไม่ตรง" ทั้งที่ค่าเหมือนกัน **เสี่ยง false negative**
2. ไม่จำเป็นอีกแล้ว เพราะได้คำตอบตรง ๆ จากการทดสอบ AUTH แล้ว (ข้อ 1 ด้านล่าง)

## 1. Redis มี override จริง ไม่ต้องหมุนฉุกเฉิน

ทดสอบด้วย `redis-cli AUTH` โดยใช้ค่าปริยายที่อยู่ในไฟล์ compose (ผ่าน guard ตรวจความยาว = 15)
ผลที่ได้คือ **`WRONGPASS`**

⇒ รหัสที่คอนเทนเนอร์ใช้อยู่จริง **ไม่ใช่** ค่าปริยายสาธารณะที่อยู่ในไฟล์
⇒ **ไม่ต้อง rotate ฉุกเฉิน** ยังคงต้องถอดค่าปริยายออกจากไฟล์อยู่ แต่เป็นงานตามคิวปกติไม่ใช่งานเร่ง

จุดที่ยังมีค่าปริยายฝังอยู่ในไฟล์ที่ commit
`docker-compose.production.yml:90` · `:378` · `docker-compose.staging.yml:69` · `docker-compose.bluegreen.yml:53`

## 2. Redis มีคอนเทนเนอร์เดียวใช้ร่วมทุก environment

ยืนยันจาก `docker ps` มี `gacp-redis` ตัวเดียว
⇒ การหมุนรหัส Redis ในอนาคต **ต้อง recompose ทุก environment พร้อมกันในหน้าต่างเดียว**
`docker-compose.production.yml:378` ตั้ง `--requirepass` และ `:90` ประกอบ `REDIS_URL` จากตัวแปรเดียวกัน
ถ้าขึ้นไม่พร้อมกัน ฝั่งที่ยังถือรหัสเก่าจะต่อไม่ได้ทันที

## 3. compose อ่าน `.env.production` ยืนยันจากสแตกที่รันอยู่

label `com.docker.compose.project.environment_file` ชี้ `/opt/gacp-platform/.env.production`
ก่อนหน้านี้เอกสารพิสูจน์ได้แค่ระดับ "สคริปต์ deploy ตั้งค่าไว้แบบนี้"
(`scripts/deploy/deploy-production.sh:39`, `scripts/deploy/deploy-staging.sh:28`)
ตอนนี้ยกระดับเป็น **ยืนยันจากของจริงที่รันอยู่** แล้ว

## 4. หน้าต่างประวัติศาสตร์ของค่าปริยาย Redis ปิดถาวร

- ค่าปริยายเข้าไฟล์เมื่อ 2026-03-11 (commit `001796b6`) ก่อนหน้านั้น Redis **ไม่มี auth เลย**
- คอนเทนเนอร์ที่รันอยู่ปัจจุบันเกิด 2026-06-03 พร้อม override
- ช่วง 2026-03-11 ถึง 2026-06-03 คือ **accepted risk** ปิดถาวร ไม่ขุดต่อ

เหตุผลที่ยอมรับได้: ข้อมูลใน Redis เป็น cache/session ที่หมดอายุไปแล้ว · port 6379 ไม่ผูกออกนอก docker network
(`docker-compose.production.yml` โซน redis มีคอมเมนต์ยืนยันว่าไม่เปิดพอร์ตสาธารณะ) · และปัจจุบันยืนยันแล้วว่ามี override

## 5. เหตุการณ์ 2026-08-04 เวลา 17:01 และ 18:50 คลี่คลายแล้ว ไม่มีอะไรค้าง

มีการแก้ `DB_PASSWORD` และ `REDIS_PASSWORD` ใน `.env.production` และ `.env.staging` ด้วย `sed`
(ทำด้วยมือคน ไม่ใช่สคริปต์) โดย **ไม่ได้ `ALTER USER` ใน postgres** ⇒ ไฟล์กับคอนเทนเนอร์ไม่ตรงกัน

**restore กลับจากไฟล์ `.bak` แล้ว** ยืนยันด้วย diff ว่าง ได้สถานะ `PROD-OK` และ `STAGING-OK`
ปัจจุบันไฟล์ตรงกับคอนเทนเนอร์ ไม่มี drift ค้าง
