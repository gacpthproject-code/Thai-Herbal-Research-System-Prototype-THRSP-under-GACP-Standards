# ขั้นตอนส่งมอบชุดข้อมูลดิบเพื่อการวิจัย

ชุดข้อมูลดิบตามสัญญา C05F680149 ภาคผนวก 4 ข้อ 3 ส่งให้คลังข้อมูลวิจัยของโครงการ เป็นไฟล์พร้อม manifest ไม่มีการดึงอัตโนมัติ
ความหมายของทุกคอลัมน์อยู่ใน [คู่มือการใช้ชุดข้อมูล](data-dictionary.md) ซึ่งสร้างจากโค้ด ชุดตัวอย่างสังเคราะห์อยู่ใน [sample/](sample/README.md)

## ใครส่ง ส่งอะไร ส่งให้ใคร

- ผู้ส่งออก: ผู้ดูแลระบบของกรม (`system_admin_dtam`) ส่งออกได้เฉพาะข้อมูลขององค์กรตัวเอง บทบาทอื่นเปิดดูรายการและคู่มือได้แต่ส่งออกไม่ได้ (`DATASET_EXPORT_FORBIDDEN`) ทุกการส่งออกออกไปได้เมื่อบันทึกในประวัติการใช้งานสำเร็จแล้วเท่านั้น (บันทึกไม่ได้ = 503 `DATASET_EXPORT_AUDIT_FAILED` ไม่มีข้อมูลออก) บันทึกนั้นระบุรูปแบบไฟล์ จำนวนแถว ค่าแฮช sha256 ของไฟล์ที่ส่ง (ชุดเต็มมีค่าแฮชของ `manifest.json` ด้วย) และลายนิ้วมือกุญแจ ประตูส่งออกตอบพร้อม `Cache-Control: no-store` เบราว์เซอร์และ proxy จึงไม่เก็บสำเนา
- สิ่งที่ส่ง: ชุดเต็มหนึ่งไฟล์ ZIP จากปุ่ม "ดาวน์โหลดชุดเต็ม (ZIP)" ที่หน้า `/provider/datasets` หรือประตู `GET /api/datasets/bundle` ในไฟล์มี CSV และ JSONL ของทุกโดเมนที่ส่งออกได้ รายการลบทั้งสามรายการ คู่มือ และ `manifest.json`
- ผู้รับ: คลังข้อมูลวิจัยของโครงการ ผู้ดูแลคลังฝั่งโครงการยังไม่ระบุ (รอ operator ตามคำถาม Q7) operator เป็นผู้ส่งไฟล์ด้วยช่องทางที่ operator เลือก ระบบไม่ส่งเอง

## โดเมนและรายการลบ

| `survey-responses/withdrawn` | รายการลบ | ชุดคำตอบที่ผู้ตอบถอนความยินยอมหรือลบบัญชีของตัวเอง |

ข้อมูลการทำงานของฟาร์มสามโดเมนแรกยังส่งออกไม่ได้ ประตูตอบ 403 `DATASET_RESEARCH_BASIS_NOT_IN_FORCE` และชุดเต็มระบุไว้ใน `manifest.json` ช่อง `notExported` จะส่งออกได้เมื่อครบทุกข้อต่อไปนี้

1. operator อนุมัติถ้อยคำใน [ร่างย่อหน้าการใช้ข้อมูลเพื่อการวิจัย](privacy-notice-research-use-draft.md) และเงื่อนไขก่อนมีผลในไฟล์นั้นเป็นจริงแล้ว
2. นโยบายความเป็นส่วนตัวฉบับที่มีย่อหน้านั้นประกาศแล้วและถึงวันมีผล
3. คณะกรรมการจริยธรรมการวิจัยของมหาวิทยาลัยที่ทำวิจัยร่วมมีหนังสืออนุมัติงานวิจัยแล้ว (คำสั่ง 56(4.3))
4. เพิ่มรายการที่มีวันที่กำกับใน `apps/backend/data/datasets/research-use-bases.js` (เพิ่มต่อท้ายเท่านั้น ห้ามแก้รายการเดิม) ด้วยวันมีผล รุ่นของนโยบาย และหนังสืออนุมัติในช่อง `ethicsApproval` (ชื่อคณะกรรมการ `committee` เลขที่ `reference` วันที่อนุมัติ `approvedOn` ซึ่งต้องไม่หลังวันมีผล) แล้ว deploy รายการที่ไม่มีหนังสืออนุมัติครบ ประตูยังตอบ 403 แม้ถึงวันมีผลแล้ว และ `manifest.json` ช่อง `researchBasis` ระบุหนังสือที่ใช้ทุกครั้งที่ส่งออก

## ผู้รับต้องทำอะไรทุกครั้งที่รับชุดใหม่

1. ตรวจ `manifest.json`: sha256 และจำนวนแถวของทุกไฟล์ต้องตรงกับไฟล์ที่ได้รับ
2. เทียบ `pseudonymKeyFingerprint` กับครั้งก่อน ถ้าเปลี่ยน แปลว่ากุญแจรหัสแฝงเปลี่ยน ให้ลบชุดเก่าทั้งหมดแล้วรับชุดใหม่ทั้งชุด และห้ามใช้รายการลบข้ามรุ่นกุญแจ
3. ใช้รายการลบทั้งสามรายการ: ลบแถวใน `cultivation-logs` ที่ `id` ตรงกับ `cultivation-logs/deleted` ลบแถวใน `harvest-batches` ที่ `id` ตรงกับ `harvest-batches/deleted` และลบแถวใน `survey-responses` ที่ `responseId` ตรงกับ `survey-responses/withdrawn` ระบบนี้เรียกคืนข้อมูลที่ส่งไปแล้วเองไม่ได้ รายการคำตอบที่ถอนรวมคำตอบของผู้ที่ลบบัญชีตามสิทธิ์ PDPA ด้วย เพราะข้อความยินยอมรุ่น v3 เก็บรหัสบัญชีไว้เพื่อลบหรือถอนคำตอบตามคำขอ และการลบบัญชีคือคำขอนั้น
4. ลบให้ทันกำหนด ประโยคนี้อยู่ใน `manifest.json` ช่อง `deletionDuty` และในคู่มือของทุกชุดด้วย: คลังข้อมูลวิจัยของโครงการต้องลบข้อมูลของทุกรหัสแฝงที่อยู่ในรายการคำตอบที่ถอนความยินยอมแล้ว (survey-responses/withdrawn) ทั้งในคลัง ในสำเนา และในข้อมูลสำรอง ให้เสร็จภายใน 90 วันนับจากวันที่ได้รับชุดข้อมูลที่มีรหัสแฝงนั้นในรายการ ใช้ทั้งกับผู้ตอบที่ถอนความยินยอมและผู้ตอบที่ลบบัญชีตามกฎหมายคุ้มครองข้อมูลส่วนบุคคล ตามประกาศคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล เรื่องหลักเกณฑ์การลบ ทำลาย หรือทำให้ไม่ระบุตัวบุคคล พ.ศ. 2567
5. แทนที่ข้อมูลโดเมนเดิมด้วยไฟล์ชุดใหม่ (ทุกไฟล์เป็นชุดเต็ม ไม่ใช่ส่วนเพิ่ม)
6. ห้ามจับคู่แถวกับหน้าตรวจสอบย้อนกลับสาธารณะหรือข้อมูลภายนอกอื่นเพื่อระบุฟาร์มหรือบุคคล: วันที่เก็บเกี่ยวและน้ำหนักสดของรุ่นเป็นค่าเดียวกับที่หน้าสาธารณะของรุ่นนั้นแสดงพร้อมชื่อฟาร์ม

## กุญแจรหัสแฝง

ใช้กุญแจ `DATASET_PSEUDONYM_KEY` ดอกเดียวตลอดโครงการ แยกจากกุญแจอื่นของระบบ ประตูส่งออกตอบ 503 และไม่มีข้อมูลออกเมื่อไม่มีกุญแจ กุญแจเท่ากับ `HMAC_KEY` กุญแจที่เปิดเผยแล้ว (กุญแจชุดตัวอย่างใน `apps/backend/data/datasets/public-pseudonym-keys.js` หรือค่าสำรองของชุดเทสต์) หรือกุญแจสั้นกว่า 32 ไบต์ ทุกสภาพแวดล้อม เปลี่ยนเฉพาะเมื่อกุญแจรั่ว เมื่อเปลี่ยนต้องส่งชุดเต็มใหม่และแจ้งผู้รับให้ลบชุดเก่าทั้งหมด ค่ากุญแจไม่ปรากฏในไฟล์ใด manifest มีเพียงลายนิ้วมือ

## ตรวจซ้ำได้

`node apps/backend/scripts/datasets/check-dataset.js` สร้าง Postgres ชั่วคราว เขียนชุดตัวอย่างผ่านประตูจริงของระบบ เปิด backend จากโค้ดชุดนี้ แล้วตรวจเกณฑ์ K1-K13 ผ่านประตู HTTP จริงด้วยบัญชีทุกบทบาท `check-dataset.selftest.js` ทำลายข้อเท็จจริงทีละข้อแล้วยืนยันว่าเกณฑ์ข้อนั้นจับได้ ผลรันอยู่ใน `evidence/dataset/<sha>/` (จำนวนแถว ผลผ่าน/ไม่ผ่าน และ sha256 ของชุดตัวอย่าง ไม่มีข้อมูลจริงและไม่มีกุญแจ) ทั้งสองไฟล์รันผ่าน `~/work/state/heavy.sh`

## ข้อจำกัดที่รู้แล้ว

- ไฟล์ทั้งไฟล์หรือทั้งชุดถูกสร้างในหน่วยความจำก่อนส่ง พอสำหรับขนาด pilot
- การลบบันทึกกิจกรรมทีละรายการ (`DELETE /api/cultivation-logs/:id`) ลบแถวจริงโดยไม่เหลือร่องรอย แถวนั้นหยุดส่งออกแต่ไม่อยู่ในรายการลบ คลังจึงไม่รู้ว่าต้องลบ ต้องแก้ (ลบแบบเหลือร่องรอย มี migration) ก่อนข้อมูลการทำงานของฟาร์มส่งออกได้ เทสต์ `apps/backend/__tests__/unit/dataset-export-service.test.js` ไม่ผ่านทันทีที่มีมติข้อมูลฟาร์มที่มีผลใน `research-use-bases.js` ขณะตาราง `CultivationLog` ยังไม่มีคอลัมน์ลบแบบเหลือร่องรอย
- การสแกนคิวอาร์โค้ดของรุ่นที่ถูกลบยังอยู่ใน `trace-scans` (เป็นเหตุการณ์ของผู้สแกนสาธารณะ ไม่มีข้อมูลส่วนบุคคล) หลังคลังลบรุ่นตามรายการลบแล้ว `scannedEntityId` ของแถวเหล่านั้นจะเชื่อมไม่ถึงรุ่นใด
- รุ่นเก็บเกี่ยวในชุดข้อมูลจับคู่กับหน้าตรวจสอบย้อนกลับสาธารณะได้ด้วยวันที่เก็บเกี่ยวและน้ำหนักสด ค่าเริ่มต้นที่เลือกคือส่งน้ำหนักตามจริงและบอกเจ้าของข้อมูลตรง ๆ ในร่างนโยบาย (เหตุผลอยู่ใน [ร่างย่อหน้า](privacy-notice-research-use-draft.md)) ทางที่กันได้จริงคือหยาบทั้งวันที่และน้ำหนักพร้อมกัน ต้องให้ operator ตัดสิน
- รายการลบของข้อมูลฟาร์มว่างจนกว่าฐานการใช้ข้อมูลฟาร์มมีผล แล้วมีเฉพาะแถวที่ถูกลบในหรือหลังวันเริ่มมีผล (แถวที่ไม่เคยออกจากระบบไม่ถูกเปิดเผยแม้เป็นรหัสแฝง)
- ยังไม่ได้ตรวจกับข้อมูลบน staging (เกณฑ์ K14 ต้องได้รับอนุญาตจาก operator ก่อน)
