# Data sovereignty audit — outbound data flows

**Date:** 2026-07-25 · **Scope:** whole monorepo · **Mode:** evidence collection only, nothing removed during the audit

The platform holds Thai citizen personal data under PDPA: national ID numbers,
names, addresses, phone numbers, farm GPS coordinates, uploaded ID-card images,
payment slips and certification records. The owner's requirement is that none of
it leaves Thailand. This audit maps every outbound integration, what data would
actually cross the border, whether the path is live, and what breaks if it is
removed.

Produced by five parallel read-only agents (backend, web, mobile, infra, data
lens), each required to prove a call site rather than infer one from a
dependency being present.



---

# Backend (Express + Prisma API)

_7 PII/credential flows of 17 total_


## Data Sovereignty Audit — `apps/backend/**` (Express + Prisma API)

**Method:** dependency manifest → `require()` call-site trace → caller trace to route/job → payload construction quoted → guard quoted. Every row below was proven by reading the call site; rows marked *no call site* are declared-but-unused dependencies and are reported as such rather than guessed at.

**"Critical" definition used for `criticalCount`:** the flow's payload carries CITIZEN-PII or CREDENTIALS **and** the endpoint is foreign-operated either always (Google, LINE, Twilio) or by the default configuration shipped in this repo's `.env` examples. Flows that only *could* become foreign if an operator repoints a host (generic SMTP, MinIO/S3) are listed but excluded from the critical count, with the repointing risk called out.

### Detail on the two SDKs the brief flagged

#### §3 — Firebase: configured, bundled, unreachable

```ts
export function isFirebaseHealthAuthEnabled(): boolean {
```

```
NEXT_PUBLIC_FIREBASE_HEALTH_AUTH=false
```

`NEXT_PUBLIC_*` is inlined at build time, so this **cannot be flipped at runtime** — a rebuild is required. `build-images.yml:156-165` documents the reason: the backend `FIREBASE_*_AUTH` flags were reverted to `false` on prod+staging on 2026-06-18 for exactly this PDPA cross-border concern.

#### §4 — Sentry: three independent reasons it is dead

### Detail on the two that matter

#### 1. OSM tiles leak farm GPS — LIVE, the only true citizen-PII off-shore flow

Route: `/establishments/new` → `EstablishmentFormScreen` (`lib/core/router/app_router.dart:204-205`), reachable from the authenticated app shell.

Payload construction (`establishment_form_screen.dart`):
```dart
// :47-60  farm coordinate is acquired from the handset
final Position position = await Geolocator.getCurrentPosition();
ref.read(establishmentProvider.notifier).setLocation(
      LatLng(position.latitude, position.longitude),
    );

// :229-245  the map is then centred on that exact coordinate and
//           tiles for that coordinate are fetched from a foreign CDN
FlutterMap(
  options: MapOptions(
    initialCenter: state.selectedLocation!,   // ← the farm
    initialZoom: 15,
    ...
  children: [
    TileLayer(
      urlTemplate: 'https://tile.openstreetmap.org/{z}/{x}/{y}.png',
      userAgentPackageName: 'com.gacp.app',
    ),
```
There is no literal `lat`/`lng` in the URL, but at `initialZoom: 15` the `{z}/{x}/{y}` triple pins the farm to roughly a 1.2 km cell, and the request carries the device's public IP and a self-identifying UA (`com.gacp.app`). Cross-referencing `apps/backend/prisma/schema/farm.prisma:36-37` (`latitude Float?` / `longitude Float?` on the farm record) and `:237-238`, this is the same field the platform treats as farm-location personal data. Every pan/zoom emits more tiles, tightening the fix.

**Blast radius if removed:** delete the `TileLayer` and the map renders blank grey; the coordinate capture (`_getCurrentLocation`, the `onTap` handler at `:234-237` that writes `setLocation(point)`) and the submitted value are untouched, so the establishment record still saves its GPS. User-facing loss = the visual confirmation map on one screen. Straightforward Thai-hosted replacement: point `urlTemplate` at a self-hosted tile server, or **GISTDA / Longdo Map (Metamedia Technology, Bangkok)** tiles — a one-line `urlTemplate` swap in both files, no API change to `flutter_map`.

#### 2. `map_picker_screen.dart` — identical leak, but dead

`grep -rn "MapPickerScreen"` across `lib/` and `test/` returns only its own declaration (`:6,:9,:12,:15`). It is not in `app_router.dart` and is never `Navigator.push`ed. Removing it costs nothing; leaving it means the leak returns the day someone wires it up. Note its UA is still the Flutter template default `com.example.mobile_app` (`:59`) — as is the release `applicationId` (`android/app/build.gradle.kts:9,27`).

#### 3. Google Fonts — LIVE on the login and registration screens

`pubspec.yaml` declares **no** `assets:` block (lines 75-78 are entirely commented out) and there is no `assets/` directory (`ls assets` → not found) and no `google_fonts/` asset folder anywhere in the repo. `GoogleFonts.config.allowRuntimeFetching` is never set (grep returns zero hits). Therefore `google_fonts` 6.3.3 takes its default path: an HTTP GET to `fonts.gstatic.com` for the Sarabun file on first use, cached to app storage afterwards.

Call sites, all on unauthenticated entry screens:
- `lib/presentation/features/auth/screens/login_screen.dart:5` (import), `:141` — `GoogleFonts.sarabun(...)` on the title `'ระบบรับรองมาตรฐาน GACP'`; route `/login` (`app_router.dart:76`).
- `lib/presentation/features/auth/screens/registration_screen.dart:5`, `:376` (app-bar title `'ลงทะเบียนผู้ใช้ใหม่'`), `:475` (`'เลือกประเภทผู้ใช้งาน'`); routes `/register` and `/register/*` (`app_router.dart:80-97`).

No application data is in the payload — only the font request, the device IP and UA. It is nonetheless a Google callback fired by every citizen at the login screen, before any consent.

**Blast radius:** 3 call sites, zero logic. `AppTheme` already declares `fontFamily: 'Kanit'` (`lib/core/theme/app_theme.dart:71,103,116,195,227,240`) — and that family is *also* not bundled as an asset, so it currently silently falls back to the system font. The clean fix is to bundle Sarabun/Kanit TTFs under `assets/fonts/`, declare them in `pubspec.yaml`, replace `GoogleFonts.sarabun(...)` with `TextStyle(fontFamily: 'Sarabun', ...)`, and drop the dependency. This also fixes the existing Kanit fallback bug. Nothing else in the app imports `google_fonts`.

#### 4. Geolocator → Play Services network location

`geolocator_android` resolves position through `FusedLocationProviderClient` unless `forceLocationManager: true` is passed — grep shows no `LocationSettings`/`forceLocationManager` anywhere, and the single call is the bare `Geolocator.getCurrentPosition()` at `establishment_form_screen.dart:57`. On a cold fix Play Services uploads surrounding Wi-Fi/cell identifiers to Google to compute the position. `AndroidManifest.xml:2-3` grants `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION`.

**Blast radius:** one call site. Fix is a parameter, not a removal — `Geolocator.getCurrentPosition(locationSettings: AndroidSettings(forceLocationManager: true))` keeps the feature and uses the raw GNSS/`LocationManager` path with no Google round-trip. No user-facing change beyond a slower first fix.

## Headline

The three biggest sovereignty facts are not SDKs — they are the hosting and delivery chain itself:

1. **Every citizen request is terminated by Cloudflare (US) before it reaches the origin.** Thai national IDs, ID-card image uploads, payment slips and GPS coordinates all traverse a foreign edge in plaintext-at-the-edge.

Firebase and Sentry — the two things one would expect to be the problem — are both **wired but disarmed**, with explicit PDPA comments explaining why. That work is already done; the infrastructure layer is where the exposure actually is.

> ### ⚠️ `healthIdHash` is NOT a safe pseudonym
> `healthIdHash` = `crypto.createHash('sha256').update(String(text)).digest('hex')` — **unsalted, unkeyed SHA-256** (`apps/backend/shared/encryption.js:130-133`, wired at `apps/backend/services/prisma-auth-service.js:155`).
> A Thai national ID is 13 digits with a checksum → search space ≈10¹¹. An unsalted SHA-256 over that space is exhaustively reversible on a single GPU in hours. **Treat `healthIdHash` as equivalent to the plaintext national ID wherever it crosses a border.** The `*Hmac` columns (auth.prisma:34-38) are the keyed replacement, but they are not yet what Firebase uses.

## PART 5 — PII IN LOGS AND ERROR PAYLOADS

**The active logger performs no redaction.** `apps/backend/shared/logger.js` is 37 lines — plain Winston, `format.json()`, **Console transport only** (:9-14, :21-26). No `redact`, `sanitize`, `mask` or `scrub` anywhere in it.

Consequences:

1. **Logs stay in-country by default.** Console-only means stdout → Docker logs → the host. With `@logtail` broken and `@sentry/node` unrequired, **no log shipper currently exports these lines abroad.** The exposure is local-only *today* — and that is exactly what would change the moment a DSN or a log-shipping sidecar is added.
2. **`services/notification/providers/sms-provider.js:126-132`** — the mock SMS path logs the **full message body and recipient phone number** at `info` level (`logger.info('[sms-provider:mock] send', {to, body, ...})`). In dev/test that is every notification's PII in plaintext logs. Since `SMS_PROVIDER` defaults to `'mock'` (:82), this is the default path.
3. **`services/sms/sms-service.js:115`** logs `[SMS:Twilio] Sent to ${phone}` — recipient number in the log line.
4. **Error paths log raw messages** — e.g. `firebase-auth-handlers.js:154,234,366,441` (`logger.error(..., error.message)`) and `scheduler-audit-schedules-post-handler.js:381` (`logger.error('[provider] create audit schedule failed:', error)` — the **whole error object**). Harmless to stdout; **these are precisely the call sites that would feed Sentry** if Flow 6 were switched on, since `production-logger.js:101-111` wraps `logger.error` → `Sentry.captureException`.

**Good practice already present** (worth preserving during any refactor):
- `maskIdentifier()` (`firebase-auth-handlers.js:28-33`) truncates the national ID to `1234****` before it reaches `AuditLog.metadata`, with an explicit PDPA data-minimisation rationale (:23-27).
- `maskThaiId()` is applied to actor identity in audit metadata (`scheduler-audit-schedules-post-handler.js:40,315`), citing PDPA Section 27.
- `sanitizeUserPayload()` gates the user object on every auth response (firebase-auth-handlers.js:207,414).
- Sentry Session Replay and profiling are explicitly disabled with a documented PDPA rationale (`sentry.client.config.ts:10-16`).

## RECOMMENDED ORDER OF REMOVAL

1. **Zero-risk, do now** — dead code: `production-logger.js` + `@sentry/node`, `google-meet-service.js`, `line-notify-service.js`, the Gmail/SendGrid/SES branches of `email-service.js`, `sendViaTwilio`. Nothing calls any of them.
2. **Low-risk, high-value** — Sentry web (Flow 6): remove the build wrapper before someone provisions a DSN. Vendor Google Fonts into the 14 PDF templates. Set `CHECKPOINT_DISABLE=1`. Vendor tesseract traineddata. Swap the Drive link.
3. **Needs a replacement chosen first** — OSM tiles → a Thai tile source (affects 4 call sites + CSP); `SMTP_HOST` → a Thai relay; Flutter `google_fonts` → bundled TTF.
4. **Coordinate with the auth owner** — Firebase (Flow 2) and Google Calendar (Flow 1). Both are already off. Firebase removal is safe because the legacy login path is fully self-hosted and the FE fallback is explicit, but it touches auth and deserves a deliberate PR with the auth-hardening gate (`npm run gate:auth-hardening`) green.

**Independent of removals — the highest-leverage fix in this report:** migrate `Firebase uid` (and any other external identifier) off `healthIdHash`. The unsalted-SHA-256 columns are a re-identification liability *inside the database too*, not just at the border. The keyed-HMAC migration is already designed and half-built (`auth.prisma:34-38`, `AUTH_LOOKUP_USE_HMAC`, RFC `docs/handoffs/H-4-national-id-hmac-migration-rfc.md`) — finishing it retires the risk at its source.
