## 2. สี่รู และการปิด

### H1 — ปิดทางยึด workspace องค์กรด้วยเลขทะเบียน (sweep ID-01 + ID-05)

**รู:** `ensureJuristicEntity`/`ensureCommunityEntity` เป็น find-or-create คีย์ด้วย hash เลขทะเบียน (ข้อมูลสาธารณะ) แล้ว **upsert ผู้เรียกเป็น OWNER ของ entity ที่มีอยู่แล้ว** โดยไม่พิสูจน์อะไร (`entity-service.js:1455-1584` — upsert ที่ :1499-1513, :1567-1581) — เส้นเรียก: `POST /api/entities` + branch `needsLegacyMaterialise` ใน `/prepare` (`applications.js:1016-1032`)

**การปิด:**
- **ไม่พบ entity เดิม** → สร้างใหม่ + ผู้สร้างเป็น OWNER (เหมือนเดิม — การพิสูจน์เอกสารต่อเจ้าหน้าที่อยู่ M2 §5)
- **พบ entity เดิม + ผู้เรียกเป็นสมาชิก OWNER ACTIVE อยู่แล้ว** → คืนสำเร็จแบบ idempotent (คง docstring `entity-service.js:1444-1447` — กัน double-click/retry ของเจ้าของจริง ซึ่ง FE เรียกจาก `workspaces/new/page.tsx:65`)
- **พบ entity เดิม + ผู้เรียกไม่ใช่ OWNER ของมัน** → **ห้าม upsert membership** — 409 `ENTITY_ALREADY_REGISTERED` + ชี้ให้ขอ invite + audit row (actorId + เลขทะเบียนแบบ hash) — แถว audit เหล่านี้คือตัวจับ "การพยายามยึด" ให้ admin เห็น
- ถอด `needsLegacyMaterialise` ทิ้ง (dead code อำนาจสูง ตื่นเฉพาะตอน middleware fail-open) · ผลพลอย: `ensureEntityFromApplicantData` เหลือ 0 caller ใน production — ถอดด้วย พร้อม comment ค้างที่ `application-applicant-query-methods.js:244` (ตรวจแล้ว wizard จริงไม่พึ่ง — FE สร้าง entity ทาง `POST /api/entities` เท่านั้น)

**AC:** (1) B เรียกด้วยเลขทะเบียนของ entity ที่ A เป็น OWNER → 409 + ไม่มี membership ใหม่ + มี audit row (2) A (OWNER เดิม) เรียกซ้ำ → สำเร็จ idempotent ไม่มี row ใหม่ (3) เลขทะเบียนใหม่ → สร้างได้ OWNER (4) grep `needsLegacyMaterialise|ensureEntityFromApplicantData` ใน production path = 0

**ความเสี่ยงที่เหลือ (ประกาศตรงๆ):** ทางสร้าง entity ใหม่ยังเป็น first-come-first-owner — คนแรกที่พิมพ์เลขทะเบียนบริษัทที่ยังไม่อยู่ในระบบได้เป็น OWNER และเจ้าตัวจริงที่มาทีหลังเจอ 409 (squat-then-block) · ผู้ถือความเสี่ยงถัดไป: **M2 §5 (ยืนยันองค์กรผ่านตาเจ้าหน้าที่ในคำขอแรก) + เส้น dispute ฝั่ง admin (ทะเบียนหนี้ — operator จัดเวฟ)** — ไม่ใช่หนี้ลอย

### H2 — mask ข้อมูลบุคคลใน GET /api/entities/:id (sweep ID-03 + SC-10)

**รู:** endpoint คืน `thaiCitizenId` ถอดรหัสแล้ว **และ** `payload` ทั้งก้อน (มี `director.idCard` plaintext — `routes/api/entities/index.js:155`, `entity-service.js:1386-1413`) ให้สมาชิกทุก role รวม VIEWER — ขณะพี่น้อง `listMembersForEntity` mask แล้วที่ service boundary (`entity-service.js:1164-1171` — mask ให้**ทุก role รวม OWNER**)

**การปิด:** mask ตาม convention พี่น้องเป๊ะ = **ทุก role รวม OWNER**: `thaiCitizenId` ผ่าน masker เดิม + `payload.director.idCard` mask แบบเดียวกัน (field อื่นใน payload คงเดิม — ไม่ใช่ PII ระดับเลขบัตร)

**AC:** ทุก role (VIEWER/MANAGER/ADMIN/OWNER) อ่าน entity → เลขบัตรทั้งสองจุดถูก mask · เทส pin สอง endpoint ด้วย fixture เดียวกัน

### H3 — เส้นออกใบหาฟาร์มด้วย entity ก่อนเสมอ (sweep FA-01 + SC-05)

**รู:** `resolveFarmForCertificate` ค้นฟาร์มด้วย `ownerId: app.applicant.id` ทุกทาง (`certificate-service.js:454,466,511,530`) → workspace หลายคน: ผู้ยื่น ≠ ผู้สร้างฟาร์ม = เกิด "Certified Farm" ผี VERIFIED · และเส้น reuse **เขียนทับ** farmName/address/พื้นที่ของฟาร์มจริงด้วย payload ใบสมัคร (`:577-592`)

**การปิด (ก้าวแรกของ G1 — ยังไม่รื้อ 124 จุด):**
- ทุก lookup (by id / by name / by address): ลอง **entity-scope ก่อน** (`entityId: app.entityId` เมื่อมี) — **พลาดแล้วจึง probe `ownerId` ต่อเป็นราย lookup** (ไม่ใช่เงื่อนไขระดับ `app.entityId == null` — ฟาร์ม legacy ที่ `entityId` ยัง null ต้องยังถูกเจอผ่าน ownerId แม้คำขอมี entity มิฉะนั้นฟาร์มผีเกิดซ้ำกับแถว legacy พอดี) · ทุกครั้งที่ขา ownerId เป็นตัวเจอ: log + counter ลง evidence (drain metric)
- ขา ownerId ที่เจอฟาร์มซึ่ง `entityId` ไม่ null และ**ไม่ตรง** `app.entityId` → ไม่ใช้ (ฟาร์มของ entity อื่น) — กันใบไปเกาะฟาร์มข้ามองค์กร
- **เลิกเขียนทับฟาร์มที่ reuse**: เปลี่ยนเป็น fill-only-null (เติมเฉพาะช่องว่าง) — ข้อมูลฟาร์มจริงที่สมาชิกอื่นสร้างต้องไม่ถูก payload ของผู้ยื่นทับ (รีวิว M-2)
- ฟาร์มสร้างใหม่ stamp `entityId: app.entityId ?? null` (ตามจริงของโค้ด `:569` — แถว legacy ได้ null)

**AC:** (1) ฟาร์ม entityId=E + คำขอของ E ยื่นโดย B (ไม่ใช่คนสร้างฟาร์ม) → ใบเกาะฟาร์มเดิม ไม่มีฟาร์มใหม่ (2) **ฟาร์ม legacy (entityId null, ownerId=ผู้ยื่น) + คำขอมี entityId → ใบเกาะฟาร์ม legacy เดิม ไม่มีฟาร์มใหม่** + counter fallback ขยับ (3) ฟาร์มของ entity อื่น → ไม่ถูก reuse (4) reuse แล้วข้อมูลเดิมของฟาร์ม (ชื่อ/ที่อยู่/พื้นที่ที่มีค่าแล้ว) ไม่เปลี่ยน — pin ค่าก่อน/หลัง

### H4 — ประตู role เก่าเลิกตัดสินเอง ให้ guard M1 ตัดสินเดียว (sweep ID-02)

**รู:** ที่ `/submit` ประตู role เก่า (`applications.js:617-630`) ตัดสิน**ก่อน** guard (`:651`) และไม่นับ grant — FE ส่ง header เสมอ ⇒ ผู้ถือ grant โดน 403 เสมอบนเว็บจริง = M1 D6 ถูกทำหมัน (PR-C จดคอมเมนต์ tension ไว้แล้ว — ตอนนี้ operator เคาะ: ยุบ)

**การปิด:** ถอดประตูเก่า — guard M1 (engine: role defaults ∪ GRANT − REVOKE) ตัดสินเดียว · **supersede อย่างเป็นลายลักษณ์อักษร**: เทส `applications-submit-capability-gate.test.js:193-211` (เคส VIEWER/MANAGER 403 `CAPABILITY_DENIED`) พลิกเป็น pin ที่ guard ด้วย code `ENTITY_PERMISSION_DENIED` (ตรวจแล้ว FE/mobile ไม่ผูก `CAPABILITY_DENIED` — 0 hits) + ประโยค "ต้องยังเขียว" ใน plan M1 (`...-farm-holds-certificate.md:380`) และ comment `applications.js:639-647` ถูกยกเลิกโดย spec นี้

**AC:** (1) MANAGER/VIEWER ไม่มี grant → 403 (ความหมายเดิม — engine ให้อยู่แล้วเพราะ MANAGER ไม่มี SUBMIT_APPLICATION ใน defaults) (2) MANAGER มี GRANT → สำเร็จ**ทั้งที่ส่ง header** (เคสที่วันนี้พัง) (3) REVOKE ทับ role → 403 (4) mutation: คืนประตูเก่า → เทส (2) ต้องแดง

**แฝดที่ไม่แตะในเวฟนี้ (ทะเบียนหนี้):** pattern role-only เดียวกันที่ `certificates.js:302-311` ทำให้ grant `PRINT_QR` ตายแบบเดียวกัน — บันทึกแล้ว ห้ามหายเงียบ
