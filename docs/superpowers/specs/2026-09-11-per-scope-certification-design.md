## 1. โมเดล

ผู้ยื่นติ๊กลักษณะพื้นที่ N แบบ ⇒ ระบบสร้าง **N เคส** (คำขอพี่น้อง) **เลขอิสระคนละใบ**
ผูกกันด้วย `batchId` · ทุกฝ่ายหลังจากนั้นทำงาน **รายเคส**

```
กรอกครั้งเดียว · แนบเอกสารครั้งเดียว
        │
        ▼  fan-out
┌───────────────┬───────────────┬───────────────┐
│ เคส A กลางแจ้ง │ เคส B โรงเรือน │ เคส C อาคาร   │   ← เลขคนละเลข
└───────────────┴───────────────┴───────────────┘
        │
   งวดที่ 1 : **รายเคส** เคสละ 5,885 — สามใบแจ้งหนี้
        │
        ▼  ตรวจเอกสาร — รายเคส · มอบหมายคนละคนได้
   ผ่าน A · ยังแก้ B · ตก C
        │
   งวดที่ 2 : **รายเคส เฉพาะเคสที่ผ่าน** (29,425 ต่อเคส)
        │
        ▼  ลงพื้นที่ · รายงาน · อนุมัติ — รายเคส
        ▼  ใบรับรอง — เคสละใบ อายุนับจากวันที่เคสนั้นผ่าน
```

**ดีไซน์นี้เคยมีอยู่ในระบบแล้ว**: `Application.batchId` · `areaTypeIndex` · `totalAreaTypes`
ยังอยู่ใน schema · คอมเมนต์ในไฟล์เขียนเองว่าเป็น *"a dead design in which one submission
fanned out into N sibling applications, one per area type"* ⇒ เรากำลังรื้อฟื้น ไม่ใช่สร้างใหม่
**ยังไม่ทราบว่าทำไมถูกทิ้ง** — หาใน git ไม่เจอเหตุผล ถือเป็นความเสี่ยงที่ต้องเฝ้าระหว่างทำ

> QT / INV / รีซีต งวดที่ 1 จะตรงกับ INV / รีซีต ขั้น 2 ตรงนี้ต้องคำนึงถึง finance"*
>
> งวด 2 จ่ายเฉพาะเคสที่ผ่าน ⇒ ถ้างวด 1 เป็นยอดรวมก้อนเดียว จะกระทบยอดระหว่างสองงวด
> ไม่ได้เลย — เงินเข้าก้อนหนึ่งแล้วออกเป็นสามก้อนย่อยที่ไม่ตรงกับก้อนแรก
>
> **ข่าวดี: โครงสร้างรองรับอยู่แล้ว** — `Quotation.applicationId` · `Invoice.applicationId`
> และใบเสร็จห้อยจากใบแจ้งหนี้ ⇒ เมื่อหนึ่งเคส = หนึ่งคำขอ สายเอกสาร
> **ใบเสนอราคา → ใบแจ้งหนี้ → ใบเสร็จ ของทั้งสองงวด จะถือเลขคำขอเดียวกันโดยอัตโนมัติ**
> การเงินจึงตอบได้ว่าเคสหนึ่ง ๆ จ่ายครบหรือยัง โดยไม่ต้องสร้างตัวผูกใหม่
| M8 | ใบรับรอง | เคสละใบ · **อายุ 1 ปี (ยืนยันแล้ว)** นับจากวันที่เคสนั้นผ่าน · ต่ออายุแยกใบ |
| M9 | ฟาร์ม/บันทึกปลูก | **เลือกใบรับรองก่อน** → ระบบเติมและ**ล็อก** ปลูกอะไร ปลูกแบบไหน พื้นที่เท่าไร |

## 3. "ตก" มีสามความหมาย — ต้องแยกให้ขาด

| สภาพ | สถานะ | เคสยังมีชีวิตไหม |
|---|---|---|
| อยู่ระหว่างแก้เอกสาร | `REVISION_REQUESTED` | **ยัง** · นาฬิกา 5 วันทำการเดินอยู่ · แก้แล้วกลับ `ASSIGNED_FOR_REVIEW` วนได้ |
| อยู่ระหว่างแก้หลังลงพื้นที่ | `CAR_PENDING` | **ยัง** · แก้แล้วไป `CAR_REVIEWING` |
| หมดเวลา | `EXPIRED` | **ตายถาวร** (cron ตัด) |
| ผู้ตรวจปฏิเสธตรง | `REJECTED` | **ตายถาวร** |

กติกา: เคสที่ยังมีชีวิต **ไม่เรียกเก็บงวด 2** และ **ไม่ขวางเคสพี่น้อง** ·
เคสที่ตายถาวร อยากได้รูปแบบนั้นต้อง **ยื่นเคสใหม่ เลขใหม่ จ่ายงวด 1 ใหม่**
(ตรง กทล.๑ ส่วนที่ ๔ (๓) *"ไม่เปลี่ยนพื้นที่…โดยไม่ยื่นคำขอใหม่"*)

**เคสที่ตายต้องไม่ลากพี่น้องตาย** — สามเคสเป็นคนละคำขอ จึงเป็นธรรมชาติ แต่ต้องมีด่านตรึง
เพราะ cron ที่ตัด `EXPIRED` ทำงานราย row และไม่มีใครบอกมันเรื่อง batch

## 4. สิ่งที่แต่ละฝ่ายต้องเห็น

| บทบาท | เห็นอะไร |
|---|---|
| ผู้ยื่น | กรอกครั้งเดียว · เห็นสามเคสและสถานะรายเคส · **จ่ายรายเคสทั้งสองงวด** |
| คนส่งคิวงาน | **สามชุด ไม่ใช่ชุดเดียวที่เขียนว่า 3 รูปแบบ** · มอบหมายผู้ตรวจเอกสารคนละคนต่อเคสได้ |
| ผู้ตรวจเอกสาร | เคสของตัวเอง พร้อมเอกสารที่สำเนามาแล้ว |
| คนแจกงานลงพื้นที่ | ภาพรวม "ขอมา 3 ผ่าน 1" · **เลือกได้**ว่าส่งเฉพาะที่ผ่าน หรือรอให้ครบ |
| ผู้ตรวจแปลง | รายงาน **แยกตามเคส** ต่อหนึ่งแปลงปลูก |
| ผู้อนุมัติ | อนุมัติ **แยกใบคำขอ** |

## 5. ฟาร์มและบันทึกการปลูก (M9)

**เลือกใบรับรองก่อน** แล้วระบบเติมจากใบนั้นและล็อกไว้:
ปลูกอะไร (ชนิดพืช) · ปลูกแบบไหน (ลักษณะพื้นที่) · พื้นที่เท่าไร

ใบรับรองกลายเป็น **แม่แบบที่ล็อกข้อมูล** ไม่ใช่ผลลัพธ์ที่ตามมาทีหลัง ⇒ ข้อมูลฟาร์มและ
บันทึกการปลูกดริฟต์ออกจากสิ่งที่รับรองไว้ไม่ได้

ด่านที่มีอยู่แล้วและใช้ต่อได้ทันที: `certified-scope.certifiedAreaTypes` อ่าน **ทุกใบที่ยังมีผล**
ของฟาร์มแล้วรวมขอบข่าย (เสร็จ `91ae7a56`) · `plots.js` และ `planting-service` เรียกมันอยู่แล้ว

## 6. สิ่งที่ต้องกวาดออก เพราะกลายเป็นส่วนเกิน

เมื่อหนึ่งเคสมีหนึ่งรูปแบบ สิ่งเหล่านี้ไม่มีเหตุผลให้มีอยู่:

- `AuditScopeResult` + `audit-scope-results.js` + ด่านใน `submitDecision` — ผลรายรูปแบบ
  ภายในงานตรวจเดียว · เคสละรูปแบบแล้ว ผลของเคสคือผลของรูปแบบนั้น
- `audit-visit-area-types.js` + `auditSchedule.areaTypes` — การนัดของเคสครอบคลุมรูปแบบเดียว
  เสมอ ไม่มีอะไรให้เลือก

**ที่คงไว้และเหตุผล** — `CertificateScope` ยังอยู่ แม้หนึ่งใบจะมีแถวเดียวเสมอ เพราะมันคือ
**บันทึกว่าใบนี้รับรองอะไรไว้ ณ วันที่ตัดสิน** พร้อม `auditId` ที่พิสูจน์ · ก่อนหน้านี้ขอบข่าย
ถูกอ่านจากคำขอสด ๆ แปลว่าสิ่งที่ตัดสินไปแล้วเปลี่ยนตามข้อมูลคำขอ · ยุบเป็นคอลัมน์ก็ได้
แต่เป็น migration อีกใบบนฐานที่แชร์กัน โดยไม่ได้พฤติกรรมอะไรเพิ่ม

## 8. คำถามที่ปิดไปแล้ว และที่ยังเหลือ

**ปิดแล้ว (operator 2026-09-11):**
- **อายุใบรับรอง = 1 ปี** · เป็นมติของเจ้าของ scheme ไม่ใช่การอ้างเอกสารกรม —
  เอกสารทางการสองฉบับไม่ได้ระบุอายุ และข้อเท็จจริงนั้นยังเป็นจริง ⇒ ถ้ากรมประกาศ
  อายุที่ต่างไป ต้องกลับมาแก้มตินี้
- **ออกใบตามจำนวนรูปแบบที่ขอ** · สามรูปแบบ = สามใบ · ต่ออายุแยกใบ
- **เกณฑ์ข้อไหนต่างกันตามลักษณะพื้นที่** — ไม่ต้องมีตารางเกณฑ์รายลักษณะเลย
  operator: *"คนประเมินคือคนลงพื้นที่"* ⇒ ผู้ตรวจเป็นคนตัดสินต่อเคส และแบบประเมิน
  25 ข้อใช้ชุดเดียวได้ · ที่เคยคิดว่าต้องรอ "เกณฑ์มาตรฐาน GACP" จากกรม ไม่ต้องรอ

**ยังเหลือ:**
1. **ทำไมดีไซน์ fan-out เดิมถูกทิ้ง** — ตอบไปแล้วบางส่วน: มันไม่ได้ถูกทิ้ง มันถูกย้าย
   จาก `batchId`/`areaTypeIndex` (แตกอัตโนมัติ) มาเป็น `ApplicationBundle` ที่ผู้ยื่น
   ประกอบเอง · สิ่งที่ยังไม่ทราบคือทำไมถึงเลิกแตกอัตโนมัติ — เฝ้าไว้ระหว่างทำ
