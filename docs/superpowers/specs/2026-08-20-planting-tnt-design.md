# การปลูก + Track & Trace (QR หลังใบรับรอง) — design

**วันที่:** 2026-08-20 · **สถานะ:** อนุมัติโดย operator ในห้อง brainstorm (คำต่อคำอยู่ใน session log) ·
**ที่มา:** sketch กระดาษ 5 แผ่นของ operator + grill 11 คำถาม — เอกสารนี้คือคำตอบที่เคาะแล้วทั้งหมด ไม่มีข้อเปิด

## 1. เป้าหมาย

เกษตรกรที่**ได้ใบรับรอง GACP แล้ว** บันทึกการปลูกจริงในระบบ แล้วได้ QR ที่ผู้รับซื้อ (โรงงาน)
และผู้บริโภคสแกนดู **timeline การปลูกจริง + ผลตรวจ Lab + การเก็บเกี่ยว** ได้ — เพื่อให้ใบรับรอง
แปลงเป็นมูลค่าการขายได้จริง ไม่จบแค่กระดาษ

## 2. กติกาที่ operator เคาะ (ห้ามตีความใหม่โดยไม่ถาม)

| # | กติกา |
|---|---|
| R1 | ข้อมูลฟาร์มในแบบฟอร์มขออนุญาต = การประกาศ "**จะปลูก**" (intent) — อยู่กับใบคำขอเท่านั้น **ไม่มีผลใดๆ ต่อเมนูการปลูก**: ไม่ prefill ไม่แสดง ไม่ sync |
| R2 | **ห้ามใช้ระบบบันทึกการปลูกก่อนได้ใบรับรอง** — ทั้งเมนูล็อกจนกว่าผู้ใช้มีใบ GACP ที่ active |
| R3 | **QR ออกได้หลังมีใบรับรองเท่านั้น** (เป็นผลอัตโนมัติจาก R2 — รอบปลูกเกิดได้เฉพาะหลังมีใบ) |
| R4 | ผลตรวจ Lab ผูกระดับ **HarvestBatch** (รอบเก็บเกี่ยว) — ทุก Lot ที่แบ่งจาก batch สืบทอดผลเดียวกัน |
| R5 | **เกษตรกรอัปโหลดผล Lab เอง** (ไม่มี role ห้อง Lab เฟสนี้) — แสดงทันทีพร้อมป้ายสถานะตรงไปตรงมา |
| R6 | โรงงาน/ผู้รับซื้อ = **คนสแกนดูอย่างเดียว** เฟสนี้ (ไม่มี login ฝั่งผู้ซื้อ) |
| R7 | **ผล Lab = optional** (ไม่บล็อกขั้นไหนทั้งสิ้น) แต่ **ข้อมูลการปลูก + ข้อมูลแปลงปลูก = บังคับครบทุกช่อง** ตั้งแต่สร้างรอบปลูก |
| R8 | **ไม่ทำระดับ "ต้น" อีกแล้ว** — ไม่มีติดตาม/QR รายต้น (PlantUnit) ความละเอียดของระบบจบที่ รอบปลูก/แปลง และ Lot สินค้า · "จำนวนต้น" เป็นแค่ตัวเลขในข้อมูลรอบปลูก ไม่ใช่การติดตามรายหน่วย |
| R9 | **หน้า public แจ้งแค่ว่า "มี/ไม่มี" ผลตรวจ** — ไฟล์ COA และค่าผลตรวจไม่ขึ้น public โรงงานขอเอกสารจากเกษตรกรเองผ่านช่องทางติดต่อ (แทนที่มติ "สองชั้น" เดิมจากรอบ grill — เปลี่ยนเพราะไฟล์ COA มี PII ของเกษตรกรในตัวเอกสาร) |

## 3. โครงสร้าง

สองเลนขนาน เชื่อมกันที่ "ใบรับรอง" เท่านั้น:

```
เลน 1 (เดิม ไม่แตะ):  Register → คำขอ → จ่าย 5,000 → ตรวจเอกสาร → จ่าย 25,000 → ตรวจฟาร์ม → ใบรับรอง
                                                                                        │ (เลขใบ = กุญแจเปิดเลน 2)
เลน 2 (งานนี้):        เมนูการปลูก [ล็อกจนมีใบ] → รอบปลูก(+QR แปลง) → บันทึกดูแล/ปุ๋ย
                        → เก็บเกี่ยว (HarvestBatch) → ผล Lab (อัปโหลด) → แปรรูป/Lot (+QR สินค้า)
                        → หน้าสแกนสาธารณะ (timeline)
```

ของที่มีอยู่แล้วและจะใช้ต่อ: `PlantingCycle` `CareLog` `FertilizerRecord` `HarvestBatch` `Lot`
`TraceQrSecurity` `TraceQrScan` + route `routes/api/trace/*` + หน้า `/health/planting` `/trace/*`
(สำรวจ 2026-08-20 — โครง API+UI มีแล้ว งานคือแก้ gate/เพิ่มขา Lab/ทำ timeline)

## 4. การเปลี่ยนแปลงหลัก

### 4.1 ประตูเมนูการปลูก (R1+R2)
- `/health/planting/*` ตรวจว่าผู้ใช้มีใบรับรอง active → ไม่มี = หน้า lock อธิบายว่าต้องได้ใบก่อน (ลิงก์ไปเมนูคำขอ)
- ตอนสร้าง**แต่ละรอบปลูก**: เลือกใบรับรองที่คุ้มครองรอบนั้น (ผู้ใช้มีใบ active ใบเดียว = เลือกให้อัตโนมัติ) → `PlantingCycle.certificateId` (คอลัมน์ใหม่)
- **เลิก**ดึงรายการฟาร์มจากฝั่งคำขอใน `/health/planting/new` (ปัจจุบัน `client-view.tsx:58-101` ดึง+กรองใบรับรอง) —
  เกษตรกรกรอกข้อมูลแปลงปลูกจริงใหม่ในเมนูนี้ — **บังคับครบทุกช่อง (R7) ตั้งแต่ตอนสร้างรอบ ไม่มี submit แบบขาด**:
  ชื่อแปลงปลูก, ตำบล/อำเภอ/จังหวัด, พิกัด (เก็บภายใน), ขนาดพื้นที่**พร้อมหน่วย** (บทเรียน areaUnit),
  พืช+สายพันธุ์+แหล่งที่มาเมล็ด/ต้นกล้า, วันเริ่มปลูก, จำนวนต้น, วิธีปลูก/วัสดุปลูก, แหล่งน้ำ —
  validator ฝั่ง server บังคับเท่ากับ FE (ประตูเดียวมาตรฐานเดียว)
- ใบหมดอายุ/ถูกเพิกถอนกลางรอบ: บันทึกรอบเดิม**ต่อได้** (ข้อมูลจริงต้องบันทึกได้) แต่**เริ่มรอบใหม่ไม่ได้** จนใบกลับมา active

### 4.2 QR (R3)
- **QR แปลงปลูก**: mint อัตโนมัติตอนสร้างรอบปลูก — ใช้กลไก `TraceQrSecurity`/`generatePublicTraceUrl` เดิม
- **QR สินค้า**: ต่อ Lot ตอนแปรรูป/บรรจุ (ของเดิม `trace/lots.js` มีแล้ว) — หน้า Lot ลิงก์ย้อนถึงรอบปลูก+ผล Lab
- ทั้งสอง QR ผูก `certificateId` — header หน้าสแกนแสดงเลขใบ + ลิงก์ `/verify/<เลขใบ>` เดิม

### 4.3 ผล Lab (R4+R5+R7)
- **Optional ทั้งขา (R7)**: ไม่มีผล Lab ก็สร้างรอบ/เก็บเกี่ยว/ออก Lot/มี QR ได้ครบ — timeline แสดงช่องผล Lab
  เป็น "ยังไม่มีผลตรวจ Lab" ตามจริง (ไม่ซ่อน — โรงงานเห็นว่ายังไม่มีแล้วไปขอเอาเองได้)
- **ไฟล์ COA เป็นข้อมูลภายในเท่านั้น (R9)**: เกษตรกร (เจ้าของ) และเจ้าหน้าที่เห็น — ไม่มี route public ใดเสิร์ฟไฟล์
  หรือค่าผลตรวจ เหตุผล: เอกสาร COA จริงมีชื่อ/ที่อยู่/เลขอ้างอิงของเกษตรกรพิมพ์ในตัวเอกสาร
  การเปิดไฟล์ public = เผยแพร่ PII · หน้า public ได้แค่ existence + วันที่ + ชื่อ Lab
- โมเดลใหม่ `BatchLabResult`: `harvestBatchId` FK, ไฟล์ COA (upload เดิมของระบบ), ชื่อ Lab, วันที่ตรวจ,
  สรุปผล (ผ่าน/ไม่ผ่าน + มาตรฐานที่อ้าง), `uploadedBy` (เกษตรกร), `verificationStatus` (`FARMER_UPLOADED` เริ่มต้น —
  โครงรองรับ `OFFICER_VERIFIED` ภายหน้า แต่**ไม่ build ฝั่งเจ้าหน้าที่เฟสนี้**)
- แสดงบน timeline ทันทีที่อัปโหลด พร้อมป้าย "อัปโหลดโดยเกษตรกร — ยังไม่ผ่านการตรวจสอบโดยเจ้าหน้าที่"
  (ตาม pattern ป้ายตรงไปตรงมาของหน้า verify — `integrity-presentation.ts`)

### 4.4 หน้าสแกนสาธารณะ (timeline)
เนื้อหา (มุมโรงงาน+ผู้บริโภค — เคาะจาก grill ทั้ง 6):

| ข้อมูล | แสดง |
|---|---|
| สถานะใบรับรอง | เลขใบ + สถานะจริงเสมอ (active/หมดอายุ/เพิกถอน) + ลิงก์ verify |
| ผล Lab | **สถานะการมีอยู่เท่านั้น (R9)**: "มีผลตรวจ Lab ✓ — ตรวจเมื่อ <วันที่> โดย <ชื่อ Lab>" หรือ "ยังไม่มีผลตรวจ" · ไม่มีไฟล์ ไม่มีค่า ไม่มีสรุปผ่าน/ไม่ผ่าน — โรงงานขอ COA จากเกษตรกรเอง |
| ตำแหน่งแปลง | ตำบล/อำเภอ/จังหวัดเท่านั้น — พิกัดเป๊ะไม่ขึ้น public |
| ปุ๋ย/สาร | สรุปประเภท (อินทรีย์/เคมี + จำนวนครั้ง + ครั้งสุดท้ายก่อนเก็บกี่วัน) — ไม่แสดงชื่อสาร/สูตร |
| ปริมาณ | เฉพาะที่เก็บเกี่ยวแล้วจริง (จาก HarvestBatch) — ไม่มีตัวเลขคาดการณ์ |
| ติดต่อซื้อ | เกษตรกรตั้งเอง: เบอร์/LINE/ไม่แสดง — **default ไม่แสดง** |
| รูปภาพ | รูปจากการตรวจ onsite (ป้าย "ถ่ายโดยผู้ตรวจ") เป็นฐาน + เกษตรกรเพิ่มได้ (ป้าย "จากเกษตรกร") |
| timeline | ปลูก → บันทึกดูแล → เก็บเกี่ยว → ผล Lab → Lot — เรียงเวลา อ่านบนมือถือเป็นหลัก |

### 4.5 ความปลอดภัย/ความถูกต้อง
- หน้าสแกนเป็น public route — ใช้ rate-limit แบบ keyGenerator ที่ถูกต้อง (บทเรียน BACKLOG:73 อย่าให้ per-path)
- ชื่อบุคคลบน public: mask ตาม pattern หน้า verify เดิม
- ไฟล์ COA: จำกัดชนิด/ขนาดตาม upload policy เดิม; hash เก็บใน record (โครงเดียวกับ fileHash ที่ fraud-detection ใช้)
- เมนูการปลูกอยู่หลัง auth `health` เดิม — ownership ตรวจแบบเดียวกับ IDOR guard ของ certificates

## 5. สิ่งที่ไม่ทำเฟสนี้ (ตัดสินแล้ว ไม่ใช่ลืม)

role ห้อง Lab/login โรงงาน · การแตะ flow สมัคร/คำขอ/การเงิน · ตัวเลขคาดการณ์ผลผลิต ·
การตรวจผล Lab โดยเจ้าหน้าที่ (โครง status รองรับไว้เฉยๆ) · inbox ติดต่อผ่านแพลตฟอร์ม ·
**ระดับรายต้น (R8 — เลิกทิศทางนี้ถาวร)**: `PlantUnit`/QR ต่อต้น/`BULK_PLANT_UNIT_GENERATION`/route `trace/plant/:qrCode`

## 7. แก้ไขเพิ่มเติม 2026-08-23 — QR สองใบ แก้ได้จนตัด แล้วแช่แข็ง (มติ operator)

**คำสั่ง operator (คำต่อคำ):** "หลังบรรจุแล้วต้องแก้ไม่ได้ มันต้องออกมาเป็น 2 QR
1. คือไว้สำหรับอัพเดตการปลูก จนถึงตัด
2. เมื่อตัดแล้ว บันทึกใส่ถูกแล้วจะเปลี่ยนไม่ได้ จะออกมาเป็น QR ที่ 2 สำหรับแปะถุง"

และก่อนหน้านั้นในบทสนทนาเดียวกัน: QR ใบที่ 1 เป็น **รายแปลง** ("ปลูก 1 แปลง 100 ต้น ก็ออกแค่ QR code เดียว")
ออกทันทีที่ลงข้อมูลการปลูกใหม่ · บน PC เกษตรกรต้องจำเองว่าแปลงไหน แต่**บนมือถือ เกษตรกรที่ล็อกอินแล้ว
สแกน QR จากในแปลงได้ แล้วเข้าหน้าอัพเดตของแปลงนั้นตรง ๆ**

### 7.1 กติกาที่มติน้ีตั้งขึ้น (แทนที่ข้อ 4.2 เดิม)

| # | กติกา |
|---|---|
| R10 | **QR มีสองใบเท่านั้น** — ใบที่ 1 รายแปลง (แก้ไขได้) · ใบที่ 2 ต่อการบรรจุ (แก้ไม่ได้) · ไม่มีใบที่สาม |
| R11 | **QR ใบที่ 1 ออกตอนสร้างข้อมูลการปลูก** และเป็นประตูสำหรับ**อัพเดต**บันทึกการปลูก **จนถึงวันตัด** |
| R12 | **ตัดแล้ว = บันทึกการปลูกของรอบนั้นล็อกถาวร** แก้ไม่ได้อีก |
| R13 | **QR ใบที่ 2 ออกตอนบรรจุ** สำหรับแปะถุงส่งโรงงาน · เนื้อหาที่มันชี้คือภาพแช่แข็ง ณ เวลาบรรจุ **เปลี่ยนตามภายหลังไม่ได้เด็ดขาด** |
| R14 | **สแกนเพื่ออัพเดตได้เฉพาะเจ้าของที่ล็อกอินแล้ว** — สิทธิ์มาจาก session ไม่ใช่จากตัวรหัสใน QR · คนแปลกหน้าที่ถ่ายรูป QR ไปสแกน ได้เห็นแค่หน้า public เท่านั้น เขียนอะไรไม่ได้ |

### 7.2 ผลต่อ QR ใบที่ 1 เมื่อขึ้นฤดูใหม่

QR ใบที่ 1 ผูกกับ**แปลง** จึงเป็นป้ายถาวรที่ปักไว้หน้าแปลงได้ ไม่ต้องพิมพ์ใหม่ทุกฤดู
สิ่งที่มันชี้คือ**รอบปลูกปัจจุบันของแปลงนั้น**: รอบที่ตัดไปแล้วล็อกตาม R12 · เริ่มรอบใหม่บนแปลงเดิม =
QR ใบเดิมชี้ไปที่รอบใหม่ที่ยังแก้ได้ · ประวัติรอบเก่ายังสืบย้อนได้จาก QR ใบที่ 2 ของฤดูนั้น ๆ

### 7.3 ช่องว่างที่มติน้ียังไม่ครอบคลุม — ต้องถาม operator

"ตัด" กับ "บรรจุ" ไม่ใช่เวลาเดียวกัน ระหว่างนั้นมี **ตาก/ทำแห้ง/แปรรูป** ซึ่งเป็นข้อมูลที่ต้องบันทึกและ
ผู้ตรวจ GACP สนใจ (ระยะเวลาตาก วิธีทำแห้ง) ถ้าบันทึกการปลูกล็อกตั้งแต่วันตัดตาม R12 ข้อมูลช่วงนี้
ต้องไปอยู่ที่ **HarvestBatch** แล้วไปแช่แข็งพร้อมกันตอนบรรจุ — ยังไม่ได้ยืนยันกับ operator

### 7.4 สิ่งที่ยังต้องมี ไม่งั้นยังไม่ใช่ Track & Trace

- **สมดุลมวล**: น้ำหนักรวมของถุงที่ออก QR ใบที่ 2 ได้ ต้องไม่เกินน้ำหนักที่เก็บเกี่ยวจริง — ถ้าไม่มีตัวคุมนี้ QR กลายเป็นเครื่องฟอกของนอกระบบ

### 8.1 R16 — เงื่อนไขที่ทำให้ยังเป็นมาตรฐานสูงสุด

เหตุผลที่ต้องเลื่อน: "แหล่งที่มาเมล็ด/ต้นกล้า" เป็นช่องที่คนยืนอยู่ในแปลงตอบไม่ได้ทันที
บังคับตอนนั้น = ได้คำตอบมั่วเพื่อให้ผ่านฟอร์ม ซึ่ง**แย่กว่าปล่อยว่าง** เพราะข้อมูลมั่วดูเหมือนข้อมูลจริง

การเลื่อนเส้นตายจะลดมาตรฐานทันทีถ้าไม่มีสี่ข้อนี้ครบ — ทั้งสี่ข้อบังคับ ไม่ใช่ทางเลือก:

1. **ประตูเก็บเกี่ยวปิดตายจริง** — กดเก็บเกี่ยวไม่ได้จนกรอกครบ บังคับฝั่ง server ไม่ใช่แค่ซ่อนปุ่ม
2. **สถานะค้างต้องเห็นตลอด ไม่ใช่ซ่อน** — การ์ดพื้นที่ปลูกขึ้น "ข้อมูลยังไม่ครบ 3 ช่อง" ทุกครั้งที่เห็น ไม่ใช่แจ้งครั้งเดียวแล้วเงียบ
3. **ยังไม่ครบ = ยังไม่มีป้ายถุง** — ป้ายแปลงออกได้ (ต้องใช้บันทึกระหว่างปลูก) แต่ของยังออกสู่ตลาดไม่ได้ ⇒ ไม่มีถุงใดหลุดออกไปพร้อมข้อมูลที่ไม่ครบ
4. **บันทึกด้วยว่ากรอกครบเมื่อไหร่** — ถ้ากรอกครบหลังเริ่มปลูกไปแล้ว 40 วัน ให้เก็บไว้และแสดงตามจริง ตามหลัก "เพิ่มได้ ทับไม่ได้ พร้อมสองเวลา"

ผลรวม: เกษตรกรเริ่มบันทึกได้ทันทีในแปลง (ซึ่งคือสิ่งที่ทำให้ข้อมูลมีคุณภาพ) แต่ **ไม่มีของชิ้นใดออกจากระบบพร้อมข้อมูลที่ไม่ครบ** ซึ่งเข้มกว่า R7 เดิมที่บังคับตอนสร้าง เพราะ R7 เดิมไม่ได้กันการกรอกมั่วเลย

## 10. ข้อ 8(2) ของ มกษ. 3502-2561 ครอบคลุมสองสถานะ — แต่ไม่ได้บังคับว่าต้องเป็น QR

คำต่อคำ: "ระบุ**รุ่นผลิตผล หรือ**ติด**รหัส หรือ**เครื่องหมายแสดงแหล่งผลิต **หรือ**วันที่เก็บเกี่ยว
พืชสมุนไพรที่อยู่ระหว่าง**การเก็บรักษาและขนย้าย** หรือ**บรรจุเพื่อจำหน่าย**"

⇒ ของที่กำลังตากในโรง (ระหว่างเก็บรักษา) **ต้องมีเครื่องหมาย** — แก้ความเข้าใจเดิมที่บันทึกไว้ว่า
QR ของรุ่นเก็บเกี่ยวเป็น "ใบที่สามที่ไม่มีใครออกแบบ" มาตรฐานบังคับให้มีเครื่องหมายจริง

⇒ **แต่คำเชื่อมคือ "หรือ"** ป้ายกระดาษเขียนเลขรุ่น + วันเก็บเกี่ยว ทำตามมาตรฐานได้ครบ
ไม่ต้องเป็น QR และไม่มีใครสแกนของที่อยู่ในโรงตากอยู่แล้ว

**สรุปที่ทั้งถูกกฎหมายและตรงมติ R10 "สอง QR":**

| ของ | เครื่องหมาย | อ้างอิง |
|---|---|---|
| พื้นที่ปลูก | **QR ถาวร** | ข้อ 8(1) บังคับรหัสแปลง + ต้องสแกนบันทึกได้ |
| รุ่นเก็บเกี่ยว (ระหว่างตาก) | **ป้ายกระดาษ** เลขรุ่น + วันตัด | ข้อ 8(2) บังคับเครื่องหมาย ไม่บังคับ QR |
| ถุงบรรจุ | **QR แช่แข็ง** | ข้อ 8(2) + ปลายทางต้องตรวจได้ |

⇒ สิ่งที่ต้องทำคือ**ตัด `HARVEST_BATCH` QR ทิ้ง** (7 จุดมินต์) ไม่ใช่รับใบที่สามเข้ามา — **ยังรอ operator เคาะ**

## 11. แก้ไข 2026-08-24 — R10 เปลี่ยนจาก "สองใบ" เป็น "สามตัวตน" (มติ operator)

**R10 เดิมผิด** เขียนไว้ว่า "QR มีสองใบเท่านั้น ไม่มีใบที่สาม" — เขียนตอนที่ยังไม่มีใครอ่าน
มกษ. 3502-2561 ข้อ 8(2) ซึ่งบังคับให้พืชสมุนไพรที่อยู่ระหว่าง **"การเก็บรักษาและขนย้าย"**
ต้องมีเครื่องหมาย ไม่ใช่แค่ของที่บรรจุขาย

การยืนยัน "สองใบ" เหลือทางเลือกแค่สองทางและแย่ทั้งคู่:
ปล่อยรุ่นที่กำลังตากไม่มีตัวตน = **ผิดมาตรฐาน** · หรือยัดรุ่นไปอยู่ใต้ป้ายแปลง/ป้ายถุง =
**ที่มาพัง** เพราะแปลงหนึ่งออกได้หลายรุ่นต่อฤดู และถุงยังไม่เกิดตอนตาก

**ประโยคที่ตัดสินอยู่ท้ายวรรคของข้อ 8(2): "เพื่อให้สามารถตรวจสอบที่มาได้"** — รายการ "หรือ"
ไม่ได้แปลว่าเลือกอะไรก็ได้ แต่แปลว่าอะไรก็ได้ที่ทำให้ตรวจสอบที่มาได้จริง เกณฑ์คือผลลัพธ์

### เหตุผลที่ตัวที่ 2 ต้องสแกนได้ ไม่ใช่กระดาษเขียนเลข

- **บันทึกการตากต้องผูกกับรุ่นนั้น** คนยืนหน้าถาดตากสามถาดมีปัญหา "อันไหน" เหมือนคนยืนกลางแปลง

- **ข้อ 8(2) ครอบคลุมการขนย้ายด้วย** รุ่นเดินทางไปโรงแปรรูปก่อนบรรจุได้ ปลายทางต้องยืนยันว่ารับถูกรุ่น

  ถ้ารุ่นไม่มีตัวตนที่เครื่องอ่านได้ การเรียกคืนคือการโทรหาทีละคน
