Scope here = **business notifications + dead code (Phases 1+2)**. Phases 3 (MFA-email retirement w/ enrolled-user migration) and 4 (password-reset email → recovery path) are SEPARATE missions gated on prerequisites — explicitly OUT.
> Evidence base: the 3-lane external-services audit (2026-08-17, this session's ledger): 3 email stacks (E1 root `services/email-service.js`, E2 `services/email/email-service.js`, E3 fanout provider/transport) + 2 SMS stacks (S1 `services/sms/sms-service.js`, S2 fanout), two dispatch systems (Path A `notification-service.js` ~30 callers; Path B `notification-fanout-service.js` ~5 callers), and the key fact: **every business notify site already writes the in-app row** — removal loses no in-app notification.

**Goal:** the in-app Notification row becomes the ONLY business-notification channel in code (not just in config): email/SMS dispatch legs removed, transports retired, dead code deleted, secrets catalog and env templates cleaned — WITHOUT touching the two transition-only auth email paths (MFA email-OTP send + password-reset send in E1).

## Binding rules
- **KEEP (transition, per directive):** E1's `sendMfaOtp` + `sendPasswordReset` + the minimal E1 transporter they need. Do not deepen, do not remove — Phases 3/4 own them.
- **DELETE (sanctioned by the recorded operator decision — the flag-only caution does NOT apply to this mission):** every business email/SMS dispatch leg + the E2/E3/S1/S2 stacks + dead methods/templates.
- Every removal site must keep its **in-app row write byte-identical** (tests pin it). No notification TYPE may lose its in-app leg.
- **Secrets/boot safety:** E3/S2 vars are catalogued `required:'production'` in `config/secrets.js` (EMAIL_SMTP_HOST/USER/PASS :262-314; THAIBULKSMS key/secret :319-355) — retiring the transports MUST remove those catalog rows in the same task, or production boot fails validation on vars nothing uses.
- Ratchet must not rise; deletions should DROP counters where they scan the removed dirs.
- Urgent-reach loss (APPLICATION_EXPIRED / SLA breach no longer push offline users) was decided by the operator: in-app now, Web Push follow-up. The runbook/docs note it honestly; no silent capability loss.
