## 2. โครงสร้างและการไหลของข้อมูล

```
ผู้ยื่นอัปโหลด → POST /draft-documents (เดิม ตอบทันทีเหมือนเดิม)
                  └─ enqueue งาน doc-precheck {documentId, slotId, applicationId}
คิว Bull (services/queue-service.js — มีอยู่ใช้สร้าง PDF) → ตัวประมวลผล doc-precheck
   1 extract   : PDF มีชั้นข้อความ → pdf-parse · สแกน/ภาพ → OCR (ocr-service.js, tesseract tha+eng)
   2 checks    : readability · doc-type · cross-match · validity (+ signature = manual เสมอ)
   3 persist   : แถว DocumentPrecheck + DocumentPrecheckFlag (ตารางใหม่)
หน้าผู้ยื่น   ← GET สถานะ/ธงของเอกสารตัวเอง (poll จนเสร็จ)
หน้าเจ้าหน้าที่ ← ธงของช่องบนหน้าตรวจรายช่อง (application-document-review-service.js)
คำตัดสินเจ้าหน้าที่ต่อช่อง → เก็บคู่กับ precheck รอบนั้น → วัดความแม่น
```

**หน่วยงานแยกความรับผิดชอบ** (แต่ละหน่วยทดสอบแยกได้):
- `document-precheck/extract`: ไฟล์ไปเป็นข้อความรายหน้า พร้อมค่าความมั่นใจและจำนวนหน้า เป็นหน่วยเดียวที่แตะไฟล์
- `document-precheck/normalize`: ปรับชื่อ (ตัด "บริษัท … จำกัด" / "นาย/นาง/นางสาว" / ช่องว่าง) แปลงเลขไทยเป็นเลขอารบิก อ่านวันที่ พ.ศ. และเดือนไทย ตรวจ checksum เลข 13 หลัก ทั้งหมดเป็นฟังก์ชัน pure
- `document-precheck/rules/<check>.js`: กฎของแต่ละเรื่อง รับข้อความกับข้อมูลคำขอ แล้วคืนธง ทั้งหมดเป็นฟังก์ชัน pure
- `document-precheck/catalog.js`: ต่อชนิดเอกสาร ระบุวลีบังคับ จำนวนหน้าที่ควรมี เกณฑ์อายุ และที่มาของแต่ละเกณฑ์ เป็นแหล่งเดียว
- `document-precheck/service.js`: รวมขั้นทั้งหมดและบันทึกผล
- `jobs/document-precheck-processor.js`: ตัวประมวลผลของคิว
- `POST /api/documents/verify` เดิมและ `document-analysis-service.js` ถูกลบ เพราะไม่มีผู้เรียกบนเว็บ (grep 2026-09-27) และงานนี้มาแทน

## 3. กฎตรวจ

หลัก: ทุกเกณฑ์ต้องมีที่มาจาก กทล.1 หรือ `reports/research/2026-09-01-dtam-application-baseline/facts.md` เกณฑ์ที่หาที่มาไม่ได้จะไม่ตรวจ

| เรื่อง | ผลที่เป็นไปได้ | กฎ |
|---|---|---|
| readability | `PASS` · `UNREADABLE` · `PAGE_COUNT` | ไฟล์เปล่า/ไม่มีข้อความ หรือค่าความมั่นใจของ OCR ต่ำกว่าเกณฑ์ → `UNREADABLE` (เกณฑ์กำหนดจากชุดทดสอบ ไม่เดา) · จำนวนหน้าผิดจากที่ catalog ระบุ → `PAGE_COUNT` |
| doc-type | `MATCH` · `NOT_FOUND` · `UNREADABLE` | ต้องพบวลีบังคับของชนิดนั้น (จับคู่แบบคลาดเคลื่อนได้เล็กน้อยเพื่อรับ OCR ที่เพี้ยน) · อ่านไม่ออกไม่นับว่าผิดชนิด |
| cross-match | `MATCH` · `MISMATCH` · `NOT_FOUND` | เทียบกับข้อมูลที่ผู้ยื่นกรอก: ชื่อนิติบุคคล · เลขนิติบุคคล 13 หลัก · เลขโฉนด · ชื่อกรรมการ · เลข 13 หลักต้องตรงทุกหลักและผ่าน checksum · ชื่อยอมให้เพี้ยนตามเกณฑ์ที่วัดจากชุดทดสอบ |
| validity | `PASS` · `EXPIRED` · `DATE_NOT_FOUND` | หนังสือรับรองนิติบุคคลต้องออกไม่เกิน 6 เดือน (`facts.md:50`) นับตามเวลากรุงเทพ (สกิล `thai-business-days`) · ชนิดอื่นที่ยังไม่มีที่มาของเกณฑ์จะไม่ตรวจอายุ |
| signature | `MANUAL` เสมอ | ขึ้นรายการให้เจ้าหน้าที่ตรวจลายมือชื่อ/ตรา |

**ข้อความเตือน.** เป็นภาษาไทยตามสกิล `thai-ui-copy` เลขประจำตัวปิดบางส่วน เช่น "…4567" และไม่เอ่ยชื่อเทคโนโลยีเบื้องหลัง

**เมื่อระบบพลาดหรือล่ม**
- งานล้มหรือเกินเวลา: ลองใหม่ตามจำนวนครั้งที่กำหนด ถ้ายังไม่สำเร็จ บันทึกสถานะ `FAILED` พร้อมธง "ตรวจอัตโนมัติไม่สำเร็จ เจ้าหน้าที่จะตรวจเอง" จะไม่มีกรณีที่ผลหายไปเงียบ ๆ
- OCR รันในตัวประมวลผลของคิว จำกัดจำนวนงานที่รันพร้อมกัน และไม่รันใน request ของ API
- อัปโหลดไฟล์ใหม่ในช่องเดิม: precheck เดิมเปลี่ยนเป็น `SUPERSEDED` (เก็บไว้ดูย้อนหลัง) แล้วตรวจไฟล์ใหม่

## 4. ข้อมูล (Prisma, migration แบบ expand อย่างเดียว)

- `DocumentPrecheck`
  - ฟิลด์: id · organizationId · applicationId · documentId · slotId · status (`PENDING`|`DONE`|`FAILED`|`SUPERSEDED`) · rulesVersion · extractMethod (`TEXT_LAYER`|`OCR`) · ocrConfidence · pageCount · extractedText · applicantAcknowledgedAt · createdAt · completedAt
  - extractedText เก็บในฐานของเราเท่านั้น และเข้าเกณฑ์ PDPA retention เดียวกับไฟล์เอกสาร
- `DocumentPrecheckFlag`
  - ฟิลด์: id · precheckId · check · result · reasonTH · confidence · evidenceSnippet (ปิดเลขแล้ว)
- ที่เก็บคำตัดสินของเจ้าหน้าที่: ใช้แถวคำตัดสินรายช่องที่มีอยู่แล้วของ `application-document-review-service` แล้วอ้าง `precheckId` ของรอบที่เจ้าหน้าที่เห็นตอนกด (เพิ่มคอลัมน์ nullable)
- ทุก query เลือกฟิลด์แบบระบุชื่อ (explicit select) · ผ่าน tenant wall (organizationId) · ผู้ยื่นเห็นเฉพาะของตัวเอง · เจ้าหน้าที่ใช้สิทธิ์อ่านเดียวกับหน้าตรวจรายช่อง

## 6. ทดสอบและวัดผล

1. ชุดเอกสารทดสอบ (`apps/backend/__tests__/fixtures/document-precheck/`) สร้างด้วยสคริปต์ ไม่มีข้อมูลจริงของใคร
   - ครอบคลุม 7 ชนิดเอกสาร
   - แต่ละชนิดมี variant: ถูกต้อง · เบลอ/เอียง · ผิดชนิด · ชื่อหรือเลขไม่ตรง · หมดอายุ · ไม่มีวันที่ · PDF มีชั้นข้อความ · PDF สแกน
   - ทุกไฟล์มีคำตอบที่คนกำหนดไว้ (label)
2. เทสหน่วยของ normalize และ rules เขียนแบบ RED-first และต้องผ่านทั้ง `TZ=UTC` และ `TZ=America/Los_Angeles`
3. เทส integration บน Postgres จริงกับ tesseract จริง: อัปโหลด → คิว → ธง → คำตัดสิน โดยไม่ mock ชั้นข้อมูลหรือ OCR
4. สคริปต์รายงานความแม่นยำแยกตามเรื่อง ได้แก่ precision ของธงเตือน recall และอัตรา `UNREADABLE`
   - ตั้งเกณฑ์ขั้นต่ำจากผลรอบแรก จากนั้นเกณฑ์ลดลงไม่ได้ (ratchet)
   - เน้นให้ธงเตือนผิดน้อย (precision สูง) เพราะเตือนผิดบ่อยแล้วคนจะเลิกเชื่อ
5. เก็บ view-pack ทั้งสองฝั่งจากการเดินจริงบน staging
6. วัดเวลาและหน่วยความจำของ OCR ในคอนเทนเนอร์จริง แล้วใช้ผลนี้กำหนดจำนวนงานที่รันพร้อมกัน

## 8. แก้ไขหลังสำรวจโค้ด (2026-09-27 · ก่อนเขียนแผน)

- **เลขโฉนดเทียบไม่ได้:** schema ไม่มีคอลัมน์เลขโฉนด (Plot มีแค่ plotCode, area และพิกัด) จึงไม่เทียบ สำหรับเอกสารที่ดินเทียบได้เฉพาะชื่อผู้ถือสิทธิ์กับชื่อผู้ยื่นหรือชื่อบริษัท ชื่อกรรมการอ่านจาก `Entity.payload.director.name` เลขนิติบุคคลอ่านจาก `Entity.juristicId` ชื่อบริษัทอ่านจาก `Entity.displayName`
- **OCR ยังอ่านภาษาไทยไม่ได้:** `apps/backend/data/tessdata/` มีแค่ README ยังไม่มีไฟล์ภาษาไทย (`tha.traineddata`) และอังกฤษ (`eng.traineddata`) ต้องเพิ่มไฟล์ทั้งสองเข้ารีโปและเข้าอิมเมจ ตรึงเวอร์ชันด้วย sha256 เพื่อให้ OCR อ่านไทยได้ทุกครั้ง ไม่ต้องรอดาวน์โหลดตอนรัน และได้ผลเหมือนกันทุกเครื่อง (เดิมเคยเขียนเหตุผลว่าเพื่อกันข้อมูลออกนอกประเทศ แต่กฎนั้นยกเลิกไปแล้ว)
- **`ocr-service.js` เดิมใช้ไม่ได้:** เรียก Tesseract โดยไม่ส่ง langPath ในเครื่อง และเรียก `pdf-parse` แบบ v1 ทั้งที่ติดตั้ง v2 (class `PDFParse`) งานนี้ใช้ `services/ocr/tesseract-service.js` แทน และใช้ `PDFParse` v2
- **ไม่มีตารางเอกสารที่ผูก tenant:** `ApplicationDocument` ไม่มี organizationId และตั้งใจให้ข้ามองค์กรได้เพื่อตรวจทุจริต ตารางใหม่จึงเก็บ organizationId ที่คัดลอกมาจาก Application และเพิ่มชื่อโมเดลใน `TENANT_SCOPED_MODELS` ที่ `services/tenant-prisma-extension.js`
- **ของที่พึ่งบริการที่จะลบ:** `controllers/plant-controller.js` ที่ `GET /api/cultivation/plants/:plantId/documents` เรียก `getBaseRequirements()` ซึ่งถูกถอดออกจาก `document-analysis-service` ไปแล้ว ประตูนี้จึงน่าจะพังอยู่ งานลบต้องจัดการประตูนี้ด้วย โดยตรวจก่อนว่ามีผู้เรียกบนเว็บหรือไม่
