## 1. บทสรุป

วินัยด้านโค้ดของโปรเจกต์นี้ (probe, ratchet, evidence discipline, การรายงานตามจริง) อยู่สูงกว่า
ฐานปฏิบัติการมาก และช่องว่างนั้นคือความเสี่ยงตัวจริง — ไม่ใช่คุณภาพโค้ด

ข่าวดีที่ต้องพูดเพราะมันจริง: **backup ทำงานจริงและพิสูจน์แล้วว่ากู้ได้** (2 ครั้ง: 2026-08-08 และ
2026-08-13) · **DNS ฝั่งสาธารณะถูกกันไว้ที่ Cloudflare แล้ว** · **ยังไม่เปิดรับเงินจริง** ซึ่งเป็นสิ่งเดียว
ที่กันข้อผิดพลาดเรื่องเลขเงินทั้งหมดไม่ให้กลายเป็นความเสียหายจริง

ความเสี่ยงที่เหลือแบ่งได้เป็นสองกอง: (ก) **ของที่ยิงได้เองโดยไม่ตั้งใจ** — pipeline deploy production
ที่ยังติดอาวุธ และคู่มือ rollback ที่สอนให้กู้ผิดฐาน · (ข) **ของที่หายแล้วหายเลย** — ไฟล์ที่ผู้ใช้อัปโหลด
ไม่ถูกสำรองเลย และสำเนาทั้งหมดอยู่บนดิสก์ก้อนเดียวกับต้นฉบับ

ทุกข้อในแผน §7 **ไม่ต้องใช้เงินเพิ่ม**

## 4. ทะเบียนความเสี่ยง

เรียงตาม (โอกาส × ความเสียหาย)

### R1 — pipeline deploy production ติดอาวุธและทับ staging ได้ **[กวาด+หักล้าง]**

`.github/workflows/production.yml` มี gate เดียวคือตัวแปร repo `ENABLE_PRODUCTION_DEPLOY` (`:173`)
ซึ่งแก้ได้ตลอดเวลา · trigger บน push ไป `deploy/production` (`:19`) และ **branch นั้นมีอยู่จริง**
(`git ls-remote --heads origin` คืน `refs/heads/deploy/production`)

ขั้น deploy สั่ง `git checkout <tag>` ใน `/opt/gacp-platform` (`:221-225`) แล้ว recreate `gacp-nginx` (`:258`)
⇒ **ถ้ามันยิง staging ที่ใช้งานอยู่โดนทับ**

### R2 — คู่มือ rollback สั่งให้ล้างฐานผิดตัว และมันจะสำเร็จ **[ตรวจเอง]**

`docs/operations/runbooks/deploy-staging-manual.md` หัวข้อ "4. Rollback" ข้อ 2 สอนว่า:

> `sudo bash scripts/backup/pg-backup.sh --restore <the pre-deploy dump>` (⚠️ this replaces gacp_staging data)

แต่ `scripts/backup/pg-backup.sh:33` ตั้ง `DB_NAME="${DB_NAME:-gacp_db}"` และโหมด restore (`:68`) สั่ง
`gunzip -c "$RESTORE_FILE" | docker exec -i gacp-postgres psql -U gacp -d "$DB_NAME" --single-transaction`

⇒ **รันตามคู่มือเป๊ะ ๆ โดยไม่ตั้ง `DB_NAME` เอง จะเขียนลง `gacp_db` ไม่ใช่ `gacp_staging`**
สคริปต์ถึงกับพิมพ์เตือนว่า `This will REPLACE all data in ${DB_NAME}` ซึ่งจะขึ้นคำว่า `gacp_db`
สวนทางกับคำเตือนในคู่มือเอง

**และนี่คือส่วนที่อันตรายที่สุด:** ดัมป์ก่อน deploy ที่คู่มืออ้างถึงถูกสร้างโดย
`scripts/deploy/deploy-staging.sh:93-94` ด้วย `pg_dump --clean --if-exists … | gzip`
⇒ เป็น plain SQL บีบอัด **ซึ่งเข้ากันได้กับ `gunzip | psql` พอดี** คำสั่งจะ**ไม่ error**
มันจะทำงานสำเร็จ และเพราะดัมป์มี `--clean --if-exists` มันจะ **DROP object ของ `gacp_db`
แล้วเขียนทับด้วยข้อมูลของ staging** ภายใน transaction เดียว

รูปแบบที่เข้ากันได้คือสิ่งที่ทำให้มันอันตราย ไม่ใช่สิ่งที่ทำให้ปลอดภัย

*(หมายเหตุแยก: ไฟล์ `-Fc` ที่ cron 03:17 ผลิตลง `/opt/gacp-platform/backups/` **อ่านด้วยสคริปต์นี้ไม่ได้** —
ใครหยิบไฟล์นั้นมาใช้กับคำสั่งนี้จะเจอ error ซึ่งในกรณีนั้นถือว่าโชคดี)*

นี่คือคำสั่งที่คนจะพิมพ์ตอนตกใจ

### R3 — ไฟล์ที่ผู้ใช้อัปโหลดไม่ถูกสำรองเลย **[ตรวจเอง]**

`backup-and-restore.md:117-119` บันทึกไว้เอง — volume `gacp-uploads-data`,
`gacp-platform_gacp_staging_uploads`, `gacp-minio-data` ไม่มีการสำรอง
⇒ กู้ฐานข้อมูลได้ แต่**ทุกลิงก์เอกสารชี้ไปไฟล์ที่ไม่มีอยู่** — backup ครึ่งใบ

### R4 — สำเนาทั้งหมดอยู่บนดิสก์ก้อนเดียวกับต้นฉบับ **[ตรวจเอง]**

### R5 — ดัมป์ไม่เข้ารหัส และมี PII เป็น plaintext **[กวาด+หักล้าง]**

- สิทธิ์ไฟล์ `644` · `gacp-backup.sh` ไม่มี `umask`/`chmod` **[เครื่องจริง + ตรวจเอง]**
- `apps/backend/services/prisma-pdpa-extension.js:166-171` — `firstName`, `lastName`,
  `phoneNumber`, `province` **ไม่ได้เข้ารหัสระดับคอลัมน์** และ `email` ไม่อยู่ในชุดเข้ารหัส
  ⇒ ดัมป์มีชื่อ-นามสกุล-เบอร์-อีเมล เป็นข้อความธรรมดา
- ส่วนที่เข้ารหัสไขได้ด้วย `ENCRYPTION_KEY` ที่อยู่ใน `.env.production` **บนดิสก์ก้อนเดียวกัน**
- `scripts/backup/backup-system.sh:90` สำรอง `apps/backend/.env.production` ลง tar ด้วย
  ⇒ มี backup ที่บรรจุ secret อยู่ข้างใน

**ข้อจำกัดที่ต้องรู้ก่อนแก้:** `docs/audit-reports/2026-07-25-data-sovereignty-audit.md:5-9`
บันทึกข้อกำหนดยืนพื้นว่า **PII คนไทยต้องไม่ออกนอกประเทศไทย** และ addendum `:541-580` ยัง **OPEN**
เพราะเครื่องอยู่สิงคโปร์ ⇒ ปลายทางของสำเนานอกเครื่อง **ต้องเลือกโดยคำนึงข้อนี้**
(เครื่องของ operator ในไทย ดีกว่าคลาวด์ต่างประเทศในแง่นี้)

และ `docs/operations/runbooks/secret-rotation.md:35` — สำเนา backup ที่ออกนอกเครื่องโดยไม่ได้วางแผน
**บังคับให้ต้อง rotate secret ทั้งชุด** ⇒ ต้องทำอย่างตั้งใจและบันทึก

## 6. ทำไม "staging เท่านั้น" ยังไม่จริง และกับดักที่ต้องรู้ก่อนแตะ

**กับดักที่ 1 — `docker-compose.production.yml` ไม่ใช่ stack ของ production แต่เป็นไฟล์ฐานของทั้งสอง**
มันประกาศ network `gacp-network` (`:545-548`), volume ทุกก้อน (`:553-576`), และ container กลาง
`gacp-postgres` (`:296`) `gacp-redis` (`:377`) `gacp-nginx` (`:33`) `gacp-minio` (`:233`) พร้อม monitoring ทั้งชุด ·
`docker-compose.staging.yml` เข้าร่วม `gacp-network` โดยไม่ได้ประกาศเอง — ทำงานได้เพราะ
`deploy-staging.sh` ส่งทั้งสองไฟล์เสมอ (`:111`, `:136`) ⇒ **ลบหรือเปลี่ยนชื่อไฟล์ production ไม่ได้
จนกว่าจะย้ายของกลางออกก่อน**

**กับดักที่ 2 — nginx ของ staging พึ่ง config ของ production**
`deploy/nginx/staging.gacpth.com.conf:44,85` ใช้ `$gacp_prelaunch_deny` ที่นิยามใน
`deploy/nginx/gacp-platform.conf:107` ⇒ **ลบ config production แล้ว nginx ไม่สตาร์ตเลย**

**กับดักที่ 3 — ลำดับการปลด `gacp_db`**
`scripts/ops/gacp-backup.sh:20,30` ใช้ `set -euo pipefail` แล้ววน `for DB in gacp_db gacp_staging`
โดย **`gacp_db` มาก่อน** ⇒ ถ้าฐานนั้นหาย `pg_dump` exit non-zero, `set -e` ตัดลูป และ
**`gacp_staging` จะไม่ถูกสำรองอีกเลยโดยไม่มีใครรู้** (ไม่มีการแจ้งเตือน — `backup-and-restore.md:115-116`)
⇒ **แก้สคริปต์ก่อน ปลดฐานทีหลัง เสมอ**

**กับดักที่ 4 — มี CI check อย่างน้อย 4 ตัวที่บังคับให้ production ต้องมีอยู่**
`check-production-topology.js:56-59` (เป็น gate ของ push-to-main ผ่าน `topology-guard.yml`) ·
`check-infra-contracts.js:166-171` (hard-assert `environment==='production' && provider==='digitalocean'`) ·
`production-readiness-check.js:256` (require `docker-compose.production.yml`) ·
`nginx-exposure.test.js:36-37` (hardcode path ทั้งสอง)

**มีของช่วยอยู่แล้ว:** `scripts/ops/bootstrap-staging-runner.sh` — หัวไฟล์ระบุว่าหน้าที่ข้อ (1)
คือเคลียร์ stack production **[กวาด+หักล้าง]** อ่านก่อนเขียนอะไรใหม่

```bash
docker exec gacp-postgres psql -U gacp -d gacp_db -c "select 'applications' AS t, count(*) AS n, max(created_at) AS newest from applications union all select 'invoices', count(*), max(created_at) from invoices union all select 'users', count(*), max(created_at) from users;"

```
