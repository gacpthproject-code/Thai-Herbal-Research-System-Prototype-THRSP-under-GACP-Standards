## ครึ่งแรก — "ไม่รู้จ่ายบิลไหนตอนไหน" → แก้แล้ว

## ครึ่งหลัง — "ปุ่มขึ้นตลอด จ่ายซ้ำได้" → **ยังไม่แก้ ต้องให้ operator ตัดสิน**

ตรวจด้วย 5 มุมมองขนาน เจอ 41 ข้อ · CRITICAL 7 · ข้างล่างคือข้อที่ผมยืนยันด้วยตัวเองแล้ว

### C6 + C2 — จ่ายเงินออนไลน์ให้เสร็จไม่ได้เลย (ยืนยันแล้ว)

`apps/web-app/package.json` **ไม่มี dependency ของ Stripe แม้แต่ตัวเดียว** และ `clientSecret`
ที่ backend คืนมา ปรากฏแค่ในนิยาม type กับ fixture กับเทส — ไม่มี component ไหนใช้เลย

จอสุดท้ายของ `/health/payments/checkout` เขียนว่า
"คุณยังไม่ถูกเรียกเก็บเงินจนกว่าจะทำขั้นตอนชำระเงินถัดไปเสร็จ" แล้วมีปุ่มเดียว: กลับไปหน้ารายการ
**ไม่มีขั้นตอนถัดไปอยู่จริง**

นี่คือคำอธิบายทั้งหมดของ "ปุ่มขึ้นตลอด": กดปุ่ม → ระบบ mint invoice `pending` →
กลับมาหน้ารายการ → หนี้ที่เพิ่งถูกสร้างทำให้ปุ่มขึ้นอีก → กดได้ไม่จำกัด ·
ไม่มีใครทำให้ปุ่มหายได้ เพราะไม่มีใครจ่ายจนจบได้

### C3 — จ่ายซ้ำที่ order เดียวกัน ระบบตอบ Stripe ว่า 200 แล้วเงียบ (ยืนยันแล้ว)

`checkout-settlement-service.js:247` — หา order จาก `paymentIntent.metadata.checkoutOrderId`
แล้วถ้า order เป็น SETTLED อยู่แล้ว คืน `{settled:true, alreadySettled:true}` ทันที
**โดยไม่เทียบ `paymentIntent.id` กับ `order.stripePaymentIntentId` เลย**

⇒ เงินก้อนที่สองที่เข้ามาจริง แยกไม่ออกจาก webhook ส่งซ้ำ · ไม่มีใบเสร็จใบที่สอง
ไม่มีการแจ้งเตือน ไม่มีคิวคืนเงิน ไม่มีแถวไหนในระบบรู้ว่ามีเงินก้อนที่สอง

### C4 — idempotency key หมดอายุแล้วได้ QR ใบใหม่ ใบเก่ายังจ่ายได้

`stripe-checkout-service.js:722` ใช้ `checkout:{orderId}` เป็นคีย์คงที่ตลอดอายุ order
แต่ Stripe เก็บผลคีย์ไว้ 24 ชม. · พ้นจากนั้นได้ PaymentIntent ใบใหม่ และโค้ดที่บรรทัด 725
**ทับ pointer เฉย ๆ** ไม่ยกเลิกใบเก่า (adapter ไม่มีเมธอด cancel ให้เรียกด้วยซ้ำ)
⇒ สองใบเรียกเก็บได้จริงพร้อมกัน แล้วไปบรรจบกับ C3

*หมายเหตุ: กฎ 24 ชม. เป็นพฤติกรรมฝั่ง Stripe ยังไม่ได้ยิงจริงยืนยันในเซสชันนี้*

### C7 — คำขอที่ EXPIRED ไปแล้ว ฟื้นกลับมาเองถ้ามีเงินเข้าทีหลัง (ยืนยันแล้ว)

`checkout-settlement-service.js:418` เรียก `writeApplicationStatus` โดย**ไม่ส่ง
`assertTransition`** ซึ่ง default เป็น `false` (`application-status-writer.js:701`)
⇒ `assertTransitionAllowed` ไม่เคยทำงาน · คำขอที่ระบบปิดไปแล้วเพราะไม่จ่ายตามกำหนด
ถ้าเปิดลิงก์เดิมแล้วจ่าย จะเด้งกลับเป็น DOC_FEE_PAID/AUDIT_FEE_PAID พร้อมออกใบเสร็จ
โดยไม่ผ่านกระบวนการ waiver-reopen

### C5 — ผู้ยื่นหลายคำขอ อาจจ่ายผิดคำขอ (ยืนยันแล้ว)

เข้าหน้านี้จากเมนู (ไม่มี `?app=`):
- `pendingAmount` รวมหนี้ของ**ทุกคำขอ** (`client-view.tsx:308`)
- `activeApplicationId` = คำขอของ **invoice แถวแรก** ไม่ว่าคำขอนั้นจะค้างจ่ายหรือไม่
  (`payments-application-id.ts:33`)
- การจัดกลุ่มใช้ "งวด" อย่างเดียว ใบของทุกคำขอกองรวมในกล่อง "งวดที่ 1" กล่องเดียว
- การ์ดไม่พิมพ์เลขที่คำขอ · ตัวระบุเดียวบนจอคือ UUID ในแบนเนอร์

⇒ ปุ่มขึ้นเพราะคำขอ B เป็นหนี้ แต่ชี้ไปคำขอ A ได้ และไม่มีจุดไหนให้ทันสังเกต

## ที่ต้องตัดสิน

ทุกข้อข้างบนอยู่ในเส้นทางเงิน = **L3 (agent ห้ามแก้เอง)** และเป็น Tier C = operator merge
ผมเสนอลำดับนี้:

1. **C6/C2 ก่อนเพื่อน** — ตัดสินว่าจะต่อ Stripe PaymentElement บนเว็บ หรือให้ backend คืน
   hosted checkout url แล้ว redirect · **ระหว่างที่ยังไม่มี** ปุ่ม "ชำระเงินออนไลน์" ไม่ควรอยู่
   บนจอ หรืออย่างน้อยต้องไม่ mint invoice ตั้งแต่กดปุ่ม (นั่นคือสิ่งที่ทำให้ปุ่มขึ้นซ้ำ)
2. **C3 + C7** — สองข้อนี้เป็น diff เล็กและตรงไปตรงมา (เทียบ PI id ก่อนตอบ alreadySettled ·
   ส่ง `assertTransition: true`) ผมเขียนให้ได้ทันทีที่สั่ง
3. **C4** — ต้องเพิ่ม `cancelPaymentIntent` เข้า adapter ก่อน แล้วห้ามทับ pointer
4. **C5** — จัดกลุ่มสองชั้น คำขอ → งวด และพิมพ์เลขที่คำขอจริง (ต้องเพิ่ม `applicationNumber`
   เข้า payload ของ `listByApplicant` ก่อน)
