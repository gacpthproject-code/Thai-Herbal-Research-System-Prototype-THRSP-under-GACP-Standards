## 1. สรุปสำหรับ operator

1. **SKU ในระบบนี้คือ "ชื่อของสิ่งที่ขาย" ไม่ใช่ "เลขที่ใบเสร็จ"** — มันคือรหัสสั้น ๆ ที่พิมพ์คู่กับรายการบนเอกสาร เพื่อให้คนที่ถือใบเสร็จกับคนที่กระทบยอดกับกรมฯ พูดถึงของชิ้นเดียวกันโดยไม่ต้องเปิดตาราง
2. **สเก็ตช์ของคุณถูก แต่ยังไม่พอ** — "ยื่นใหม่งวด 1 / ยื่นใหม่งวด 2 / ต่อสัญญา" คือ *เหตุการณ์เรียกเก็บ* จริง 3 เหตุการณ์ที่โค้ดเก็บเงินอยู่จริง และถูกเก็บไว้ทั้งดุ้นเป็นคอลัมน์ `billingEvent` สามค่า แต่หนึ่งเหตุการณ์มีสองราคาประกอบกัน (ราคาเต็ม + ค่าแพลตฟอร์ม 10%) และคิดเงิน **ต่อรูปแบบการปลูก** ดังนั้น "ต่อสัญญา" ไม่มีราคาเดียว — มันคือ 35,310 หรือ 70,620 หรือ 105,930 แล้วแต่จำนวนรูปแบบ
3. **สิ่งที่เปลี่ยนสำหรับคุณ 3 อย่าง** — (ก) เอกสารจะมีคอลัมน์ "รหัส" เพิ่มมา (ข) เอกสารจะพิมพ์ "จำนวน 2 × 30,000 = 60,000" แทน "จำนวน 1 × 60,000" ซึ่งวันนี้พิมพ์ผิดอยู่ (`invoice-template-service.js:352-358` ตอกเลข 1 ไว้ตายตัวที่ `:353` และ `:355`) (ค) ราคาจะย้ายจาก "ค่าคงที่ในโค้ดที่แก้แล้วมีผลย้อนหลังกับใบที่ออกไปแล้ว" ไปเป็น "แถวราคาที่มีวันมีผล และถูกปักหมุดไว้บนใบที่ออกไปแล้ว"
4. **สิ่งที่ไม่เปลี่ยน คือยอดเงิน** — ทุกช่องในสเปกนี้กระทบยอดกับเครื่องคิดค่าธรรมเนียมตัวเดิมเป๊ะ **ที่ความละเอียดบาท ซึ่งเป็นความละเอียดที่เครื่องตัวนั้นทำงานอยู่จริง** (`fee-service.js:144` และ `:146` ใช้ `Math.round` ปัดเป็นบาทเต็ม) ฉบับก่อนเขียนว่า "เป๊ะทุกสตางค์" ซึ่ง **เกินจริง** — ที่อัตราวันนี้ไม่มีเศษสตางค์เลยก็จริง แต่คำกล่าวนั้นจะพังทันทีที่อัตราเปลี่ยนเป็นเลขที่หารไม่ลง (แก้แล้วที่ R2/R4/R7/R8)
5. **สิ่งที่สเปกนี้ยังไม่แก้ให้** — บั๊กคิดเงิน 2 ตัวที่ยังอยู่ (**B1** ต่ออายุที่จ่ายผ่านราง Stripe ถูกคิดเป็นงวด 2 ขาดไป 5,885/ขอบเขต · **B2** จำนวนขอบเขตบนเอกสารกับบนบิลมาจาก **คนละแหล่ง** และไม่มีอะไรบังคับให้ตรงกัน) — **ต้องแก้สองตัวนี้ก่อน** ไม่งั้นแถวราคาเวอร์ชันแรกจะบันทึกตัวเลขที่ผิดไว้เป็นทางการ (§4 P0) · จาก §0.3: **ยังไม่มีแถวจริงแถวใดถูกกัด** (ต่ออายุ 2 คำขอ 0 invoice 0 order) จึงไม่ต้องคืนเงินย้อนหลัง

### 2.3 รูปแบบรหัส (ทำไมไม่ใช่ SKU001/002/003)

รูปแบบผูกพัน: `<โดเมน>-<เหตุการณ์>-<องค์ประกอบ>` · `^[A-Z][A-Z0-9]{1,7}(-[A-Z0-9]{1,12}){1,3}$` · **ยาวรวมไม่เกิน 24 ตัวอักษร (บังคับเป็น assertion แยก ไม่ใช่ด้วย regex)** · ไม่มีเลขลำดับ ไม่มีปี ไม่มีคำที่บอกวิธีปฏิบัติทางภาษี

> **แก้จากฉบับก่อน — blocker**: regex เดิม `(-[A-Z0-9]{1,9}){1,3}` **ปฏิเสธรหัสของตัวเอง 4 ตัว** (`SUBS-ENTERPRISE-M`, `SUBS-ENTERPRISE-Y`, `ADJ-DN-ADDITIONAL`, `ADJ-DN-CORRECTION`) เพราะ `ENTERPRISE` และ `ADDITIONAL` ยาว 10 ตัว เกินเพดาน 9 → boot assertion ของ P1 ("ทุกคีย์ผ่าน regex §2.3") จะโยน **ตั้งแต่เซิร์ฟเวอร์สตาร์ตครั้งแรก** รันจริงใน session นี้ได้ `total 14 fail 4` · เพดานท่อนถูกขยายเป็น 12 แล้วรันซ้ำได้ `re2 fail 0 maxlen 17` · เพดานความยาวรวม 24 ตัวอักษรย้ายออกมาเป็น assertion แยก เพราะ regex เพียว ๆ อนุญาตได้ถึง 47 ตัว จึงไม่เคยบังคับความยาวรวมได้อยู่แล้ว

1. **คำถามของ operator เองจบด้วย "อันนี้ผมแค่เดา"** — นั่นคือหลักฐานเชิงประจักษ์ว่ารหัสทึบต้องมีตารางเปิด ซึ่งคนที่ถือใบเสร็จอยู่ไม่มี · `GACP-NEW-P2-STATE` บนใบงวดที่ 1 ผิดตั้งแต่มองครั้งแรก `SKU002` ไม่ผิดให้เห็น
2. **รหัสที่ใช้อยู่จริงวันนี้ก็พูดได้อยู่แล้ว** — `DTAM_FEE` / `PLATFORM_FEE` / `PLATFORM_VAT` (`stripe-checkout-service.js:190, 201, 212` — ฉบับก่อนอ้าง 189/199/209 ซึ่งเป็นบรรทัด `lineNumber` กับ `organizationId`) และ `PHASE_2_STATE` ที่ต่อสตริงขึ้นมา (`services/application-service/application-phase-invoice-methods.js:109`) การเปลี่ยนเป็นตัวเลขคือถอยหลัง
3. **ม.86/4(4) ต้องการเลขที่เอกสารเรียงลำดับจริง ซึ่งมีตัวจ่ายของตัวเองอยู่แล้ว** (`prisma/schema/billing.prisma:658-682` · `services/receipt-numbering-service.js:70-75`) รหัสตัวเลขเชิญให้สับสนระหว่าง "SKU003" กับ "ใบที่ 003" ตัวอักษรตัดปัญหานั้นด้วยรูปร่าง — **กฎเหล็ก: ห้ามอนุมานเลขที่เอกสารจาก SKU และห้ามอนุมาน SKU จากเลขที่เอกสาร ตลอดไป**
4. **รหัสเรียงเลขต้องมีทะเบียนกลางคอยจ่ายเลขถัดไป** และพังวันที่เลิกใช้รหัสหนึ่งแล้วมีคนหยิบเลขที่เหลือรูกลับมาใช้กับของคนละอย่าง รหัสที่พูดได้เพิ่มได้โดยไม่ต้องประสานกับใคร
5. **เข้ากับ pattern ของ repo** — ทั้ง schema ไม่มี Prisma enum แม้แต่ตัวเดียว (ตรวจด้วย grep นับ `enum` ต้นบรรทัดในทุกไฟล์ `.prisma` — ไม่มีไฟล์ไหนได้ค่าบวก) บ้านนี้ใช้ String + CHECK + โมดูลคำศัพท์ที่ freeze + boot assertion (เหตุผลบันทึกที่ `shared/checkout-status.js`)

**สเก็ตช์ของ operator ไม่ถูกทิ้ง** — SKU001/002/003 ถูกเก็บไว้ทั้งดุ้นเป็นคอลัมน์ `billingEvent` สามค่า `GACP_NEW_P1` / `GACP_NEW_P2` / `GACP_RENEWAL` ที่ §2.2

| R6 | `ยอดชำระ = Σ จำนวนเงินของบรรทัด **ที่มี \`skuCode\`** + VAT` (บวกเฉย ๆ) · บรรทัดที่ `skuCode` เป็น NULL — วันนี้คือบรรทัด `PLATFORM_VAT` ที่ยังถูกเขียนอยู่ 14 แถว (§0.3) — **ไม่เข้าสมการ** · ความเป็นภาษีของบรรทัดอ่านจาก **แคตตาล็อก `shared/sku-catalogue.js`** ไม่ใช่จากคอลัมน์ `InvoiceLineItem.isTaxable` ซึ่ง §0.3 แสดงว่ายังถือสูตรเก่าทุกแถว (`DTAM_FEE` เป็น `false` ทั้ง 14 แถว) |
| R7 | **ความต่างจากเครื่องคิดวันนี้ ประกาศไว้ตรงนี้ ไม่ซ่อน — เหลือข้อเดียว**: `fee-service.js:143-144` *คูณจำนวนก่อน แล้วค่อยปัด* (`Math.round(stateAmount_รวม × 0.10)`) สเปกนี้ *ปัดต่อหน่วยก่อน แล้วค่อยคูณ* ที่อัตราปัจจุบันให้ผลเท่ากันทุกช่อง เพราะทุกอัตราหารด้วย 10 ลงตัว (ยืนยันที่ scope 1/2/3 ใน §0.2) · **ความต่างเรื่องความละเอียดหายไปแล้ว** หลัง R2/R4 เปลี่ยนเป็นบาทเต็ม |
| R8 | **boot guard — เงื่อนไขเชิงพีชคณิต ไม่ใช่ลูปที่มีขอบ**: ปฏิเสธการโหลดอัตราใด ๆ ที่ `rate × PLATFORM_RATE` ไม่ลงตัวเป็นบาทเต็ม **หรือ** `(rate + rate × PLATFORM_RATE) × VAT_RATE` ไม่ลงตัวเป็นบาทเต็ม · คำนวณด้วยจำนวนเต็มสตางค์ ห้ามเทียบ float ตรง ๆ · เมื่อเงื่อนไขนี้ผ่าน การคูณด้วย `n` ใด ๆ ก็ยังลงตัว จึง **ไม่ต้องมีขอบบนของ n** |
| R9 | **ตรวจแล้วว่ากติกานี้จับของจริง** (รันใน session นี้): อัตรา 5,000 / 25,000 / 30,000 **ผ่านทั้งสามตัว** · อัตราสมมติ 5,010 / 25,010 / 30,010 **ตกทั้งสามตัว** เพราะ VAT ออกมา 385.77 / 1,925.77 / 2,310.77 ขณะที่เครื่องจะปัดเป็น 386 / 1,926 / 2,311 — ส่วนต่าง 0.23 บาทต่อใบ ที่ฉบับก่อนมองไม่เห็นเพราะ guard เดิมทดสอบแต่ลำดับการปัดของ *ค่าแพลตฟอร์ม* และไม่ทดสอบ VAT เลย |
| R10 | **ฐานทางกฎหมาย: หาไม่เจอ** — ไม่พบกฎการปัดเศษตามกฎหมายไทยใน ม.86/4, ป.86/2542 หรือประกาศอธิบดีฯ ฉบับที่ 39 กฎที่บล็อกพาณิชย์อ้างกันทั่วไปไม่มีการอ้างมาตรา/ประกาศใด ๆ **R1-R9 จึงเป็นกฎของระบบนี้เอง ห้ามพิมพ์หรืออ้างว่าเป็นข้อกำหนดตามกฎหมาย** (ดู §6.3) |

> **แก้จากฉบับก่อน**: R1-R4 เดิมสั่งปัดที่ **สองตำแหน่ง (สตางค์)** ขณะที่เครื่องคิดค่าธรรมเนียมปัดเป็น **บาทเต็ม** (`fee-service.js:144`, `:146` ใช้ `Math.round`) · R7 เดิมประกาศเฉพาะความต่างเรื่อง *ลำดับ* การปัด และไม่พูดถึงความต่างเรื่อง *ความละเอียด* เลย · ผลคือคำกล่าว "กระทบยอดเป๊ะทุกสตางค์" ที่ §1 เป็นจริงเฉพาะกับสามอัตราที่ตั้งไว้วันนี้ ซึ่งบังเอิญหารลงตัว **การตัดสินคือ: สเปกเดินตามเครื่อง — ปัดเป็นบาทเต็ม** ถ้า operator ต้องการความละเอียดระดับสตางค์จริง นั่นคือการแก้เครื่องคิดค่าธรรมเนียม = money path = L3 = คนละใบ (ตั้งเป็น Q10)

## 3. SKU ขึ้นเอกสารอย่างไร

### กฎร่วมทั้งสามใบ

- **หนึ่ง SKU = หนึ่งบรรทัด** เหตุการณ์หนึ่งจึงพิมพ์สองบรรทัด (`-STATE` แล้วตามด้วย `-PLAT`) เสมอ ห้ามสลับลำดับ
- **คอลัมน์ "รหัส" เป็นคอลัมน์ของตัวเอง** ไม่ใช่วงเล็บใต้คำบรรยาย — เพราะคนกระทบยอดต้องกวาดตาลงคอลัมน์เดียว
- **รหัสไม่แทนคำบรรยาย** — ม.86/4(5) บังคับ "ชื่อ ชนิด ประเภท ปริมาณ และมูลค่า" และ ป.86/2542 ไม่มีข้อใดอนุญาตให้รหัสยืนแทน ทางออกเดียวที่ ป.86/2542 ข้อ 9(1) ให้เมื่อรายการไม่พอคือแนบใบต่อ ไม่ใช่ใส่รหัส
- **`จำนวน` ต้องเป็นตัวเลข `scopeCount` ตัวเดียวกับที่คำนวณค่าธรรมเนียม** ห้ามคำนวณซ้ำที่ renderer · วิธีบังคับให้เป็นจริง: **`quantity` ถูก *เขียนลงแถว* ตอนออกบิล (P4) แล้ว renderer *อ่าน* จากแถวนั้น (P6)** ไม่ใช่ให้ renderer หาเอง — วันนี้ renderer หามาจาก `application.totalAreaTypes` ด้วยการหาร (`invoice-template-service.js:341-344`) ขณะที่รางเก็บเงินนับจากเซ็ต `cultivationMethods` และรางออกใบตามงวดใช้ค่าที่แช่ไว้จากใบเสนอราคา — **สามที่มา ไม่มีอะไรทำให้ตรงกัน** (ดู §4 P0 บั๊ก B2) *(กฎนี้ต่อมาจาก design-event · กลไกบังคับเพิ่มเข้ามาตอนแก้ตามผลตรวจสอบ เพราะกฎเดิมไม่มีคอลัมน์ไหนรองรับเลย)*
- **VAT ไม่มีบรรทัดในตารางรายการ** อยู่ในช่องสรุปเท่านั้น ตาม ม.86/4(6) ที่ต้อง "แยกออกจากมูลค่าของสินค้าและหรือของบริการให้ชัดแจ้ง"
- **ท้ายเอกสารพิมพ์ที่มาของราคา**: `แคตตาล็อกราคา: PRICEBOOK-2026-001 (มีผล 2026-08-23)` — ทำให้กระดาษตอบคำถาม "ราคานี้มาจากไหน" ได้เองในอีกห้าปี โดยไม่ต้องเปิดฐานข้อมูล *(ต่อมาจาก design-catalogue)*

### 3.1 ใบเสนอราคา (`services/pdf/templates/quotation.html`)

หัวตารางวันนี้ 6 คอลัมน์ `ลำดับที่ | รายการ | จำนวน | หน่วย | ราคา/หน่วย | จำนวนเงิน (บาท)` (`quotation.html:108-115`) → **แทรก `รหัส` ต่อจาก `ลำดับที่` เป็น 7 คอลัมน์**

ใบเสนอราคาคำขอใหม่แสดง **4 บรรทัด** (สองงวด × สององค์ประกอบ) พร้อมหัวข้อคั่นงวด · ใบเสนอราคาต่ออายุแสดง **2 บรรทัด** ครั้งเดียว

ตัวอย่าง ต่ออายุ 3 รูปแบบ:

```
1 | GACP-RNW-STATE | ค่าบริการต่ออายุใบรับรอง — ราคาเต็ม   | 3 | รูปแบบการปลูก | 30,000.00 | 90,000.00
2 | GACP-RNW-PLAT  | ค่าบริการแพลตฟอร์ม 10% (ต่ออายุ)      | 3 | รูปแบบการปลูก |  3,000.00 |  9,000.00
                                                    ค่าบริการ    99,000.00
                                        ภาษีมูลค่าเพิ่ม 7%      6,930.00
                                            จำนวนเงินทั้งสิ้น  105,930.00
```

ต้องแก้เพิ่มบนใบนี้ 3 อย่าง:

1. วันนี้พิมพ์ **หนึ่งบรรทัดต่อรูปแบบการปลูก** โดยตอก `จำนวน = 1` และ `หน่วย = คำขอ` (`invoice-template-service.js:1026-1035`) → เปลี่ยนเป็นหนึ่งบรรทัดต่อ SKU จำนวน = scopeCount
2. **ใบเสนอราคาวันนี้ไม่มีบรรทัด VAT เลย** — นับจำนวน `TOTALS_ROWS_HTML` ใน `quotation.html` ได้ **0** บล็อกสรุปแบบผู้ออกรายเดียวมีอยู่ในโค้ด (`invoice-template-service.js:190-227`) แต่ไม่ถูกเรียกจาก PDF ใดเลย ต้องต่อสายให้ถึง
3. renderer ยังบังคับ `issuerSide` เป็น DTAM หรือ PLATFORM (`invoice-template-service.js:977-990`) และเก็บบล็อกตัวตนกรมฯ ไว้เต็ม — ชื่อกอง ที่อยู่ ผู้ลงนาม บัญชีธนาคาร เลขประจำตัวผู้เสียภาษี (`invoice-template-service.js:932-946`, ค่าคงที่ `DTAM_QUOTATION_META`) ทั้งที่ผู้ออกเหลือรายเดียว — ต้องปิดสาขา DTAM · **ครุฑไม่ได้อยู่ในสองช่วงนั้น** อย่างที่ฉบับก่อนเขียน มันถูกฉีดที่ `invoice-template-service.js:1057` (`GARUDA_DATA_URL: getLogoDataUrl()`) และวาดโดย `services/pdf/templates/quotation.html:77`

### 3.2 ใบวางบิล / ใบแจ้งหนี้ (`services/pdf/templates/invoice.html`)

หัวตารางวันนี้ 5 คอลัมน์ `# | รายการ / Description | จำนวน Qty | ราคา/หน่วย Unit Price | มูลค่า Total` (`invoice.html:496-500`) → **แทรก `รหัส` เป็น 6 คอลัมน์**

ใบวางบิลออก **ต่อหนึ่งงวด** จึงมี 2 บรรทัดเสมอ ตัวอย่าง งวดที่ 2 · 2 รูปแบบ:

```
1 | GACP-NEW-P2-STATE | ค่าบริการตรวจประเมินพื้นที่ คำขอใหม่ — ราคาเต็ม | 2 | 25,000.00 | 50,000.00
2 | GACP-NEW-P2-PLAT  | ค่าบริการแพลตฟอร์ม 10% (ตรวจประเมิน)         | 2 |  2,500.00 |  5,000.00
                                                ค่าบริการ / Service fee   55,000.00
                                             ภาษีมูลค่าเพิ่ม 7% / VAT      3,850.00
                                               ยอดที่ต้องชำระทั้งสิ้น     58,850.00
```

ที่ต้องแก้:

1. วันนี้ `buildItemsRows` คืน **หนึ่งบรรทัดเสมอ** ตอก `1` ในช่องจำนวน และพิมพ์ `amts.subtotal` ทั้งช่องราคา/หน่วยและช่องมูลค่า (`invoice-template-service.js:352-359`) — 3 ขอบเขตจึงพิมพ์ "จำนวน 1 × 82,500" แทน "จำนวน 3 × 27,500" นี่คือช่อง "ปริมาณ" ตาม ม.86/4(5) ที่หายไป
2. วันนี้บรรทัดไม่ได้อ่านจาก `InvoiceLineItem` เลย แม้ราง checkout จะเขียนไว้ 3 แถว (`stripe-checkout-service.js:184-220`) — **บรรทัดต้องมาจาก line item ที่ถูกปักหมุด SKU แล้ว**
3. คำบรรยายวันนี้มาจาก map ตาม `serviceType` (`invoice-template-service.js:261-277`) และราง checkout เขียน `serviceType = CERTIFICATION_CHECKOUT_M1|M2` (`stripe-checkout-service.js:171`) ซึ่ง **ไม่มีในแมป** จึงตกลง fallback `ค่าธรรมเนียม GACP` ที่ `:276` — เกษตรกรไม่เคยเห็นคำว่า "งวดที่ 1" หรือ "ต่ออายุ" บนใบวางบิลจริงเลย → **คำบรรยายต้องคีย์ด้วย `skuCode` ไม่ใช่ `serviceType`**
4. คำบรรยายที่เก็บอยู่ในฐานข้อมูลวันนี้เป็นเท็จตามคำวินิจฉัยใหม่ (`stripe-checkout-service.js:191` และ `:213`) ต้องถูกแทนที่พร้อมกับการเปลี่ยนผู้เขียน

### 3.3 ใบเสร็จรับเงิน (`services/pdf/templates/receipt.html`)

คอลัมน์และเนื้อบรรทัดเหมือนใบวางบิลทุกประการ ใช้ `buildItemsRows` ตัวเดียวกัน เรียกที่ `invoice-template-service.js:689` ต่างกันแค่ป้ายช่องสรุปเป็น `ยอดที่รับชำระทั้งสิ้น` — **แก้ `buildItemsRows` ครั้งเดียว ได้ทั้งใบวางบิลและใบเสร็จ**

**คำเตือนที่ต้องแก้ก่อน SKU ขึ้นใบเสร็จ**: `generateReceiptPdf` สลับไปใช้ `government-revenue-receipt.html` และพิมพ์ `VAT_TEXT = 'ยกเว้น / Exempt'` เพียงเพราะ `serviceType.includes('STATE_FEE')` (`invoice-template-service.js:638, 691, 721`) ขณะที่รางออกใบตามงวดยังมินต์ใบ STATE อยู่ (`application-phase-invoice-methods.js:436-459`) → เกษตรกรจึงอาจถือใบเสร็จที่อ้างยกเว้น VAT สำหรับเงินที่ถูกคิด VAT ไปแล้ว **สเปกนี้ไม่แก้ให้ ต้องแก้แยกใบ และควรแก้ก่อน** (ข้อค้นพบนี้มาจาก design-catalogue ตามที่กรรมการ operability ชี้)

## 4. แผนงาน expand-before-contract

แต่ละเฟสส่งขึ้น main ได้เดี่ยว ๆ · tier ตัดสินโดย `scripts/probes/tier-check.sh` เท่านั้น ห้ามประเมินเอง · **diff ทุกอันข้างล่างเป็นภาพร่าง ยังไม่ถูก apply (L3)**

> **ตัดเฟสใหม่ตามผลตรวจสอบ** — ลำดับเดิมมีสองที่ที่ **ไม่ใช่ expand-before-contract จริง**:
> - **P7 พึ่งการตัดของเก่าทิ้ง** probe กระทบยอดของมันจะผ่านได้ก็ต่อเมื่อบรรทัด `PLATFORM_VAT` ถูกเลิกออก ซึ่งคือ C3 ในเฟส contract ที่อยู่ *หลัง* มัน · แก้โดยให้สมการ (R6/P7) นับเฉพาะบรรทัดที่มี `skuCode` — ของเก่ายังอยู่ครบ ไม่ต้องตัดอะไรก่อน **นั่นคือ expand จริง**
> - **P4 กับ P6 ถูกยุบเป็นก้อนเดียวทั้งที่แตะสองรางและสองพฤติกรรม** · แยกเป็น P4a/P4b (ราง checkout / ราง phase) และ P6a/P6b (อ่านบรรทัดจริง / หัวคอลัมน์กับคำบรรยาย) เพื่อให้แต่ละใบย้อนกลับได้เดี่ยว ๆ และ P6a มี **ทางเดิมเป็น fallback ครบทุกตัวอักษร** สำหรับ 40 ใบที่ไม่มี line item
> ลำดับที่บังคับ: **P0 → P1 → P2 → P3 → P4a → (P4b) → P5 → P6a → P6b → P7** โดย P3/P4a ห้ามเริ่มก่อน P0 ปิด (เหตุผลอยู่ในแต่ละเฟส)

### P0 — แก้บั๊กคิดเงินขาดก่อน (Tier C · operator merge · ไม่ใช่งาน SKU แต่บล็อกงาน SKU)

### P4b — เขียนคู่บนราง phase (Tier C)

ราง phase มินต์ **46 ใน 60 ใบ** ที่มีอยู่ (§0.3: `PHASE_1_*` 40 ใบ + `PHASE_2_*` 6 ใบ) จึงเมินไม่ได้ · แต่ราง phase มินต์ใบ STATE ด้วย `vatAmount: 0` (`application-phase-invoice-methods.js:443` ในบล็อก `:436-459`) ซึ่ง **ขัดกับแคตตาล็อกที่ประกาศว่า `-STATE` มี VAT** และมันสร้าง `code` ด้วยการต่อสตริง (`:109`)

**การตัดสิน: P4b เขียน `skuCode` + `unitLabel` เท่านั้น ไม่แตะ `vatAmount` ไม่แตะจำนวนเงิน** (นั่นคือ money path = L3) แถวของราง phase จึงได้ชื่อของสิ่งที่ขาย แต่ **ถูกกันออกจาก probe กระทบยอด P7 อย่างเปิดเผยและมีเงื่อนไขปลด** ไม่ใช่ข้ามเงียบ ๆ: `WHERE invoice.serviceType NOT LIKE 'PHASE_%'` พร้อมคอมเมนต์ชี้ C5 · เงื่อนไขปลด = ปิดรางนี้ (C5) หรือ operator ตัดสิน `vatAmount` ของมัน (Q6)

> **แก้จากฉบับก่อน**: §6.2 ข้อ 1 เดิมอ้างว่า "สเปกนี้เขียนกับ *ทั้งสองราง* ด้วยการเขียนคู่" แต่ P4 มี diff ของราง checkout รางเดียว ตอนนี้แยกเป็น P4a/P4b และบอกตรง ๆ ว่า P4b ทำได้แค่ไหน และอะไรที่มันทำไม่ได้

### P5 — backfill (Tier C)

*ต่อมาจาก design-event: คีย์ที่ระดับใบ ไม่ใช่ระดับบรรทัด เพราะ 40 ใน 60 ใบไม่มี line item เลย — §0.3 ชี้ต่อว่า 40 ใบนั้นคือใบ `PHASE_1_*` **ทั้งราง***

backfill เขียน **`Invoice.billingEvent`** (ไม่ใช่ `Invoice.skuCode` — ดู P2 ที่แก้แล้ว) ด้วย **รายการเรียงลำดับ หยุดที่ข้อแรกที่ตรง** ไม่ใช่ตารางที่แถวไหนก็ยิงได้:

1. คำขอมี `formData.renewalOf` → `GACP_RENEWAL` — **ตรวจก่อนเสมอ**
2. `serviceType` ∈ {`PHASE_1_STATE_FEE`, `PHASE_1_PLATFORM_FEE`, `CERTIFICATION_CHECKOUT_M1`} → `GACP_NEW_P1`
3. `serviceType` ∈ {`PHASE_2_STATE_FEE`, `PHASE_2_PLATFORM_FEE`, `CERTIFICATION_CHECKOUT_M2`} → `GACP_NEW_P2`
4. `CERTIFICATION_CHECKOUT` (ไม่มีท้าย · **7 ใบจริง** §0.3) → **ปล่อย NULL รอ operator (Q11)**

> **แก้จากฉบับก่อน**: ตารางเดิมมีสองแถวที่ยิงใบต่ออายุ **พร้อมกัน** (แถว `PHASE_2_*` กับแถว `renewalOf`) โดยไม่ประกาศลำดับ ผลของ backfill จึงขึ้นกับลำดับการวนซ้ำ · และมันไม่ใช่เคสหายาก: การต่ออายุ **ถูกออกแบบให้ลงช่อง PHASE_2** (`fee-service.js:250-258` ติดป้าย `phase: 'PHASE_2'`) สองแถวจึงตรงพร้อมกัน *เสมอ* · จาก §0.3 วันนี้ยิงตรง **0 แถว** (ต่ออายุ 0 invoice) การประกาศลำดับจึงเป็นการกันไว้ล่วงหน้า ไม่ใช่การซ่อมของที่เสียไปแล้ว

## 7. แก้ตามผลตรวจสอบ

ฉบับ v1 ถูกตรวจแล้วพบปัญหา · ทุกข้อข้างล่าง **เปิดไฟล์จริงและ/หรือรันคำสั่งจริงใน session นี้ก่อนแก้** ไม่ได้แก้ตามคำบอกเล่า — และมีสามข้อที่ผลตรวจสอบเองพูดผิด จึง **ไม่แก้** และบันทึกไว้ว่าทำไม
