## STEP 1 — Deriving "the 8 systems"

No document in the repo enumerates an operator-authored "8 systems" list. `GOALS.md` talks in terms of goals (G0-G3) and named bugs, not a system inventory. Three independent signals converge on a defensible cut at 8:

1. **`apps/backend/modules/` (the repo's own DDD bounded-context attempt)** has exactly 6 directories: `application`, `audit`, `billing`, `certificate`, `document`, `identity` (+ `public`, a thin verify/read facade, folded into the systems it exposes rather than counted alone — see below). Five of these six `index.js` barrels are still literal `module.exports = {}` placeholders (confirmed live: `apps/backend/modules/application/index.js:10`; `SYSTEM-REALITY-CHECK.md:74` recorded the same for audit/certificate/document/identity/public as of 2026-05-30 — still true today for `application`, spot-checked). Only `modules/billing/index.js` is populated (re-exports `internal/fee-service.js` + `internal/payment-constants.js`). This 6-way split is the codebase's own intended system boundary, incomplete as scaffolding but real as an org chart.
2. **`apps/backend/routes/api/index.js`** (441 lines, the single mount table for the whole API) groups ~90 route files into domain comment-headers that don't fully match the 6 module dirs: `Cultivation` (farms/planting-cycles/cultivation-logs/harvest-batches/water-sources/seed-sources/fertilizer-records/plots/plant-units) and `Trace` (trace/lots) are a large, coherent, un-modularized domain; `System` (notifications/tickets/config/dashboard/cron/sync/analytics) plus `Admin` is a second one. Both are as large and as flow-critical as the 6 `modules/` dirs but haven't been moved into the `modules/` migration yet.
3. **`SYSTEM-REALITY-CHECK.md`** (2026-05-30, independent multi-agent pass, predates this audit by 2.5 months) converged **on its own, unprompted, on an 8-row subsystem table** (§2): สมาชิก/Auth, ยื่นเอกสาร (submission/review), ติดตาม/แจ้งเตือน (notification), ใบรับรอง (certificate), บัญชี (accounting), ฟาร์ม (farm), QR/Trace, แผนก (department = scheduler/reviewer/auditor). Different grouping at the edges (it merges scheduling+audit+review into one "แผนก" row and keeps farm/trace split) but the same order of magnitude and the same center of mass.

### 1. Identity & Access — VERDICT: **PARTIAL**

Local password login/register, MFA challenge, and PDPA erasure are complete end-to-end. OAuth IdP, consent management, and tenant isolation are orphaned or contradictory. (Tenant-isolation findings are folded into the cross-cutting RLS row above rather than repeated here.)

- **HIGH / dead-end — an enabled OAuth IdP login button sends a real user to a 404.** `apps/backend/routes/api/auth/auth-idp.js:349` (`POST /:provider/callback`) has zero callers anywhere in `apps/web-app` or `apps/mobile-app` — only the `authorize-url` half is wired (`apps/web-app/src/app/auth/_components/login-chooser.tsx:188`). No `/auth/callback/*` route exists anywhere under `apps/web-app/src/app`, yet the IdP's registered redirect URI is `https://staging.gacpth.com/auth/callback/thaid` (`docs/auth/CREDENTIAL-REQUEST-DRAFT.md:32`). A user who clicks the ThaID/Provider-ID login option is sent to a page that doesn't exist.
- **HIGH / dead-end + contradiction — MFA setup-required signal has no consumer, and the two auth surfaces disagree on what to do about it.** `apps/backend/routes/api/auth/auth-provider.js:219-220` returns `mfa_setup_required` + `setup_token` — both strings appear nowhere else in the repo; no frontend handler, no endpoint that consumes the token. The parallel HEALTH-side check (`controllers/auth-controller/health-auth-profile-handlers.js:219-222`) only `logger.warn`s and explicitly lets the user log in anyway ("warn but allow login for now"). The enforcement flag (`REQUIRE_MFA_FOR_PRIVILEGED`) is hardcoded `false` in every environment file that actually feeds a running service (`apps/backend/.env.example:167`, `docker-compose.staging.yml:97`, `production.yml:125` `:-false`, `bluegreen.yml:62` `:-false`) — directly contradicting `docs/deployment/2026-04-30-work-queue-release-notes.md:161`, which states "code path is ready." **[direct]** Two production *example* files in the repo also disagree with each other on this same flag, confirmed this session: root `.env.production.example:65` sets `REQUIRE_MFA_FOR_PRIVILEGED=true`, while `apps/backend/.env.production.example:64` sets it `="false"` — the file operators would actually copy from to stand up production carries the disabled value.
- **MEDIUM / no-caller — all 5 PDPA consent endpoints are unreachable from any UI**, `apps/backend/routes/api/identity/consent.js:45,67,116,148,180` — zero `/api/consent` calls found in `apps/web-app/src` or `apps/mobile-app`. `middleware/consent-manager.js:351` documents a frontend `/consent` page that does not exist in the app tree, and the `CONSENT_REQUIRED` 403 it can throw (gate live on `routes/api/applications/applications.js:625`) has no frontend handler. Currently latent because registration auto-records consent (`health-auth-profile-handlers.js:94-98`), but ThaID-provisioned users bypass that auto-record path and would hit an unhandled 403.
- **MEDIUM / contradiction — the documented and the mounted identity API surface disagree, and the documented role list omits a role with a blanket bypass.** `docs/architecture/canonical-permission-matrix.md:36-43` documents 5 `/api/identity/*` endpoints that are not mounted in `routes/api/index.js` and have no backing files (the `identity/` route directory holds only `consent.js` and `mfa.js`). The same doc's role list (`:11-17`) omits `platform_admin`, which `apps/backend/middleware/role-middleware.js:39-41` grants a blanket bypass of every `requireRole` check.

### 2. Application Workflow — VERDICT: **PARTIAL** (new-application spine works and audits correctly; renewal, assign-reviewer, and two auditor hops are broken)

- **CRITICAL / contradiction — a renewal invoice can be printed showing an official 30,000 THB total that the backend has no record of, and cannot ever be paid.** `apps/web-app/src/constants/fees.ts:18` (`GACP_RENEWAL_FEE = 30_000`) is rendered as the grand total on the renewal quotation/invoice documents themselves (`renewal/quotation-step.tsx:61,64`, `renewal/invoice-step.tsx:63,66,67`) — not just an internal constant mismatch, an applicant-facing printed document — while the backend's only renewal fee figure is `15000` (`routes/api/finance/pricing.js:149`) and no backend renewal invoice exists at all. `client-view.tsx:52` (`RENEWAL_PAYMENT_WIRED = false`) permanently blocks the payment step regardless.
- **HIGH / dead-end — the renewal flow 404s even earlier than the payment gate, at the create-renewal-application call itself.** `apps/web-app/src/app/health/applications/renewal/client-view.tsx:227` POSTs to `/api/applications/renewal` (singular); the only backend mount is `/renewals` (plural) at `routes/api/index.js:137`, and `applications.js` has no matching POST route either. The Next.js API proxy forwards this verbatim, so the call 404s before anything else in the renewal flow runs. `routes/api/applications/renewals.js` — the real, mounted renewal router — has zero callers anywhere in the repo.
- **HIGH / contradiction — the live "assign reviewer" hop bypasses the canonical writer, contradicting that very module's own docstring, and silently drops a seeded work-queue activity.** `scheduler-assign-reviewer-handler.js:146-149` (called from `provider/coordinator/client-view.tsx:181-186`) writes `status` via `application-provider-query-methods.js:172-178` — whose docstring at `:148-155` states "any status transition must still flow through writeApplicationStatus." Because it doesn't, `createForStage`'s one production caller is never reached for this hop, so the seeded `sac_doc_review` DOC_REVIEW work-queue activity (`migration 20260430160000.../migration.sql:202`) never spawns — a reviewer's queue entry silently fails to appear.
- **HIGH / contradiction — two auditor decision hops bypass the writer too, and the A0 default-audit-emission fix (commit `4f2561f9`) never reaches them.** `routes/api/provider/auditor.js:130-134` (AUDIT_PASSED→APPROVED) and `:219-223` (→CAR_REVIEWING) import neither `auditLogger` nor `writeApplicationStatus` — the only audit trail is a generic HTTP-layer row (`routes/api/index.js:111`, `action=CREATE, entityType=SYSTEM`), not an `APPLICATION_STATUS_TRANSITION` record. The `:219-223` hop additionally skips the `sac_car_review` activity, breaking the CAR (corrective-action-request) inbox for the same reason as the reviewer case above.
- **HIGH / stub — the ESLint guard that exists specifically to catch this bypass pattern is blind to the exact shape these bypasses take, confirmed by actually running it.** `eslint-rules/no-direct-application-status-write.js:61,116` only flags a direct object-literal write (`data: { status: 'SUBMITTED' }`); a live run this session — `npx eslint routes/api/provider/auditor.js` — returned **0 findings** on a file containing exactly the bypass described above (`data: transition.updateData`, a variable, not a literal). The guardrail exists, is wired into the gate, and does not see the bug class it was built for.
- **MEDIUM / no-caller — `APPROVED → CERTIFIED`, the edge GAP-MAP's D2 ruling says should be the only point a certificate is considered valid, has no real production trigger at all.** The only callers found repo-wide are `controllers/e2e-controller.js:452` and `scripts/force_certify.js:22` — both test/debug tooling. The one frontend function that would drive it, `provider-api.ts:21` `auditorFinalApproval`, is never invoked from any component. There is no seeded `stage_activity_configs` row for `APPROVED`, so even the work-queue has nothing to hang a "do this next" activity on. Combined with System 6's finding that a dashboard tile counts `CERTIFIED` specifically: in practice, real issued certificates likely sit at `AUDIT_PASSED`/`APPROVED` indefinitely, and the workflow's own designated terminal "valid certificate" state is close to unreachable in production.
- Verified working (ran this session): the new-application submit hop (`applications.js:849`) and the CAR hop (`applications-car.js:217`) both go through the writer correctly — 44 related tests passed (`application-status-writer-audit-default`, `a0-pr2-hop-emission-contract`, `a0-pr2-submit-hops-audit-emission`). Also confirmed stale and superseded: `docs/architecture/current-truth-map.md` §1-2's "triple-write state/status/formData.workflowState" claim — no `state` column exists on the current schema (`application.prisma:48` has only `status`), the `new-legacy/` step model has been deleted, and the two dashboard-stage models it flagged have since converged.

### 3. Billing & Payment — VERDICT: **BROKEN**

The settlement engine itself (event intake → bounded tx → exactly-once GL) is internally coherent and was hardened in the last several days (commits `cbc35619`, `091655e7`, `f2bd7b41`, `88bd0a53` — bounded-tx exactly-once settle, retry/dead-letter, payment-closure cron; supersedes GAP-MAP.md's 2026-08-04 description). But the flow that should feed it is a dead end at both its front door and its back door, and the money-in/money-out edges have no driver:

- **CRITICAL / dead-end — checkout UI still cannot take a payment.** `apps/web-app/src/app/health/payments/checkout/client-view.tsx:186` terminates at "สร้างรายการสำเร็จ รอชำระเงิน" (order created, awaiting payment) with no further step. `clientSecret` is typed (`apps/web-app/src/lib/services/checkout-service.ts:46`) but never consumed; `apps/web-app/package.json` has no `stripe`/`@stripe/stripe-js` dependency at all. No QR, no Stripe Elements, no confirm step exists — confirms GAP-MAP's 2026-08-04 finding is still true 12 days later, unchanged by the settlement-engine rework.
- **CRITICAL / no-caller — DTAM remittance is a one-way door, exactly as GOALS.md claims.** `apps/backend/services/checkout/checkout-settlement-service.js:161` is the only writer of `dtamRemittanceStatus`, and it only ever writes `'PENDING'`. `recordRemittanceToDtam` (`apps/backend/services/journal-entry-service.js:905`) has zero production callers; the `dtamRemittanceBatch` model has zero writers anywhere. The declared status vocabulary PENDING→BATCHED→REMITTED→RECONCILED (`apps/backend/shared/dtam-remittance-status.js:24-41`) exists but nothing ever drives a row past its born state — state revenue collected on the platform has no mechanism to actually reach DTAM.
- **CRITICAL / dead-end — amount-mismatch settlements capture cash and then vanish from every retry path.** `checkout-settlement-service.js:314-319` stamps the webhook event `PROCESSED` even on `AMOUNT_MISMATCH`/`ORDER_NOT_FOUND`. `apps/backend/jobs/settlement-reconcile-job.js:36-43,130` deliberately skips those orders; `apps/backend/jobs/payment-closure-job.js:122-132` also skips them (sees the PaymentIntent already `succeeded` and treats it as handled). Net effect: the order sits `PENDING_PAYMENT` forever, no invoice paid, no journal entry, money already sitting in the Stripe balance, and the only trace is one `logger.error` — no operator-facing surface at all. The current unit coverage (`__tests__/unit/settle-event.test.js`, 7 tests, confirmed passing this session) has no `AMOUNT_MISMATCH` case, so this gap is untested as well as unhandled.
- **CRITICAL (security + money) / missing-guard — `PAYMENT_ADAPTER=mock` is still ungated by environment, exactly as GAP-MAP flagged 12 days ago.** `apps/backend/config/stripe.js:69-72` has no `NODE_ENV` check; `services/payment/payment-adapter.js:57-62` selects the adapter on the env string alone; `services/payment/mock-payment-adapter.js:24-26` verifies webhooks against a hardcoded public signing key literal (`'gacp-mock-payment-signing-key'`). A production-shaped environment that has this var set would accept forged settlement events.
- **HIGH / no-caller + contradiction — the fee-override mechanism is declared, wired nowhere, and couldn't work even if called.** `apps/backend/config/business-rules.js:4-9` documents six `fee.*` `SystemConfig` DB override keys; `loadFeesFromSystemConfig` (`business-rules.js:57`) has zero callers repo-wide. Even if it were called, `modules/billing/internal/fee-service.js:22-28` snapshots the `FEES` values at `require()`-time, so a later DB update could never reach an in-flight charge calculation regardless.
- **HIGH / contradiction — VAT rate (7%) is declared as three independent literals spanning the charge/record boundary**, currently equal but with nothing to keep them that way: `business-rules.js:44` (drives the actual charge, invoice, and GL components), `config/payment-fees.js:20` (drives VAT back-out math in `financial-export-service.js:188`, `accounting-service.js:377`, `journal-entry-service.js:249`, `split-payment-calculator.js:102`), and `apps/web-app/src/constants/fees.ts:27`. ## Methodology notes / limits

- Read-only throughout; no code, config, or data changed by this audit.
- "PENDING" is used deliberately per `CLAUDE.md` L1 (EVIDENCE-OR-SILENCE) — anything not directly re-verified in this session is marked as such rather than inherited as fact from older docs, even when those older docs were themselves file:line-rigorous.
- Two things already fixed since the last written record were caught and are explicitly NOT re-reported as live bugs: (1) `success-step.tsx`'s pay-later flow no longer hardcodes "PAID" — it now fetches real `status` from the API (`apps/web-app/src/app/health/applications/new/_steps/steps/success-step.tsx:45-51`), confirming `SYSTEM-REALITY-CHECK.md`'s note that this was fixed under commit `e4d7aa4`; (2) the ADR-012 "audit-log opt-in hole" that `GAP-MAP.md` (2026-08-04) called its single biggest cross-cutting gap ("~10 of 14 hops missing the audit column") was partially closed by commit `4f2561f9` (2026-08-06, "audit-by-default writer — tri-state onAudit") — `application-status-writer.js` now emits the canonical audit row by default when callers omit `onAudit`, rather than staying silent. This fix reaches only callers that go through the canonical writer — Systems 2 and 5 above each found multiple still-open direct `prisma.update`/`tx.update` bypasses (assign-reviewer, both auditor decision hops, 3 of 4 scheduling writers) that the fix cannot reach because those callers never call the writer at all.
- Six of the eight per-system audits were run as parallel fresh-context sub-agents (subagent type `auditor`, read-only tools only); findings marked **[direct]** were verified directly in this orchestrating session instead. Every sub-agent was explicitly instructed to spot-check prior documents for staleness rather than cite them uncritically, and several did — see the "confirmed fixed since GAP-MAP" / "investigated and cleared" lines inside each system section for the claims that did NOT hold up as live bugs.
- Total tally across all 8 systems: 2 verdicts of BROKEN (Billing & Payment; Scheduling & Audit/Inspection), 6 of PARTIAL, 0 of COMPLETE. No system in this platform has a fully complete, contradiction-free, dead-end-free flow today.
