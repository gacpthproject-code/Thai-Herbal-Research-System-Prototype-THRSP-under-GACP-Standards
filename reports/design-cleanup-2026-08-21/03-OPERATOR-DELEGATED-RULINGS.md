# คำตัดสิน 3 ข้อที่ operator มอบหมายให้ agent ตัดสิน — 2026-08-22

ที่มา: "ผมอ่านงานที่ผมต้องทำแล้ว คุณทำได้เลย อนุญาต" (HARNESS_LOG 2026-08-22)
หลักที่ใช้ตัดสินทุกข้อ: เลือกทางที่**ย้อนกลับได้ถูกที่สุด**และ**ไม่เพิ่มผู้ให้บริการรายใหม่**ก่อน ถ้าภายหลังกระทรวงกำหนดอย่างอื่น เปลี่ยนได้โดยไม่เสียงานที่ทำไป

## ข้อ 1 — access token ตอน Redis ล่ม: คง fail-open (พร้อม alert ที่ทำงานจริงแล้ว)

**ตัดสิน:** คงนโยบายเดิม access token = fail-open · refresh token + session family + OTP/MFA = fail-closed (ลงแล้วใน commit `fix(auth): ... fail CLOSED`)

**เหตุผล:** access token อายุ 15 นาที ความเสียหายสูงสุดจาก fail-open คือ token ที่เพิกถอนแล้วใช้ได้ต่ออีกไม่เกิน 15 นาที ขณะที่ fail-closed จะทำให้**ทุกคนถูกเตะออกจากระบบทันที**ที่ Redis สะดุดแม้วินาทีเดียว — สำหรับระบบที่เกษตรกรกรอกฟอร์ม 8 ขั้นกลางแปลง ราคานั้นแพงกว่า สิ่งที่ทำให้ทางนี้ยอมรับได้คือ alert `ACCESS_TOKEN_BLOCKLIST_REDIS_OUTAGE` ที่เมื่อก่อน**ไม่มีวันยิง** ตอนนี้ยิงจริงทั้งตอนอ่านและตอนเขียนตก ส่วนของที่อายุยาว (refresh 7 วัน) ปิดสนิทแล้ว

**ทบทวนเมื่อ:** ย้าย blocklist ลง Postgres ตามแผน stateless ขั้น 6-7 — ตอนนั้น "store ล่ม" = "DB ล่ม" ซึ่งระบบใช้งานไม่ได้อยู่แล้ว คำถามนี้จะหายไปเอง

## ข้อ 2 — กุญแจเซ็นใบรับรอง: secret mount แบบอ่านอย่างเดียว + เก็บ public key ลงแถวใบรับรอง

**ตัดสิน:** ไม่ใช้ KMS ตอนนี้ · กุญแจเป็น Docker/host secret mount read-only · production **ต้องปฏิเสธการบูต**ถ้าโหลดกุญแจไม่ได้ (เลิกพฤติกรรมสร้างกุญแจใหม่เงียบๆ) · ทุกใบรับรองที่ออกใหม่เก็บ public key (หรือ fingerprint + key id) ลงแถวของตัวเอง และตัวตรวจสอบใช้ค่าจากแถวนั้น

**เหตุผล:** KMS แก้ปัญหา "กุญแจอยู่บนเครื่อง" แต่เพิ่ม vendor และ dependency ที่วันนี้ไม่มีในโปรเจกต์ (USE_AWS_KMS branch ใช้ไม่ได้เพราะไม่มี SDK) ขณะที่ความเสี่ยงจริงที่พบคือ**กุญแจหายแล้วระบบสร้างใหม่ทำให้ใบเก่าตรวจไม่ผ่าน** — public-key-on-row แก้ตรงนั้นและต้องทำไม่ว่าจะเลือก KMS หรือไม่ พอย้ายไปเครื่องกระทรวง ถ้าเขามี HSM/KMS ค่อยเสียบ เพราะตัวตรวจสอบไม่ผูกกับที่เก็บกุญแจแล้ว

**งานที่ตามมา (Tier C):** ขั้น 1-3 ของแผน stateless (02-STATELESS-SERVER-DESIGN.md §5) — expand ก่อน: เพิ่มคอลัมน์ public key, backfill ใบเก่าด้วยกุญแจปัจจุบัน, พิสูจน์ RED (ลบ keys/ แล้ว verify ใบเก่าต้อง fail) → GREEN (ผ่านจากคอลัมน์)

## ข้อ 3 — หน้าที่เข้าไม่ถึงหลังรีดีไซน์: แถว "เครื่องมือเพิ่มเติม" ต่อ role + ปลดระวางเฉพาะที่ซ้ำจริง

**ตัดสิน:** ไม่ลบหน้าใดในรอบนี้ (ลบแล้วเอาคืนไม่ได้ และ carpet-pages.spec.ts ยังอ้างทุกเส้น) · ทุกหน้าที่มีผู้ใช้จริงได้ทางเข้ากลับผ่านแถว **เครื่องมือเพิ่มเติม** (tier secondary) ของหน้าหลักตาม role · tile หลักยังคง ≤3 ตาม N7

| หน้า | ปลายทาง | เหตุผล |
|---|---|---|
| เกษตรกร: วิเคราะห์พื้นที่, บันทึกอบรม, แม่แบบ SOP, สร้าง SOP, รายงาน ภ.ท.27/28, เอกสารแนบ | FARMER_NAV secondary | เครื่องมือจริงที่ใช้ก่อน/หลังขอใบรับรอง ไม่มีหน้าอื่นทำแทน |
| เกษตรกร: รอบการปลูก, ข้อมูลสถานประกอบการ (บน /health/more) | **ปลดระวาง /health/more** | ซ้ำกับ tile บันทึกการปลูก และ สถานประกอบการ ที่มีอยู่แล้ว — ปลดได้เมื่อ 6 รายการบนย้ายเข้า FARMER_NAV แล้ว (W3-8) |
| เกษตรกร: สรุปยอดลูกค้า | FARMER_NAV secondary ชั่วคราว | รอคำตอบ D1 เรื่องสายตรวจสลิป |
| พนักงาน: standards, surveys, herbs, datasets | secondary ของ auditor + reviewer | งานอ้างอิงที่ผู้ตรวจใช้ระหว่างตรวจ |
| พนักงาน: image-assessment | secondary ของ auditor | ผูกกับการตรวจแปลง |
| admin portal (/admin/*) | แปลงเข้า nav-config + BackHomeCrumb (W2-3 → W2-4) | ทางออกจาก admin กลับ /provider/home ต้องมีก่อนย้ายเมนู |

**เหตุผล:** ปัญหาที่ operator บ่นคือ "เข้าใจยาก เมนูซับซ้อน" ไม่ใช่ "มีหน้าเยอะ" — แถวเครื่องมือเพิ่มเติมแยกงานประจำ (tile ใหญ่) ออกจากเครื่องมือนานๆ ใช้ (ชิปเล็ก) โดยไม่ต้องสูญเสียความสามารถ และเป็นรูปแบบเดียวกับที่หน้าหลักเกษตรกรใช้อยู่แล้ว (ทีมงาน / แบบสำรวจ / ความรู้สมุนไพร)

**งานที่ตามมา (Tier B):** เติม secondary items ใน nav-config ต่อ role + เทส nav ⊆ route + view-pack — W2-5 ของแผนคลีน
