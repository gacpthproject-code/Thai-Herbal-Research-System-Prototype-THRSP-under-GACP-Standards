### ห้าข้อที่สำคัญที่สุด (อ่านโดยไม่ต้องเป็นวิศวกรก็เข้าใจ)

1. **ปุ่มดาวน์โหลดใบแจ้งหนี้พังทั้งระบบมา 22 วัน และตอนพังหน้าจอไม่บอกอะไรเลย** — เกษตรกรกดแล้วไม่มีไฟล์ ไม่มี error ไม่มีอะไรขยับ; ฟังก์ชันเดียวกันนี้ยังเป็นประตูของ "ออกใบเสร็จ" ด้วย จึงยังไม่เคยมีใครออกใบเสร็จได้เลยสักใบ (ใบแจ้งหนี้ที่จ่ายแล้ว 12 ใบ ไม่มีเลขใบเสร็จเลย)
2. **ปุ่ม "ยกเลิก/คืนเงิน" ในหน้าบัญชีของเจ้าหน้าที่ ไม่ได้ยกเลิกอะไรเลย แต่หน้าต่างปิดและรีเฟรชเหมือนสำเร็จ** — เจ้าหน้าที่เชื่อว่ายกเลิกแล้ว ใบแจ้งหนี้ยังค้างอยู่ในยอดลูกหนี้และในใบแจ้งยอดของเกษตรกรต่อไป
3. **ลบไฟล์แนบในใบสมัคร = ไฟล์ไม่ได้ถูกลบ แต่กลายเป็นเปิดดูได้โดยผู้ใช้ที่ล็อกอินคนไหนก็ได้** — ก่อนลบ คนอื่นเปิดไม่ได้ (404) หลังลบเปิดได้ (200 + ไฟล์เต็ม) เพราะการลบไปลบ "แถวที่บอกว่าใครเป็นเจ้าของ" ทิ้ง แล้วระบบตรวจสิทธิ์เลือก "ปล่อยผ่าน" เมื่อหาเจ้าของไม่เจอ
4. **ชุดทดสอบ (unit test) เขียนรายการบัญชีจริงลงฐานข้อมูลจริง** — ตอนนี้สมุดบัญชีบันทึกว่าบริษัทจ่ายเงินให้กรมฯ ไปแล้ว 45,000 บาทที่ไม่เคยจ่าย เพิ่มขึ้นทุกครั้งที่มีคนรันเทส (วันนี้วันเดียวเพิ่ม 5 รายการ) และเป็นสมุดที่ลบไม่ได้
5. **เจ้าหน้าที่การเงิน / เจ้าหน้าที่นัดหมาย เปิดดูใบสมัครของใครก็ได้** — ได้เลขบัตรประชาชน 13 หลัก ชื่อ ที่อยู่บ้าน เบอร์โทร ผังฟาร์ม และผลตรวจ ของผู้สมัครที่ไม่เกี่ยวกับหน้าที่ตัวเองเลย (ทดสอบจริง: ใบสมัครทั้ง 25 ใบในระบบ อ่านได้ 25/25)

รองลงมาที่ควรอ่านต่อทันที: **ใบกำกับภาษีที่ระบบออกวันนี้ระบุฐานภาษี 500 บาท VAT 385 บาท** (อัตรา 77% — เป็นไปไม่ได้ตามกฎหมาย), **ทุกใบสมัครถูกวางบิลซ้ำสองชุด** ทำให้รายงานลูกหนี้ 200,330 บาทรวมเกษตรกรที่จ่ายครบและได้ใบรับรองไปแล้ว, และ **หน้าสรุปค่าธรรมเนียมก่อนกดจ่ายบวกเลขไม่ลงตัว** (5,000 + 500 แสดงรวมเป็น 5,885 โดยไม่มีบรรทัด VAT)

## 3. กลุ่มปัญหาเชิงระบบ (แก้ที่ pattern คุ้มกว่าแก้ทีละข้อ)

**P1 — api-client ไม่เคย throw + call site ไม่เช็ค `success` ⇒ ทุกการกระทำที่ไม่เช็คผลลัพธ์คือ no-op เงียบโดยโครงสร้าง**
`api-client.ts` คืน `{success:false}` เมื่อไม่ใช่ 2xx และจับ transport error เอง (`:455-505`) ⇒ `catch` ของผู้เรียกเป็น dead code สำหรับ HTTP failure ทุกกรณี
เกิดผลแล้ว: B2 (ยกเลิก/คืนเงิน) · ยังไม่ได้ยกเป็นข้อแยกแต่เป็นตระกูลเดียวกัน: `components/entity/active-entity-provider.tsx:217` `await apiClient.post('/entities/me/switch', …)` ทิ้งผลลัพธ์ (สลับ workspace ล้มเหลว = UI เดินต่อเหมือนสลับแล้ว ซึ่งในโลก org-model แปลว่าทำงานผิด entity) และ `documents-step.tsx:150` `await apiClient.delete('/applications/draft-documents/…')` (ลบไม่สำเร็จ = ไฟล์ยังแนบอยู่แต่ wizard แสดงว่าหายแล้ว)
**เครื่องบังคับที่เสนอ**: lint rule ห้าม `await apiClient.(post|patch|put|delete)(…)` ที่ผลลัพธ์ถูกทิ้ง — จับได้ทั้งตระกูลด้วยกฎเดียว

**P2 — URL / field-name drift ระหว่าง FE กับ BE ไม่มีเครื่องอะไรจับ (ตระกูล renewal-404)**
B2, H1, H2, H5, L2, L1, M1 ล้วนเป็นข้อเดียวกันในรูปต่างกัน · mock เห็นด้วยกับบั๊กเสมอ จึงไม่มีเทสไหนแดง
สิ่งที่ **กวาดครบแล้ว**: GET path literal ทั้ง 91 เส้นของ web-app ถูกยิงจริงบน preview และ mutation URL ทั้ง 9 เส้น (PATCH/PUT/DELETE) มีจริงหมด ยกเว้น `/invoices/:id` ⇒ ผิว "URL ไม่มีอยู่จริง" ปิดครบสำหรับเว็บแอปแล้ว
สิ่งที่ **ยังไม่กวาด**: method drift (FE POST ไป route ที่มีแต่ GET — 404-sweep มองไม่เห็น) และ body-field drift (ดู P5)
**เครื่องบังคับที่เสนอ**: ขยาย `renewal-endpoint-contract.test.ts` เป็น contract test ที่ generate จากรายการ path ของ FE เทียบกับตาราง route จริงของ Express รวม verb

**P3 — `catch` แล้วตอบ `success:true` พร้อมค่าว่าง/ค่าเริ่มต้น ⇒ "พัง" กับ "ไม่มีข้อมูล" หน้าตาเหมือนกัน**
M3 (คิวงาน ผู้แจ้งเตือน dashboard), M2 (`/api/pricing`), L1 (master-data), M4 (แถว audit หาย), L3 (grant), M6 (scope), H18 (pricing/calculate ตอบ success ให้อินพุตมั่ว)
**เครื่องบังคับที่เสนอ**: probe ที่ fail เมื่อ `catch` block ใน `routes/` มี `success: true` อยู่ใน response — กฎเดียวจับได้ ≥ 6 จุดในรายงานนี้

**P4 — object ACL "หาเจ้าของไม่เจอ = ปล่อยผ่าน" + best-effort dual-write + hard delete ที่ลบ record แต่ไม่ลบไฟล์**
B3, H7, M13 · ตัว resolver ที่ถูกต้องมีอยู่แล้วในไฟล์เดียวกัน (`resolveRootFileOwner`, `resolveCarDocumentOwner`, `resolveAuditEvidenceOwner`) แต่ถูกต่อเข้ากับเส้น signed-URL เท่านั้น ไม่ได้ต่อกับเส้น static
**เครื่องบังคับที่เสนอ**: `gateDraftObjectAccess` และเพื่อนต้อง fail closed ทั้งหมด แล้วเขียนเทสที่ยิง cross-user GET บนทุก prefix ที่ `classifyUploadsPath` บอกว่า sensitive

**P5 — ขอบของ API ไม่มีการบังคับคำศัพท์/ชนิด/ช่วงค่า ทั้งที่ DB บังคับ**
H9 (status เป็น TEXT อิสระ ไม่มี CHECK นอกจาก `checkout_orders`), H18, M7, M8, M9, M11 (`|| null` บน NOT NULL), M16 (สาม taxonomy)
บทเรียนที่ได้จากการตรวจซ้ำ: **NaN ไม่เคยลง column** (Prisma ปฏิเสธ — พิสูจน์สดสองครั้ง) ⇒ ทุกเคส NaN ยุบเป็น 500 ที่ไม่บอก field · **ค่าที่ลงได้จริงคือค่าที่ Prisma ยอมแต่โดเมนไม่ยอม** เช่นค่าติดลบ (`area:-5` → 201 บันทึกจริง) ⇒ การกวาดที่คุ้มกว่าคือ "NOT NULL numeric ที่ไม่มีการตรวจช่วงค่า" ไม่ใช่การกวาด NaN
**เครื่องบังคับที่เสนอ**: schema validation ที่ขอบทุก route ที่เขียน DB (บอกชื่อ field ที่ผิดเสมอ) + DB CHECK constraint สำหรับทุก column ที่เป็นคำศัพท์สถานะ

**P6 — ค่าธรรมเนียมมีหลายแหล่งความจริง และการเปลี่ยนฐาน VAT ของ W14 ตามไม่ครบ**
H10 (ใบกำกับภาษี), H11 (สามหน้าจอสามเลข), H12 (สรุปที่บวกไม่ลง), H16 (checkout ไม่เคารพราคาที่ freeze), M19 (สมุดบัญชี vs ภ.พ.30), L4 (`@default` ใน schema), L13 (คอมเมนต์ค้างสองจุด)
แหล่งความจริงที่นับได้ตอนนี้: column ที่ประทับไว้ · quotation ที่ freeze · fee engine ที่คำนวณสด · ค่าคงที่ฝั่ง FE · `@default` ใน Prisma schema · คอมเมนต์ · ตัวมินต์เอกสาร legacy · ตัวมินต์ checkout
**เครื่องบังคับที่เสนอ**: หนึ่งฟังก์ชันคือราคาของจริง ทุกตัวเขียนอื่นอ่านจากที่นั่น + เทสที่ตรึงตัวเลขทุกใบเอกสารกับ engine (ขยาย `renewal-fee-ssot.test.js` ให้ครอบ phase-invoice + checkout + journal lines)

**P7 — เอกสารการเงินสองชุดต่อหนึ่งงวด**
H15 (คู่ legacy + checkout invoice, ปิดแค่ชุดเดียว), M18 (payment_transaction ซ้ำ), M14 (quote สองคลัง), L12 (เลขเอกสารสองระบบ) — รูปเดียวกันสี่ครั้ง

**P8 — ชุดทดสอบ/สคริปต์ยิงฐานข้อมูล production ที่ใช้ร่วมกัน**
B4 (สมุดบัญชี 45,000), M17 (ใบสมัครขยะ 61 ใบ), M12 (QR localhost จากเครื่อง dev) · รากเดียวกันข้อเดียว: ไม่มีอะไรกันไม่ให้ `DATABASE_URL` ชี้ของจริง
**เครื่องบังคับที่เสนอ**: `jest.setup.js` assert ว่า DATABASE_URL เป็น test database ไม่งั้น fail loud (ท่าเดียวกับ `no-secret`) — จ่ายครั้งเดียวปิดสามข้อ

**P9 — authorization narrowing ทำเป็นบางที่ บาง role**
H17 (`return null` = ไม่แคบเลย สำหรับ account/scheduler/admin, และรั่วสามผิว), M21 (`/sow`, `/checklist` ไม่มี gate ที่ GET แต่มีที่ POST), L15 (org เดียวกันทั้งระบบ, by-id ไม่ถูก scope) · ด้าน role dashboard แน่นดี (403 ทุกเส้น) — ช่องว่างอยู่ที่มิติ "การมอบหมาย" บนการอ่านที่ผูกกับใบสมัคร

**P10 — guard ที่ผูกกับ `NODE_ENV` แทนที่จะผูกกับค่า**
M12 (localhost trace URL เขียนลง DB ร่วมได้จากทุก stack ที่ไม่ใช่ production), H13 (ไม่มี guard เลยสำหรับ cert verify URL), M20 (preview เปิด `BILLING_FREE_TIER_FOR_ALL`) · เมื่อฐานข้อมูลใช้ร่วมกัน "ไม่ใช่ production" ไม่ได้แปลว่า "ข้อมูลไม่จริง"

## 5. สิ่งที่ยังไม่ได้ตรวจ (ช่องว่างที่รู้ตัว)

1. **Method drift** — FE ที่ POST ไป route ซึ่งมีแต่ GET (หรือกลับกัน) การกวาดด้วย 404 มองไม่เห็น เพราะ Express ตอบ 404 เฉพาะเมื่อ **ไม่มี route ไหนตรง path เลย** ต้องยิงราย verb ซึ่งยังไม่มีใครทำ
2. **Body-field drift** — เทียบ body ที่ FE ส่งกับ column ที่ Prisma บังคับ และกับสิ่งที่ handler destructure จริง (คือเส้น "แถว audit หายเงียบเพราะไม่ได้ส่ง column NOT NULL" ใน brief) · **ยังไม่ถูกล่าเลย** — CAR field-name (H2) เจอได้เพราะ multer 500 ดังเท่านั้น
3. **CAR flow ยังไม่ได้กดจริง** — ยืนยันการต่อสาย CTA จากโค้ดแล้ว แต่ไม่มีใบสมัครที่อยู่ CAR_PENDING ให้กด และกติกาบ้านห้ามผลิตขึ้นมาเอง
4. **การออกใบเสร็จของเจ้าหน้าที่บัญชี** — ไม่เคยมีใครกดเลยในระบบนี้ (60 ใบ `receiptAttempts=0`) และตามโค้ดจะพังที่ `getById` เดียวกับ B1 ⇒ เป็น journey รูปร่าง blocker ที่ยังไม่ถูกแตะ
5. **เส้นทางคืนเงิน / ใบลดหนี้ / ใบเพิ่มหนี้** (`credit-note-service.js`, `debit-note-service.js`, `finance/refunds`) — ไม่ถูกแตะเลยทั้งการอ่านและการยิง
6. **การตรวจยอดใน webhook** ("amount_received ต้องเท่ากับยอดของ order เป็นสตางค์", `checkout-settlement-service.js:26-28`) — ยืนยันจากคอมเมนต์ ไม่ได้ยิงจริง
7. **ผลของ `BILLING_FREE_TIER_FOR_ALL=true`** — ทุก journey ที่มีประตู entitlement ถูกตัดสินในสภาพแวดล้อมที่ประตูเปิดค้าง (M20)
8. **ACL ของ `car/*` และ `audits/*`** — พิสูจน์สดไม่ได้ ไม่มี URL ในมือ (response ของ onsite context ไม่มี URL รูป) จึงเป็นหลักฐานระดับโค้ดเท่านั้น (M13)
9. **mobile client / partner integration** — การกวาด dead route และ dead endpoint ทำบน `apps/web-app` อย่างเดียว
10. **Timing side-channel ของ login ฝั่ง provider** — วัดเวลาตอบยังไม่ได้ทำ (M5 แก้ข้อความอย่างเดียวอาจไม่พอ)
11. **การกวาดค่าติดลบ/นอกช่วงทั้งระบบ** — พิสูจน์ได้จุดเดียว (`plot.area = -5` บันทึกจริง) ส่วนโควตาน้ำหนักของ batch ยังเป็นการอ่านโค้ด (M9)
12. **RLS enforcement (Phase 1-3) และระบบหลายองค์กรจริง** — วันนี้มีองค์กรเดียวทั้งระบบ จึงพิสูจน์ขอบเขตข้ามองค์กรไม่ได้เลย (L15)
13. **การรันเทสชุดเต็ม / probe ของ repo** — การล่าครั้งนี้เป็น read-only + ยิง API สด ไม่ได้รัน `local-gate.sh` หรือ probe ใดๆ ⇒ ตัวเลข ratchet ในรายงานนี้: ไม่มี
