## 0. คำเตือนก่อนอ่าน — เรื่อง "ถูกต้อง 100%"

operator สั่งว่า "เอาให้ถูกต้องแบบ 100% เพราะต้องถูกตามกฏหมาย"

**คำตอบตรง ๆ: ไม่มีใครรับรอง 100% ได้จากหน้าคีย์บอร์ด และผมจะไม่แกล้งทำเป็นรับรอง**

สิ่งที่ทำได้จริงและเอกสารนี้ทำ คือ:
1. ออกแบบให้ตรงเกณฑ์ที่**กฎหมายเขียนไว้เป็นตัวอักษร** (พ.ร.บ.ธุรกรรมทางอิเล็กทรอนิกส์ ม.9, 10, 11, 12, 26) แล้วชี้ว่าข้อไหนตอบเกณฑ์ไหน
2. ใช้**มาตรฐานสากลที่ให้สัตยาบันแล้ว** (GS1 EPCIS 2.0 / CBV 2.0, RFC 3161, RFC 6962, RFC 8785, ISO 22005) แทนการประดิษฐ์เอง
3. **ติดป้ายทุกกฎ** ว่ามาจากไหน: `[กฎหมาย]` `[แนวปฏิบัติหน่วยงานกำกับ]` `[มาตรฐานสากล]` `[แนวปฏิบัติที่ดี]` `[เราเลือกเอง]`
4. **รวมรายการที่ยังยืนยันไม่ได้ไว้เป็นบัญชีเปิด** (§12) — ไม่แต่งข้อสมมติให้ดูเหมือนข้อบังคับ

**เอกสารสองฉบับที่ชี้ขาดว่าออกแบบนี้ถูกกฎหมายไทยไหม ยังไม่มีใครอ่าน**: มกษ. 3502-2561 (GACP พืชสมุนไพร) และเงื่อนไข GACP ของ กรมการแพทย์แผนไทยฯ เอง (`dtam.moph.go.th/.../gacp-2.pdf`) — ทั้งคู่เป็น PDF ที่เครื่อง agent อ่านไม่ออก **ต้องให้คนอ่าน** ก่อนเอาเอกสารนี้ไปใช้จริง

**สถานะที่ซื่อสัตย์ของเอกสารนี้: `BLOCKED(operator:Thai-lawyer-review + อ่าน มกษ.3502 + เงื่อนไข GACP ของ DTAM)`** ไม่ใช่ DONE

## 1. หลักการออกแบบ — เริ่มจากห้องพิจารณาคดี ไม่ใช่เริ่มจากฐานข้อมูล

operator บอกว่าเรื่องที่สำคัญที่สุดคือ **"ต้องกันข้อพิพาท"** ดังนั้นเอกสารนี้ไม่ได้เริ่มจาก "จะเก็บตารางอะไร"
แต่เริ่มจากคำถามเดียว:

> **สองปีให้หลัง เกษตรกรกับโรงงานเถียงกันต่อหน้าคนที่สาม — เซิร์ฟเวอร์เราปิด และตัวเราเองก็ถูกกล่าวหาว่าแก้ข้อมูล
> — คนที่สามใช้อะไรตัดสิน?**

ทุกตารางในเอกสารนี้ตกผลึกมาจากคำถามนั้น ไม่ใช่ตรงกันข้าม

### 1.2 สามหลักที่ตามมาจากตารางข้างบน

**หลัก A — หลักฐานต้องเดินทางออกไปจากเรา**
ปัจจุบัน `routes/api/trace/trace-verification-routes.js:36-81` คืนค่า boolean (`valid`, `signatureValid`, `hashValid`, `chainValid`)
ที่คำนวณโดยเราเอง แปลว่า **ผู้ถูกกล่าวหาเป็นคนตอบคำถามเอง** ไร้ค่าทันทีใน D5
→ ต้องคืน payload + signature + keyId ให้คนอื่นตรวจเอง และต้อง**ส่งไฟล์ให้ผู้ซื้อถือ**

**หลัก B — แก้ได้ แต่ทับไม่ได้**
`[มาตรฐานสากล]` GS1 EPCIS 2.0 §6.1 หน้า 34: *"There is no mechanism provided in either interface by which an
application can delete or modify an EPCIS Event."* — การแก้ทำโดย**เพิ่มรายการ** (ErrorDeclaration §7.4.1.2 หน้า 76)
ทั้งรายการผิดและรายการแก้อยู่ให้เห็นตลอดไป
`[กฎหมาย]` พ.ร.บ.ธุรกรรมฯ ม.11 ให้ศาลชั่งน้ำหนักจาก "ลักษณะหรือวิธีการที่ใช้**สร้าง** เก็บรักษา หรือสื่อสาร" —
ไม่ใช่แค่วิธีที่ล็อกตอนท้าย **ถ้าก่อนล็อกเขียนทับได้ตามใจ ตัวล็อกแทบไม่มีน้ำหนัก**

**หลัก C — แช่แข็งด้วย snapshot ที่เซ็นแล้ว ไม่ใช่ด้วยการล็อกแถว**
เหตุผลเต็มอยู่ §4 และ §11.1 — สรุปสั้น: วันนี้ล็อกแค่แถว `Lot` (`traceability-service.js:1017-1040` ใช้
`update({where:{id, printedAt:null}})` เป็น latch ทางเดียว ซึ่งเขียนไว้ดี) แต่ **บรรพบุรุษของมันแก้ได้หมด**
(`harvest-service.js:142,160,311` update HarvestBatch; `cultivation-log-service.js:152,163` update + **hard delete**)
⇒ R13 ที่บอกว่า "เปลี่ยนตามภายหลังไม่ได้เด็ดขาด" **วันนี้ไม่จริง** และเรากำลังจะพิมพ์คำนั้นลงบนถุง

## 2. IDENTIFIERS — อะไรถูกระบุ ระดับไหน รหัสเข้ารหัสอะไร เดาได้แค่ไหน

### 2.1 การตัดสินใจใหญ่ที่สุดก่อน: GS1 หรือไม่ GS1

`[มาตรฐานสากล]` GTIN / GLN / SSCC **ประดิษฐ์เองไม่ได้** ต้องมี GS1 Company Prefix ที่ได้ใบอนุญาตจาก
GS1 Thailand (สถาบันรหัสสากล ภายใต้ ส.อ.ท.) และ **ห้ามให้เช่าช่วง**
(GS1 Global Office support, "Who is responsible for numbering trade items?", ดึงข้อมูล 2026-08-23)

**ทางลัดที่ไม่ซื่อสัตย์ และเราจะไม่เดินมัน:** ใช้ *ไวยากรณ์* GS1 Digital Link (`/01/.../21/...`) บนโดเมนเราเอง
ด้วยตัวเลขที่เราแต่งเอง มันจะ**สแกนได้ ดูเหมือนถูก** แต่เลขไม่ unique ระดับโลก ไม่ได้ออกโดย GS1 และไม่ conformant
⇒ ถ้าเราเขียนว่า "เป็นไปตามมาตรฐานสากล GS1" คือ**คำเท็จ ที่มีชื่อกระทรวงติดอยู่** — สร้างข้อพิพาทแบบที่ operator พยายามกันพอดี

**ข้อเสนอ: สถาปัตยกรรมสองชั้น**

| ชั้น | ทำเมื่อไหร่ | รหัส | อ้างมาตรฐานได้ว่า |
|---|---|---|---|
| **ชั้น A — รหัสประจำชาติของ DTAM** | ทำได้ทันที ไม่ต้องรอใคร | รหัสของเราเอง ประกาศตรง ๆ ว่าเป็นรหัสของ DTAM | "โครงสร้างข้อมูลตามแบบ EPCIS 2.0 / คำศัพท์ตาม CBV 2.0" — จริง ตรวจได้ |
| **ชั้น B — GS1 alias** | เมื่อ DTAM ได้ Company Prefix | GLN(แปลง) / LGTIN(รุ่น) / SGTIN(ถุง) / SSCC(พาเลท) **map 1:1** ทับรหัสชั้น A | "GS1-conformant" — พูดได้ก็ต่อเมื่อได้ prefix จริง |

ออกแบบชั้น A ให้ **ใส่ชั้น B ทับได้ภายหลังโดยไม่ต้องออกรหัสใหม่และไม่ต้องปักป้ายใหม่** — นี่คือเงื่อนไขบังคับ
ไม่ใช่ทางเลือก เพราะการเปลี่ยนรหัสหลังปักป้ายลงแปลงแล้วไม่ใช่ migration แต่คือทริปลงพื้นที่

`[เราเลือกเอง]` `[บล็อกเกอร์]` ใครถือ GS1 Company Prefix — DTAM ถือใบเดียวแล้วจัดสรรให้เกษตรกรทุกคน หรือเกษตรกรต้องสมัครเอง
(อย่างหลังไม่สมจริง) — **ยังไม่ยืนยันว่า DTAM ในฐานะส่วนราชการมีสิทธิ์ทำอย่างแรกหรือไม่** ดู §12 ข้อ 6
นี่คือความไม่แน่นอนเดียวที่ล้มแผนรหัสทั้งแผนได้

### 2.2 อะไรถูกระบุบ้าง (5 อย่าง — ไม่มีระดับต้น ตาม R8)

`[มาตรฐานสากล]` เหตุผลเชิงมาตรฐานที่ **แปลงต้องเป็นสถานที่ ไม่ใช่สินค้า**: CBV 2.0 §8.2.1 หน้า 70 ห้ามใช้
SGLN/PGLN เป็นตัวระบุ Object เด็ดขาด — แปลงจึงไม่มีวันเป็น "what" ของเหตุการณ์ได้ เป็นได้แค่ "where"
ซึ่ง**ตรงกับสัญชาตญาณของ operator ใน §7.2 พอดี** (ป้ายอยู่รอดทุกฤดูเพราะรหัสสถานที่ไม่เปลี่ยนเมื่อพืชเปลี่ยน)
operator ได้คำตอบนี้จากหน้างาน มาตรฐานได้จากหลักการ — คำตอบเดียวกัน

`[มาตรฐานสากล]` และ GS1 GLN Allocation Rules 3.0.2 §2.1.2 หน้า 10 รับรองว่าแปลงย่อยมี GLN ของตัวเองได้
โดยยกตัวอย่างเป็น "ที่ดินเกษตรที่เจ้าของแบ่งเป็นแปลงย่อย" ตรงเป๊ะ
`[มาตรฐานสากล]` **ห้าม**ใช้ GLN extension (AI 254) แทนแปลง — §4 หน้า 14 จำกัดไว้ใช้ภายในองค์กร/ข้อตกลงทวิภาคีเท่านั้น ใช้กับโครงการระดับชาติที่โรงงานภายนอกต้อง resolve ไม่ได้

### 2.3 รูปแบบรหัส — ตัดสินจากการวัด ไม่ใช่จากรสนิยม

**วัดจริงบนเครื่องนี้ 2026-08-23** ด้วย `qrcode` ที่เป็น dependency ของ repo เอง (`apps/backend/node_modules`):

```
รูปแบบปัจจุบัน (UUID พิมพ์เล็ก 70 ตัว)   ECC=M ver=5 37x37  โมดูล 1.11mm @50mm
                                          ECC=H ver=8 49x49  โมดูล 0.88mm @50mm
รหัสแปลง 10 ตัว พิมพ์ใหญ่ (URL 36 ตัว)    ECC=M ver=2 25x25  โมดูล 1.52mm @50mm
                                          ECC=H ver=4 33x33  โมดูล 1.22mm @50mm
รหัสถุง 14 ตัว พิมพ์ใหญ่ (URL 41 ตัว)     ECC=M ver=3 29x29  โมดูล 1.35mm @50mm
                                          ECC=H ver=4 33x33  โมดูล 1.22mm @50mm / 0.85mm @35mm
รหัสถุง 14 ตัว พิมพ์ผสมเล็กใหญ่           ECC=H ver=5 37x37  — แพงกว่าหนึ่ง version ฟรี ๆ
```

**ข้อสรุปที่ตัวเลขบังคับ:**
1. **พิมพ์ใหญ่ล้วน** — เข้าโหมด alphanumiric ของ QR พิมพ์ผสมเสียหนึ่ง version ทันทีโดยไม่ได้อะไร
2. **ECC = H (สูงสุด)** — ที่ป้าย 50 มม. ใช้ได้ทั้งแปลงและถุงโดยไม่ต้องขยายป้ายเลย ทนสกปรก/ลบเลือน ~30%
   นี่คือของฟรีที่ยังไม่ได้หยิบ (ปัจจุบัน hardcode `errorCorrectionLevel: 'M'` ที่ `qrcode-service.js:143-145,173-175`)
3. **ป้ายถุงย่อลงเหลือ 35 มม. ได้** ที่ ECC=H ยังได้โมดูล 0.85 มม. ซึ่งอยู่ในกรอบ GS1 (สูงสุด 0.990 มม.) — ประหยัดสติกเกอร์
4. `[แนวปฏิบัติที่ดี]` quiet zone ต้อง **4 โมดูล** ตาม ISO/IEC 18004 — วันนี้เป็น 1 ที่ template
   (`lot-label-template-service.js:47-49`) และ 2 ที่ service (`qrcode-service.js:143-145`) **ผิดทั้งสองที่**
5. `[แนวปฏิบัติที่ดี]` ต้องออก QR เป็น **vector** ไม่ใช่ PNG 300px ยืดเป็น 50 มม. (~152 dpi) ซึ่งเป็นเหตุคลาสสิกของสแกนไม่ติดบนสติกเกอร์ความร้อน

**ตัวอักษรที่ใช้** `[เราเลือกเอง]`: Crockford Base32 ตัดตัวกำกวมออก → `0123456789ABCDEFGHJKMNPQRSTVWXYZ` (32 ตัว, ไม่มี I L O U)
เหตุผล: อ่านออกเสียงทางโทรศัพท์ได้, ผู้ตรวจพิมพ์ตามได้เมื่อ QR สแกนไม่ติด (D13), และไม่มีคู่ตัวอักษรที่สับสน

**โครงสร้างรหัส:**

```
รหัสแปลง   P + 8 ตัวสุ่ม + 1 ตัวตรวจ   → เช่น  PK7QM4XR9T
รหัสถุง    B + 12 ตัวสุ่ม + 1 ตัวตรวจ  → เช่น  BK7QM4XR9T2H5
รหัสรุ่น    H + 10 ตัวสุ่ม + 1 ตัวตรวจ  (ไม่มี QR พิมพ์บน PR อย่างเดียว)
```

**ตัวตรวจ (check character)** `[เราเลือกเอง]` = 5 บิตแรกของ `HMAC-SHA256(secret_ตรวจสอบ, รหัส)` map เข้า base32
- ทำงานสองอย่าง: (ก) จับพิมพ์ผิดได้ที่ฝั่ง client แบบ**ออฟไลน์** (ข) ทำให้การไล่เดารหัสต้องผ่านด่านเพิ่ม 1/32
- **ไม่ใช่ credential** — ความลับนี้กันการ*เดา* ไม่ได้ให้*สิทธิ์* ใครรู้รหัสก็ยังเขียนอะไรไม่ได้ (R14)

**ค่าเอนโทรปีและการเดา** `[เราเลือกเอง]`:

| รหัส | บิตสุ่ม | พื้นที่ | สมมติออกไปแล้ว | โอกาสเดาถูกต่อครั้ง |
|---|---|---|---|---|
| แปลง (8 ตัว + ตรวจ) | 40 บิต | 1.1 × 10¹² | 10⁶ แปลง | ≈ 2.8 × 10⁻⁸ |
| ถุง (12 ตัว + ตรวจ) | 60 บิต | 1.15 × 10¹⁸ | 10⁸ ถุง | ≈ 2.7 × 10⁻¹² |

บวก rate-limit เฉพาะทางของเส้นทางสาธารณะ (§9.12) ⇒ การไล่ enumerate รหัสไม่ใช่เส้นทางโจมตีที่คุ้ม
**แต่ต้องพูดตรง ๆ**: เอนโทรปีป้องกันการ*เดา* ไม่ป้องกันการ*ถ่ายรูป* — คนถ่าย QR ในแปลงไปได้เสมอ
ซึ่งเป็นเหตุผลว่าทำไมหน้าแปลงต้องไม่มีคำกล่าวอ้างเรื่องสินค้า (§2.5 และ D8)

**URL รูปสุดท้าย** (โดเมนสั้นช่วยลด version):
```
QR#1  HTTPS://TRACE.GACP.GO.TH/P/PK7QM4XR9T      (37 ตัว → ver 4 @ECC H)
QR#2  HTTPS://TRACE.GACP.GO.TH/B/BK7QM4XR9T2H5   (41 ตัว → ver 4 @ECC H)
```
พิมพ์ใต้ QR ด้วยตาเปล่า: `PK7QM4XR9T` เว้นวรรคเป็นกลุ่ม `PK7Q M4XR 9T` และบรรทัด `trace.gacp.go.th`

`[เราเลือกเอง]` **QR บรรจุ URL ธรรมดา ไม่บรรจุข้อมูล** — เหตุผลจากบทเรียน Washington State ที่เปลี่ยนผู้ขายระบบแล้วพัง:
อย่าสร้างรหัสที่มีแต่ฐานข้อมูลเราอ่านออก และอย่าฝังข้อมูลใน QR เพราะข้อมูลใน QR แก้ไม่ได้แต่ก็พิสูจน์ไม่ได้

### 2.4 มีรหัสกี่ตัวใน 1 ฤดูของเกษตรกร 1 คน

สมมติ: เกษตรกร 1 คน 3 แปลง แปลงละ 100 ต้น เก็บเกี่ยว 1 ครั้ง/แปลง ได้แห้ง 25 กก./แปลง บรรจุถุงละ 1 กก.

| สิ่ง | จำนวน | QR ที่ต้องพิมพ์ |
|---|---|---|
| แปลง | 3 | **3 ป้าย — พิมพ์ครั้งเดียว ใช้ตลอดไป** (ฤดูหน้า 0 ป้าย) |
| รอบปลูก | 3 | 0 |
| รุ่นเก็บเกี่ยว | 3 | 0 |
| ถุง | 75 | **75 สติกเกอร์** |
| ใบบันทึกการบรรจุ | 3 | 0 (ไฟล์) |
| **รวมฤดูแรก** | | **3 ป้ายถาวร + 75 สติกเกอร์** |
| **รวมฤดูถัดไป** | | **0 ป้าย + 75 สติกเกอร์** |

เทียบกับแบบรายต้นที่ทิ้งไปแล้ว (R8): 300 แท็ก/ฤดู **ทุกฤดู** — ในสหรัฐฯ แท็กละ ~0.45 USD ต่อต้น ไม่ใช้ซ้ำ
บางกิจการจ่ายถึง 100,000 USD/ปี และมีคดีฟ้องรัฐโคโลราโดเรื่องต้นทุนนี้ **R8 ของ operator มีหลักฐานหนุนหนักมาก** (§11.9)

`[เราเลือกเอง]` **โหมดสำรองเมื่อ serialise ไม่ไหว**: ถ้าเกษตรกรบรรจุกระสอบใหญ่ใบเดียว N=1 อยู่แล้ว
หรือพิมพ์สติกเกอร์ต่างกัน 75 ใบไม่ไหวจริง ๆ ระบบยอมให้ออกรหัสระดับรุ่น (สติกเกอร์เหมือนกันทุกใบ)
**แต่ต้องบันทึกลง PR ว่า `serialised: false` และหน้าสาธารณะต้องแสดงว่า "รหัสนี้ใช้ร่วมกัน N ใบ"**
— ไม่ซ่อนความอ่อนของหลักฐาน แต่ติดป้ายมันไว้ให้ผู้ซื้อตัดสินใจเอง

### 2.5 หน้าแปลงต้องไม่มีคำกล่าวอ้างเรื่องสินค้า — บทเรียนทุเรียนเวียดนาม (D8)

เวียดนามใช้ "รหัสพื้นที่ปลูก" แบบเดียวกับ QR#1 ของเรา และตอนนี้กำลังถูกปลอม: มีการ**ปลอมหนังสือมอบอำนาจและตราประทับบริษัท**
เพื่อใช้รหัสพื้นที่ปลูกของคนอื่น ม.ค. 2025–พ.ค. 2026 จีนตีกลับรหัสเวียดนาม 400+ รหัส ระงับไป 167 รหัส

R14 (สิทธิ์มาจาก session) กันการ**เขียน**ได้ แต่**ไม่ได้กันการเอารหัสไปแปะถุงคนอื่น** มาตรการที่ตามมาจากหลักฐานนี้:
1. หน้าแปลงสาธารณะ **ห้ามมีข้อความใดที่รับรองสินค้าในมือผู้อ่าน** — ต้องมีบรรทัดชัด ๆ ว่า
   *"รหัสนี้ระบุแปลงปลูก ไม่ได้รับรองสินค้าที่ท่านถืออยู่ · การรับรองสินค้าอยู่ที่ QR บนถุงเท่านั้น"*
2. รหัสถุงออกได้เฉพาะจาก session ที่เป็นเจ้าของรอบ ครั้งเดียว และถูกจำกัดด้วย W_avail (§5)
3. หน้าแปลงแสดงยอดสาธารณะ: **"แปลงนี้ออกรหัสถุงแล้ว N ใบ รวม X กก. (ล่าสุด <วันที่>)"**
   ⇒ ผู้ซื้อที่ถูกเสนอ "ของจากแปลง PK7QM4XR9T 2 ตัน" เห็นทันทีว่าแปลงนั้นออกไปแค่ 75 กก.
   ราคาถูก ทำได้เลย และทำให้การ "เช่ารหัส" มองเห็นได้

## 3. EVENT MODEL — บันทึกอะไร รูปร่างไหน แก้ยังไง เวลาไหนเชื่อได้

### 3.1 ทำไมต้องเป็นเหตุการณ์ ไม่ใช่แถวที่อัปเดต

`[มาตรฐานสากล]` GS1 EPCIS 2.0 (ให้สัตยาบัน มิ.ย. 2022, ISO/IEC 19987:2024) มี **5 มิติ** ไม่ใช่ 4
— §7.2.2 หน้า 47: *"what, when, where, why and how"* (มิติ how = สภาพ/เซ็นเซอร์ เพิ่มใน 2.0)
ถ้าเราเขียนสเปกด้วย 4 มิติ เราตกรุ่นตั้งแต่วันแรก

`[มาตรฐานสากล]` และการห้ามแก้เป็น **normative ไม่ใช่ทางเลือกออกแบบ** (§6.1 หน้า 34 — อ้างเต็มใน §1.2 หลัก B)
นี่คือคำตอบของมาตรฐานต่อโจทย์ "กันข้อพิพาท" ของ operator และ**แข็งกว่า "แช่แข็งตอนบรรจุ" ของเรา**
เพราะบังคับตั้งแต่บันทึกแรก ไม่ใช่หลังบรรจุ

### 3.3 คำศัพท์ — ใช้ CBV เท่านั้น ห้ามประดิษฐ์

`[มาตรฐานสากล]` CBV 2.0 §7.1.1–7.1.2 หน้า 35 บังคับว่าเอกสารที่ CBV-Compliant **SHALL** ใช้ URI ตามที่กำหนด

**⚠️ ข้อผิดพลาดที่เกือบทำ:** CBV **ไม่มี** bizStep ชื่อ `harvesting` — การเก็บเกี่ยวถูกยุบเข้า `commissioning`
(§7.1.3 หน้า 37 ระบุ *"harvesting (of fruit/vegetable)"* ไว้ใต้ commissioning)
แต่สำหรับผลผลิตที่ออกมาเป็น **lot ไม่ใช่ชิ้นที่ serialise** GS1 US แนะนำ `creating_class_instance` (§7.1.3 หน้า 38)
ซึ่งเป็นค่าที่ **ทำซ้ำได้** ต่างจาก commissioning

| เหตุการณ์ของเรา | eventType | bizStep (CBV) | disposition | หมายเหตุ |
|---|---|---|---|---|
| E1 เปิดรอบปลูก | ObjectEvent · ADD | `commissioning` | `active` | ผูก certificationInfo + bizTransaction `cert` |
| E2 ผูกพืชเข้ากับแปลง | AssociationEvent | `installing` | `in_progress` | `[มาตรฐานสากล]` EPCIS §7.4.6 หน้า 96 — เป็น event type **เดียว**ที่ผูก object เข้ากับ *สถานที่* |
| E3.. บันทึกดูแล/ปุ๋ย/น้ำ | ObjectEvent · OBSERVE | `other` ⚠️ | `active` | ⚠️ **CBV ไม่มีค่าให้ ใส่ปุ๋ย/รดน้ำ/ตัดแต่ง** — `other` คือค่าที่ซื่อสัตย์ที่สุดที่มี (§12 ข้อ 4) |

### 3.4 สามเวลา ไม่ใช่สองเวลา

โจทย์บอกว่า "สองเวลา (เกิดเมื่อไหร่ / บันทึกเมื่อไหร่)" — **ไม่พอ** เพราะเมื่อบันทึกออฟไลน์
"บันทึกเมื่อไหร่" แตกเป็นสองเวลาที่มีน้ำหนักหลักฐานไม่เท่ากันเลย

| เวลา | ใครบอก | เชื่อได้แค่ไหน |
|---|---|---|
| `eventTime` | ผู้ใช้ประกาศ | เป็น**คำกล่าวอ้าง** — น้ำหนักเท่ากับความน่าเชื่อของผู้กล่าว |
| `captureTime` | นาฬิกาเครื่องผู้ใช้ | **เชื่อไม่ได้เลย** ตั้งย้อนได้ใน 10 วินาที |
| `recordTime` | นาฬิกาเซิร์ฟเวอร์ | เชื่อได้ระดับหนึ่ง แต่ D5 คือกรณีที่เราเองถูกกล่าวหา ⇒ ต้องมีสมอนอก (§7.4) |

`[กฎหมาย]` ทำไมต้องเก็บทั้งสาม: พ.ร.บ.ธุรกรรมฯ **ม.12** บังคับว่าการเก็บรักษาต้องคง
"แหล่งกำเนิด ต้นทาง ปลายทาง และวันเวลาส่ง/รับ" ไว้ด้วย ไม่ใช่เก็บแค่เนื้อข้อมูล

**`captureMode` — คำนวณ ไม่ใช่ให้ผู้ใช้เลือก** `[เราเลือกเอง]`:
```
LIVE            : |recordTime - captureTime| ≤ 5 นาที และ |eventTime - captureTime| ≤ 1 ชม.
OFFLINE_QUEUED  : recordTime - captureTime > 5 นาที และ eventTime ≈ captureTime (±1 ชม.)
BACKDATED       : eventTime < captureTime - 24 ชม.  → บังคับกรอก backdateReason
```

**ค่าที่คำนวณและ *ต้องแสดง* ไม่ใช่ *อาจแสดง***:
- `recordingLagDays = วัน(recordTime) - วัน(eventTime)`
- หน้าสาธารณะและ PR แสดง `บันทึกสด` / `บันทึกออฟไลน์แล้วซิงก์ภายหลัง` / `บันทึกย้อนหลัง N วัน`
- **สรุประดับรอบ**: "รอบนี้มี 14 บันทึก · สด 3 · ออฟไลน์ 9 · ย้อนหลัง 2 (มากสุด 41 วัน)"

**ทำไมต้องเปิดเผยแทนที่จะซ่อน:** `[กฎหมาย]` ม.11 ให้ศาลชั่งน้ำหนัก ไม่ใช่รับ/ไม่รับ — บันทึกย้อนหลังที่**บอกว่าย้อนหลัง**
ยังมีน้ำหนัก แต่บันทึกย้อนหลังที่**แสร้งว่าสด** ถ้าถูกจับได้ครั้งเดียว ทำลายน้ำหนักของบันทึกทั้งระบบ
`[หลักฐานภาคสนาม]` และบทเรียนรัฐ Oregon: สิ่งที่ผู้ตรวจสอบตำหนิไม่ใช่ซอฟต์แวร์ แต่คือคุณภาพ input —
ข้อมูลที่ผู้ใช้รายงานเอง การชั่งไม่สม่ำเสมอ และช่องเวลาที่ไม่ถูกติดตาม

### 3.5 หน้าต่างเวลา (Time Beacon) — พิสูจน์เวลาออฟไลน์โดยไม่เชื่อนาฬิกาเครื่อง

นี่คือกลไกที่ผมอยากให้ทำมากที่สุดในเอกสารนี้ และไม่แพง `[เราเลือกเอง]`

```
1. ทุกครั้งที่เครื่องผู้ใช้ออนไลน์และคุยกับเซิร์ฟเวอร์  → เซิร์ฟเวอร์ส่ง "beacon" กลับ:
       { serverTime: T, nonce, signature = sign(T‖nonce) }   เก็บไว้ในเครื่อง
2. เมื่อบันทึกออฟไลน์  → แนบ beacon ล่าสุดที่ถืออยู่เข้ากับเหตุการณ์
3. เมื่อซิงก์สำเร็จเวลา T₁ (recordTime) → เซิร์ฟเวอร์รู้ว่า
       เหตุการณ์นี้ถูกสร้าง "หลัง T₀ และก่อน T₁"   โดย **ไม่ต้องเชื่อนาฬิกาเครื่องเลยแม้แต่นิดเดียว**
4. หน้าสาธารณะแสดงตามจริง:  "บันทึกในช่วง 3–5 พ.ค. 2569"   ไม่ใช่ "3 พ.ค. 2569 14:22:07" ที่ปลอมได้
```

บวก `deviceSeq` (ตัวนับ monotonic ต่ออุปกรณ์ ไม่มีช่อง) ⇒ **ลำดับของเหตุการณ์ออฟไลน์พิสูจน์ได้เสมอ
แม้เวลาสัมบูรณ์จะพิสูจน์ไม่ได้** — ในข้อพิพาทจริง ลำดับ ("ฉีดยาก่อนตัดกี่วัน") มักสำคัญกว่านาฬิกา

### 3.6 การแก้ไข = เพิ่มรายการ (ตอบ §7.4 ข้อ 2 ของสเปกโดยตรง)

`[มาตรฐานสากล]` EPCIS 2.0 §7.4.1.2 หน้า 76:
> *"The prior event is not modified in any way, and subsequent queries will return both the prior event
> and the error declaration."*

**ขั้นตอนแก้ไข (3 เหตุการณ์เสมอ):**
```
Ev_ผิด    เหตุการณ์เดิม                                        (อยู่ตลอดไป)
Ev_แจ้ง   สำเนา byte-identical ของ Ev_ผิด + errorDeclaration:
              { declarationTime, reason, correctiveEventIDs: [Ev_แก้] }
Ev_แก้    เหตุการณ์ใหม่ที่ถูกต้อง
```
`[มาตรฐานสากล]` **ข้อควรระวังที่สเปกเขียนไว้เอง**: เหตุการณ์แจ้งข้อผิดพลาด **ต้องไม่**คำนวณ event hash ID ใหม่
ให้ใช้ eventID เดิม (CBV 2.0 §8.9 หน้า 97)

**ผลบนหน้าสาธารณะ:** รายการที่ถูกแก้แสดงพร้อมป้าย "แก้ไขเมื่อ <วันที่> — ดูรายการเดิม"
ไม่ใช่หายไปเงียบ ๆ `[กฎหมาย]` เพราะ ม.11 ชั่งน้ำหนักจาก "ลักษณะหรือวิธีการรักษาความครบถ้วนและไม่มีการเปลี่ยนแปลง"

**ผลบน R12 (ล็อกตอนตัด):** R12 ยังยืน แต่ **R12 อย่างเดียวไม่พอ** ดู §11.4

### 3.7 eventId = ลายนิ้วมือของเนื้อเหตุการณ์เอง

`[มาตรฐานสากล]` CBV 2.0 §8.9.2 หน้า 93-95 กำหนดวิธี canonicalise (25 คุณสมบัติเรียงลำดับ, timestamp ระดับมิลลิวินาที,
คีย์ ILMD และ extension เรียงตามพจนานุกรม) ให้ **eventID = SHA-256 ของตัวมันเอง** ได้ค่าเดียวกันไม่ว่าเข้ารหัสเป็น JSON หรือ XML
และสเปกระบุการใช้งานที่ตั้งใจไว้ตรง ๆ ว่า *"especially in conjunction with digital signatures ... for notarisation purposes"*

**⚠️ ข้อบกพร่องที่ต้องแก้ก่อน:** `signature-service.js:161` ใช้
```js
const jsonString = typeof data === 'string' ? data : JSON.stringify(data);
```
`JSON.stringify` **ไม่ใช่ canonical serialisation** — ลำดับคีย์ การ escape unicode และรูปแบบตัวเลขขึ้นกับ implementation
⇒ **สองฝ่ายที่ซื่อสัตย์ทั้งคู่ คำนวณ hash จากข้อเท็จจริงชุดเดียวกัน แล้วได้คนละค่า — ซึ่งในห้องพิจารณาคดีดูเหมือนการปลอมแปลงเป๊ะ**
→ ต้องใช้ **RFC 8785 (JSON Canonicalization Scheme)** พร้อม selftest กับ test vector ของ RFC (ตาม L6 ต้องมี `--selftest`)

หมายเหตุ: เส้นทาง trace ทำถูกกว่าเส้นทางใบรับรองอยู่แล้ว — `qrcode-service.js:339-346` เรียง key ก่อน stringify
แล้วเซ็น **chainHash** ไม่ใช่ payload เปล่า (ผมอ่านเองรอบนี้) โครงถูก เหลือเปลี่ยนตัว canonicaliser

### 4.3 ตรึงเวลายังไง — สี่ชั้น เรียงตามน้ำหนักหลักฐาน

| ชั้น | กลไก | ตอบ ม.11 ข้อไหน | สถานะ |
|---|---|---|---|
| 1 | `recordTime` ของเซิร์ฟเวอร์ | (ก) วิธีสร้าง/เก็บ — **น้ำหนักต่ำสุด** เพราะเราบอกเอง | มีแล้ว (แต่แถว mutable) |

`[มาตรฐานสากล]` RFC 3161 (Standards Track, ส.ค. 2001) — token เป็นก้อนเล็ก ๆ ที่เดินทางไปใน PR
และใครก็ตามที่มีใบรับรองของ TSA ตรวจได้ **โดยไม่ต้องเรียกกลับมาที่เซิร์ฟเวอร์เรา**
`[แนวปฏิบัติหน่วยงานกำกับ]` ไทยมีมาตรฐานเรื่องนี้แล้ว: **ขมธอ. 33-2566** ว่าด้วยการประทับเวลาอิเล็กทรอนิกส์
ประกาศโดย ETDA 24 ม.ค. 2566 และ ETDA เองมีบริการ e-Timestamping ภายใต้โครงการ TEDA
⚠️ **แต่ยังไม่ยืนยัน**ว่าเปิดให้แพลตฟอร์มเอกชนใช้ไหม โปรโตคอลอะไร ราคาเท่าไหร่ (§12 ข้อ 3)

`[มาตรฐานสากล]` เทียบเคียง (ไม่ผูกพันไทย): eIDAS มาตรา 41 — time stamp ธรรมดารับฟังเป็นพยานได้ว่าข้อมูลมีอยู่ ณ เวลานั้น
และ **qualified** time stamp ได้ **ข้อสันนิษฐาน** ความถูกต้องของเวลาและความครบถ้วนของข้อมูล
รูปร่างนี้คือสิ่งที่ร่าง พ.ร.บ.ธุรกรรมฯ ฉบับใหม่ดูเหมือนจะลอกมา (§12 ข้อ 2 — **ยังเป็นร่าง อย่าอ้างเป็นกฎหมาย**)

`[มาตรฐานสากล]` ชั้นที่ 4 — RFC 6962 Certificate Transparency: Merkle tree แบบ append-only + signed tree head ที่เผยแพร่
> *"As soon as two conflicting Signed Tree Heads for the same log are detected, this is cryptographic proof of that log's misbehavior"*

**นี่คืออาวุธเดียวที่ตอบ D5 ได้จริง** และมันคุ้มครองสองทาง: กันไม่ให้ DTAM แก้บันทึกเกษตรกรเงียบ ๆ **และ**
กัน DTAM จากการถูกกล่าวหาเท็จว่าแก้

**การเผยแพร่ STH** `[เราเลือกเอง]`: อย่างน้อย 2 ที่อิสระ + หน้าเว็บกระทรวง 1 ที่ (ณ ตอนนี้ทำได้เพราะ operator
ยกกฎ residency ชั่วคราวสำหรับเฟส demo — memory `residency-rule-lifted-until-ministry-prod` — **กฎกลับมาตอนขึ้นเครื่องกระทรวงจริง** ต้องวางแผนที่เก็บในไทยไว้)

### 4.4 สร้างซ้ำได้ยังไงในอีก 2 ปี — สามขั้นที่คนแปลกหน้าทำเองได้

```
สิ่งที่คนแปลกหน้าต้องมี:  ไฟล์ PR หนึ่งไฟล์  +  คีย์สาธารณะที่กระทรวงเผยแพร่  +  โปรแกรมตรวจ 200 บรรทัด
สิ่งที่เขา *ไม่* ต้องมี:  เซิร์ฟเวอร์เรา · ความเชื่อใจในตัวเรา · การอนุญาตจากเรา

ขั้นที่ 1  canonicalise ฟิลด์ `payload` ตาม RFC 8785 → SHA-256 → เทียบกับ `dataHash`
           ⇒ ตอบว่า "เนื้อเอกสารถูกแก้ไหม"
ขั้นที่ 2  verify(`signature`, `chainHash`, คีย์สาธารณะ)   ตรวจ fingerprint ตรงกับที่พิมพ์บนเอกสาร
           ⇒ ตอบว่า "ใครเป็นคนออกเอกสารนี้"
ขั้นที่ 3  ตรวจ RFC 3161 token / Merkle inclusion proof เทียบ STH ที่เผยแพร่
           ⇒ ตอบว่า "เอกสารนี้มีอยู่ตั้งแต่เมื่อไหร่ และเราแก้ทีหลังไม่ได้"
```

**สิ่งที่ต้องเผยแพร่ให้ครบ ไม่งั้นทั้งหมดข้างบนเป็นโมฆะ:**
1. **คีย์สาธารณะต้องอยู่ *นอก* ฐานข้อมูลเรา** — วันนี้ `certification.prisma:122` เก็บ `signaturePublicKey`
   ไว้บนแถวใบรับรองเอง คือ**ผู้ตรวจได้ทั้งลายเซ็นและกุญแจจากฐานข้อมูลที่เราคุม = วงกลม พิสูจน์อะไรไม่ได้**
   → ต้องเผยแพร่ที่ URL ถาวรของกระทรวง และในอุดมคติออกใบรับรองภายใต้ **NRCA** (Thailand National Root CA ที่ ETDA ดูแล
   ซึ่ง CA ที่รับรองต้องผ่าน WebTrust audit) — ยกระดับจาก "เราบอกว่านี่คือกุญแจ DTAM" เป็น "CA ที่ไทยรับรองบอก"
2. **สเปกการ canonicalise ต้องเผยแพร่** ไม่ใช่ซ่อนในโค้ด
3. **โปรแกรมตรวจต้อง open source** + มีหน้า HTML ตรวจแบบออฟไลน์ (เปิดจากไฟล์ ไม่ต้องเน็ต)

`[มาตรฐานสากล]` เทียบเคียง: CEN-CENELEC EN 18221 (Digital Product Passport — data storage, archiving, data persistence)
กำหนดว่า passport ต้องยังเข้าถึงได้แม้ผู้ประกอบการที่สร้างมันไม่มีอยู่แล้ว — เราควรตั้งหน้าที่แบบเดียวกัน
`[หลักฐานภาคสนาม]` และหลักฐานว่าต้องเผื่อเรื่องนี้จริง: Washington State เปลี่ยนผู้ขายระบบ traceability ปี 2017–18
พลาดกำหนด ระบบมีบั๊ก ฐานข้อมูลถูกดาวน์โหลดออกไป แล้วรัฐต้องถอยไปใช้ระบบรายงานแบบมือ

### 4.5 ⚠️ HMAC ไม่ใช่ลายเซ็น

`qrcode-service.js:304-320` (อ่านเองรอบนี้) ยังรับ `HMAC-SHA256` เพื่อรองรับ record เก่า
**HMAC คือความลับร่วม ไม่ใช่ลายเซ็น** — คนที่ตรวจได้กับคนที่ปลอมได้คือคนเดียวกัน
⇒ แถวใดที่ `signatureAlgorithm = 'HMAC-SHA256'` **ต้องถือว่า "ไม่มีลายเซ็น"** ในทุกข้อพิพาท
บังคับ: (ก) เส้นทางหลักฐานห้าม mint ด้วย HMAC เด็ดขาด (ข) ทุก projection ต้องติดป้าย `UNSIGNED_LEGACY` ให้เห็น
(ค) PR ต้องพิมพ์ชื่ออัลกอริทึมไว้บนหน้าเอกสาร เพื่อไม่ให้ใครเข้าใจผิดว่าเป็นอย่างเดียวกัน

## 5. MASS BALANCE — เลขคณิตที่กันการบรรจุเกิน

### 5.1 ทำไมข้อนี้คือทั้งเกม

`[หลักฐานภาคสนาม]` ทุกคดีฟอกของที่มีเอกสารสาธารณะ รูปร่างเดียวกันหมด: **ของจริงเข้าไปในภาชนะที่สะอาด**
- แคลิฟอร์เนีย: "burner distributor" รับของเข้า METRC ถูกต้อง แล้วตีเป็น lost/destroyed บนกระดาษ ส่งของจริงเข้าตลาดมืด
- มิชิแกน: พบของ ~58 ปอนด์ที่**มีอยู่ใน METRC แต่หาไม่เจอในโลก**
- บราซิล: 81% ของการทำลายป่าในห่วงโซ่ที่ถูกเฝ้าระวัง เกิดที่ซัพพลายเออร์ที่ไม่อยู่ในรายชื่อ — วัวถูก "ฟอก" ผ่านฟาร์มที่ compliant
- อินทรีย์สหรัฐฯ: Randy Constant ขายธัญพืชไม่อินทรีย์เป็นอินทรีย์ 142 ล้าน USD **7 ปี** ภายใต้ระบบรับรองที่ไม่มีการกระทบยอดปริมาณ

⇒ **ใบรับรองที่ไม่มีสมดุลมวล คือส่วนต่างราคาที่ไม่มีกุญแจล็อก**

`[มาตรฐานสากล]` **⚠️ ข้อสำคัญที่ต้องพูดให้ตรง: GS1 ไม่ได้บังคับสมดุลมวล**
มีการ grep ข้อความเต็มของ EPCIS 2.0 (229 หน้า), CBV 2.0 (124 หน้า) และคู่มือเกษตรของ GS1 US (54 หน้า)
ด้วยคำว่า "mass balance", "reconcile", "yield", "shrink" — **ศูนย์ผลลัพธ์ทั้งสามฉบับ**
EPCIS บันทึก input และ output อย่างซื่อสัตย์ แต่**ไม่กำหนดความสัมพันธ์เชิงเลขคณิตระหว่างกันเลย**
⇒ สมดุลมวลของเรา = `[แนวปฏิบัติที่ดี]` + `[เราเลือกเอง]` **ห้ามบอก DTAM ว่า GS1 บังคับ**

สิ่งที่มาตรฐานให้คือ*เงื่อนไขตั้งต้น*: ทุกการบริโภคเป็น `inputQuantityList` ที่มีหน่วยกำกับ บนเชือก `transformationID` เดียว
⇒ ยอดคงเหลือคำนวณได้ ซึ่ง**เป็นไปไม่ได้กับ schema ปัจจุบัน**

### 5.2 เลขคณิต

**ตัวแปรต่อ HarvestBatch หนึ่งรุ่น** (ทุกตัวมีหน่วย กิโลกรัม บันทึกด้วยหน่วยเสมอ — บทเรียน areaUnit):

```
W_fresh    น้ำหนักสด ณ วันตัด           บังคับ  · บันทึกครั้งเดียวที่ E5 · แก้ได้เฉพาะผ่าน ErrorDeclaration
W_dry      น้ำหนักแห้ง หลังตากเสร็จ      บันทึกที่ E6 (ถ้ามีการตาก)
W_reject   น้ำหนักคัดทิ้ง/ไม่ผ่าน QC      สะสมจากทุก E7 (bizStep disposing, disposition destroyed)
W_sample   น้ำหนักที่ส่ง Lab             สะสมจากทุก E8 (bizStep sampling — ของถูกทำลาย)
W_packed   Σ น้ำหนักสุทธิของทุกถุงที่ออกรหัสแล้ว ไม่รวมถุงที่ถูกยกเลิก/เรียกคืน-ทำลาย

── ฐานที่แบ่งบรรจุได้ ──────────────────────────────────────────────────
   ถ้า isDried = true :   W_base = W_dry
   ถ้า isDried = false:   W_base = W_fresh          ← ขายสด ไม่ผ่านการตาก
   W_avail = W_base − W_reject − W_sample

── INVARIANT บังคับตอนบรรจุ (fail-closed, ในทรานแซกชันเดียวกับการล็อกแถว) ──
   W_packed + w_ถุงใหม่  ≤  W_avail + ε          โดย ε = 0.001 กก. (คงที่ ไม่ใช่ %)

── การสูญเสียจากการตาก (คำนวณ ห้ามกรอก) ───────────────────────────────
   W_loss_dry = W_fresh − W_dry
   yieldRatio = W_dry / W_fresh
```

### 5.3 ⚠️ ช่องโหว่ที่มีอยู่จริงในโค้ดวันนี้

`traceability-service.js:578` (อ่านเองรอบนี้):
```js
const limitWeight = Number(batch.dryWeight || batch.freshWeight || 0);
```

**ปัญหา:** ถ้าเกษตรกรตากจริง (สด 100 กก. → แห้ง 20 กก.) แต่**ไม่บันทึก `dryWeight`**
เพดานกลายเป็น 100 กก. ⇒ บรรจุได้ 100 กก. จากของที่มีจริง 20 กก. — **ช่องฟอก 5 เท่า**

**แก้:** เพดานมาจาก `isDried` ไม่ใช่จาก `||`
```
isDried = true  และ dryWeight ว่าง   →  W_avail = 0  (ปฏิเสธการบรรจุ พร้อมข้อความว่าต้องบันทึกน้ำหนักแห้งก่อน)
isDried = true  และ dryWeight มีค่า  →  W_avail จาก dryWeight เท่านั้น
isDried = false                       →  W_avail จาก freshWeight
```

**สิ่งที่โค้ดปัจจุบันทำถูกและต้องรักษาไว้** (`traceability-service.js:547-660` อ่านเองรอบนี้ — เขียนไว้ดีมาก):
- `SELECT ... FOR UPDATE` ล็อกแถว batch ก่อนคำนวณ ⇒ บรรจุพร้อมกันสองคำสั่งไม่หลุด
- คำนวณยอดใช้แล้วใหม่**ภายในล็อก** ไม่ใช่จาก include ที่ค้าง
- **fail closed เมื่อไม่มีน้ำหนักบวก** — คอมเมนต์ที่ `:591` อธิบายไว้ถูกต้องว่า
  "A missing/zero limit is NOT 'no limit'; it means 'no available weight'" — บั๊ก #22 ที่แก้แล้ว **ห้ามถอย**
- ยอดใช้แล้วไม่นับ lot ที่ soft-delete

### 5.4 แถบผลได้ (yield band) — ธง ไม่ใช่ประตู

`[หลักฐานภาคสนาม]` **บทเรียนสองด้าน**:
- ด้านหนึ่ง: 9 ธ.ค. 2025 ผู้พิพากษาที่ Orange County ตัดสินว่าการที่แคลิฟอร์เนียใช้ METRC **ไม่ตรงตามกฎหมายรัฐ**
  เพราะหน่วยงานกำกับไม่เคยเปลี่ยนข้อมูลเป็น**ธงเตือนความผิดปกติอัตโนมัติ** — *มีบันทึกไม่ใช่การปฏิบัติตาม การใช้บันทึกต่างหาก*
  (แหล่งข่าวเป็นคู่ความ ไม่ได้ตรวจคำสั่งศาลจริง — อย่าอ้างต่อหน่วยงานกำกับ)
- อีกด้าน: ในแคลิฟอร์เนีย 68% ของการตรวจแบบไม่แจ้งล่วงหน้ามาจาก exception report และการพักใบอนุญาตเริ่มจากส่วนต่าง
  ⇒ ผลักผู้ประกอบการให้โกงเพื่อเอาตัวรอด

**การออกแบบที่อยู่ระหว่างสองหลุมนี้** `[เราเลือกเอง]`:
- ตาราง `drying_yield_band(speciesCode, partCode, minRatio, maxRatio, effectiveFrom, effectiveTo, source)`
  — **เป็นข้อมูลมีวันที่ ไม่ใช่ค่าคงที่ในโค้ด** (memory: operator-no-hardcode-in-api)
  และคอลัมน์ `source` บังคับให้ระบุที่มาของตัวเลข **ห้ามใส่ตัวเลขที่ไม่มีที่มา**
- อยู่นอกแถบ → **ธงที่เจ้าหน้าที่เห็น + ช่องให้เกษตรกรอธิบาย + นาฬิกานับ**
  **ไม่บล็อกอัตโนมัติ ไม่ผ่านเงียบ ๆ**
- อธิบายแล้ว = ธงยังอยู่ในประวัติ พร้อมคำอธิบาย (เพิ่มได้ ทับไม่ได้)
- ⚠️ **ยังไม่มีตัวเลขแถบสำหรับสมุนไพรไทยชนิดใดเลย** — ต้องมาจาก มกษ. 3502 / งานวิจัย / ค่าที่เก็บได้จริง
  **ห้ามเดา** เปิดระบบครั้งแรกให้ตาราง**ว่าง** = ไม่มีธง ดีกว่ามีธงจากตัวเลขมั่ว

## 6. CERTIFICATE — ณ วันตัด กับ ณ วันนี้

### 6.1 สองข้อเท็จจริง ห้ามยุบเป็นข้อเดียว

**นี่คือความขัดแย้งภายในสเปกเองที่ต้องแก้:** R13 บอกว่าเนื้อของ QR#2 แช่แข็ง แต่ §4.4 บอกว่าหน้าสาธารณะ
แสดง "สถานะจริงเสมอ (active/หมดอายุ/เพิกถอน)" — **ทั้งสองถูก แต่พูดคนละเรื่อง**

| | `certStatusAtHarvest` | `certStatusNow` |
|---|---|---|
| คืออะไร | สถานะใบ ณ **วันตัด** | สถานะใบ **วันนี้** |
| เปลี่ยนได้ไหม | **ไม่มีวัน** — แช่แข็งใน PR | เปลี่ยนทุกวันได้ |
| ใช้ทำอะไร | ข้อเท็จจริงเชิงหลักฐาน: ตอนตัดของ ผู้ตัดมีสิทธิ์ไหม | ข้อมูลสภาพปัจจุบันของผู้ผลิต |
| แสดงที่ไหน | PR + หน้าสาธารณะ (ช่องแยก มีวันที่กำกับ) | หน้าสาธารณะ (ช่องแยก มีวันที่วันนี้กำกับ) |

**ถ้ายุบสองอันนี้เข้าด้วยกัน บันทึกที่แช่แข็งกลายเป็นบันทึกที่เปลี่ยนได้เงียบ ๆ และตกข้อ ม.10**
(ต้องรักษาความถูกต้อง "ตั้งแต่การสร้างข้อความเสร็จสมบูรณ์")

### 6.2 ทำไมต้องมีตารางประวัติสถานะใบ

`Certificate.status` วันนี้เป็น**คอลัมน์เดียวที่เขียนทับได้** ⇒ คำถาม "วันที่ 3 พ.ค. ใบใบนี้สถานะอะไร"
**ตอบไม่ได้จากฐานข้อมูลปัจจุบัน** ไม่ว่าจะเขียนโค้ดเก่งแค่ไหน

```
certificate_status_event  (append-only เหมือน trace_event)
  id, certificateId, statusFrom, statusTo, effectiveAt, decidedAt,
  reason, reasonCategory (EXPIRY | REVOCATION_FRAUD | REVOCATION_ADMIN | SUSPENSION | RENEWAL | REINSTATEMENT),
  actorId, documentRef, prevHash, chainHash, signature
```
ฟังก์ชัน `certificateStatusAsOf(certId, ณ วันที่)` อ่านจากตารางนี้เท่านั้น

**การ backfill ต้องซื่อสัตย์:** เรา*ไม่รู้*ประวัติที่ผ่านมา ⇒ แถวที่ backfill ต้องมี `backfilled: true`
และ `effectiveAt` = วันที่ backfill ไม่ใช่วันที่เดา · PR ที่อ้างช่วงก่อน backfill ต้องระบุว่า
"ประวัติสถานะก่อน <วันที่> ไม่มีบันทึก" **ห้ามแต่งประวัติที่ไม่มี**

### 6.3 ประตูที่มีอยู่ กับที่ยังขาด

**มีแล้วและทดสอบแล้ว** (`__tests__/integration/generic-trace-cert-gate.test.js`): trace resolver คืน 410 พร้อมไม่มีฟิลด์ trace
เมื่อใบถูกเพิกถอน/หมดอายุ โดยเทียบสถานะแบบ case-insensitive (`reason: 'certificate_expired'`)
**ยังขาด**: ประตูเทียบกับ **วันนี้** ไม่ใช่ **วันตัด** ⇒ §7.4 ข้อ 3 ของสเปกยังตอบไม่ได้

### 6.4 ใบหมดอายุ/ถูกเพิกถอนกลางฤดู

`[เราเลือกเอง]` — สอดคล้องกับ §4.1 ของสเปกที่ operator เคาะแล้ว:

| การกระทำ | อนุญาต? | เหตุผล |
|---|---|---|
| บันทึกดูแลรอบที่เปิดอยู่ต่อ | ✅ | **ข้อเท็จจริงต้องบันทึกได้เสมอ** — การห้ามบันทึกคือการสร้างช่องว่างในหลักฐาน |
| เปิดรอบใหม่ | ❌ | จนใบกลับมา active |
| บันทึกการตัด (E5) | ✅ บันทึกได้ แต่ `certStatusAtHarvest` = สถานะจริง ณ วันนั้น | ข้อเท็จจริงต้องบันทึกได้ |
| **ออกรหัสถุงจากรุ่นที่ตัดตอนใบไม่ active** | ❌ **ปฏิเสธ** | ⇒ ไม่มีของหลุดสู่ตลาดพร้อม QR ที่หลอกให้เข้าใจว่ามีใบ |
| ออกรหัสถุงจากรุ่นที่ตัดตอนใบ active แล้วเพิกถอนทีหลัง | ✅ | สิทธิ์เกิด ณ วันตัด · **PR ต้องระบุว่าใบถูกเพิกถอนเมื่อ <วันที่> ซึ่งอยู่หลังวันตัด** ให้ผู้ซื้อตัดสินเอง |

### 6.5 เพิกถอนหลังขายไปแล้ว (D10)

```
1. PR ที่ผู้ซื้อถือ  → **ไม่เปลี่ยน**  (นี่คือหัวใจของการแช่แข็ง — ถ้าเปลี่ยนได้ก็ไม่ใช่หลักฐาน)
2. เหตุการณ์เพิกถอน → เขียนลง certificate_status_event + เข้า Merkle tree ของวันนั้น
                       ⇒ **เวลาของการเพิกถอนถูกประทับและปฏิเสธไม่ได้เช่นกัน**
3. หน้าสาธารณะของ serial ที่กระทบ → แบนเนอร์เด่น:
       "ใบรับรอง XXX ถูกเพิกถอนเมื่อ <วันที่> ซึ่งเป็นเวลา <N> วันหลังการบรรจุสินค้ารายการนี้"
       — ข้อเท็จจริง ไม่ใช่คำตัดสินเรื่องคุณภาพสินค้า
4. แจ้งผู้ซื้อทุกรายที่เคยรับ PR จากใบนั้น → ผ่าน in-app notification เท่านั้น
       (memory: external-services-cleanup — in-app only)
       ⚠️ ต้องมี "ใครรับ PR ไปบ้าง" ⇒ ต้องมีเหตุการณ์ E13 (§7.5) — และชนกับ R6 (ผู้ซื้อไม่มี login) ดู §11.8
5. บันทึกว่าเราแจ้งแล้ว/แจ้งไม่ได้ ตามจริง — เป็นเหตุการณ์เช่นกัน
```

`[เราเลือกเอง]` **`reasonCategory` สำคัญต่อถ้อยคำ**: เพิกถอนเพราะทุจริต กับ เพิกถอนเพราะเหตุทางธุรการ
(ส่งเอกสารต่ออายุไม่ทัน) ต้องแสดงต่างกัน — อย่างแรกกระทบความน่าเชื่อของที่มาสินค้า อย่างหลังไม่
⚠️ **ถ้อยคำต้องให้ทนายไทยร่าง** — มีความเสี่ยงหมิ่นประมาท/กฎหมายคุ้มครองผู้บริโภคทั้งสองทาง (§13 ข้อ iv)

## 7. DISPUTE ARTEFACT — ใบบันทึกการบรรจุ (Packing Record)

### 7.1 หลักการ

`[หลักฐานภาคสนาม]` บทเรียนจากคดีจริงในไทย — คำพิพากษาฎีกา 6757/2560: ศาลรับข้อความ Facebook ที่**ไม่มีลายเซ็น**
เป็นหลักฐานการปลดหนี้เป็นหนังสือ โดยอาศัย พ.ร.บ.ธุรกรรมฯ ม.7 และ ม.8
สิ่งที่ชี้ขาดคือ **การระบุตัวผู้ส่ง + การที่จำเลยยอมรับว่าส่งจริง** — ไม่มีวิทยาการรหัสลับเข้ามาเกี่ยวเลย

**บทเรียน:** ชัยชนะที่ถูกที่สุดในข้อพิพาทเกษตรกร-โรงงาน คือ **artefact ที่ทั้งสองฝ่ายได้รับสำเนาไว้ตอนนั้น
และปฏิเสธไม่ได้ว่าได้รับ** — วิทยาการรหัสลับเพิ่มน้ำหนักได้อีก แต่**การครอบครองของคู่กรณี**คือฐาน

⇒ **PR ต้องถูกส่งถึงมือผู้ซื้อ (ดาวน์โหลด/LINE/อีเมล) ไม่ใช่แค่ "สแกนดูได้"**
บันทึกที่มีแต่เราถือ คือบันทึกที่มีแต่เราเท่านั้นที่จะถูกกล่าวหาว่าแก้

### 7.3 Hash URI ของ COA — การอัปเกรด R9 ที่ผมอยากเสนอที่สุด

`[มาตรฐานสากล]` CBV 2.0 §8.6 หน้า 86 กำหนดรูปแบบอ้างอิงเอกสารแบบ hash:
```
ni:///sha256;<digest>?btid=<documentURI>&mt=application/pdf
```
> *"users can verify — with a reasonable level of certainty — that the content of a given document or file ...
> is authentic. For that purpose, they just need to verify if the hash value of the document ... is identical
> to the hashValue included in the Hash URI."*

**ทำไมนี่คือส่วนเสริมของ R9 ไม่ใช่การกลับมติ:**

| | R9 วันนี้ | R9 + Hash URI |
|---|---|---|
| ไฟล์ COA ขึ้นสาธารณะ | ❌ ไม่ | ❌ ไม่ (เหมือนเดิม) |
| ค่าผลตรวจขึ้นสาธารณะ | ❌ ไม่ | ❌ ไม่ (เหมือนเดิม) |
| สรุปผ่าน/ไม่ผ่านขึ้นสาธารณะ | ❌ ไม่ | ❌ ไม่ (เหมือนเดิม) |
| PII รั่ว | ศูนย์ | ศูนย์ (hash ไม่ย้อนกลับได้) |
| **โรงงานพิสูจน์ได้ไหมว่า COA ที่ได้รับทาง LINE คือฉบับที่ระบบเห็น** | **❌ ไม่ได้** | **✅ ได้** |

**สถานการณ์ที่ R9 วันนี้แพ้ (D3):** เกษตรกรส่ง COA ที่ถูกแก้ตัวเลขให้โรงงาน หน้าสาธารณะยังขึ้น "มีผลตรวจ ✓"
แพลตฟอร์มไม่มีทางโต้แย้งได้เลย — ด้วย Hash URI ข้อพิพาทนี้**เป็นไปไม่ได้**

โครงในโค้ดพร้อมแล้ว: `Attachment` มี `fileHash` (SHA-256) และ `uploadedBy` อยู่แล้ว
พร้อมคอมเมนต์ในดัชนีที่ระบุ use case PDPA ตรง ๆ — ต้องแค่ใส่ hash ลง PR ไม่ต้องสร้างกลไกไฟล์ใหม่

`[แนวปฏิบัติที่ดี]` และเก็บ PII **ไว้นอก payload ที่เซ็น** โดยหลักการ ⇒ สิทธิ์ลบตาม PDPA กับความไม่เปลี่ยนแปลง
ของบันทึก **ไม่มีวันชนกัน** เพราะสิ่งที่แช่แข็งคือ hash ไม่ใช่ไฟล์

### 7.4 Merkle log และการเผยแพร่ตัวเลข tree head

```
รายวัน 23:59 น. (Asia/Bangkok)
  ใบไม้ = eventId ทุกใบของวันนั้น + dataHash ของ PR ทุกใบของวันนั้น (เรียงตาม seq)
  สร้าง Merkle tree  →  Signed Tree Head { treeSize, rootHash, timestamp, signature }
  เผยแพร่ STH ไปอย่างน้อย 3 ที่:  หน้าเว็บกระทรวง 1 · แหล่งอิสระ ≥2
  ส่ง inclusion proof กลับเข้าไปใน PR ทุกใบของวันนั้น เป็น **ภาคผนวกที่เซ็นแยก**
  (ไม่แก้ PR เดิม — PR เดิมแช่แข็งไปแล้ว; ภาคผนวกคือไฟล์ที่สอง ผูกด้วย documentId)
```

`[มาตรฐานสากล]` ทำไมเพียงพอ: STH สองใบที่ขัดกันสำหรับ log เดียวกัน = หลักฐานทางวิทยาการรหัสลับว่า log ประพฤติมิชอบ (RFC 6962)
และ **ลายเซ็นของ log เองทำให้ log ปฏิเสธพฤติกรรมนั้นไม่ได้**

### 7.5 การส่งมอบและการครอบครอง (E13)

```
ตอนบรรจุเสร็จ หน้าจอเกษตรกรมี:  [ดาวน์โหลด PR]  [ส่งให้ผู้ซื้อ]  [QR สำหรับให้ผู้ซื้อดาวน์โหลด]
ทุกครั้งที่ไฟล์ออกจากระบบ → เหตุการณ์ E13:
   { deliveredAt, channel(DOWNLOAD|LINK|QR), fileHash, recipientHint (ถ้ามี), actorId }
```
`[กฎหมาย]` ม.12 บังคับให้เก็บ "แหล่งกำเนิด ต้นทาง ปลายทาง และวันเวลาส่ง/รับ" — E13 ตอบข้อนี้โดยตรง
และคือสิ่งที่ทำให้ D10 (แจ้งเตือนการเพิกถอน) เป็นไปได้เลย

### 7.6 รูปแบบไฟล์ — สองร่างที่พิสูจน์ได้ว่าเป็นเนื้อเดียวกัน

`[หลักฐานภาคสนาม]` วิธีพิจารณาความแพ่งของไทย **ไม่มีกฎเฉพาะสำหรับพยานหลักฐานอิเล็กทรอนิกส์**
ต้องยื่นเป็นพยานเอกสารหรือพยานวัตถุ และศาลไทยเคยวินิจฉัยไปคนละทาง · ป.วิ.พ. ม.93 นิยมต้นฉบับ
⇒ ต้องมีทั้งสองร่าง และต้องพิสูจน์ได้ว่าเนื้อเดียวกัน:

| ร่าง | ไฟล์ | สำหรับ |
|---|---|---|
| เครื่องอ่าน | `<documentId>.gacp-pr.json` | โปรแกรมตรวจ · ระบบโรงงาน · ผู้เชี่ยวชาญ |
| คนอ่าน | `<documentId>.pdf` (PDF/A) **ที่ฝังไฟล์ JSON ไว้เป็น attachment** + พิมพ์ `dataHash` และ fingerprint ไว้บนหน้ากระดาษ | เจ้าหน้าที่ศาล · ผู้ตรวจ · แฟ้มโรงงาน |

⇒ ต้อง**เขียนฐานนี้ไว้เป็นนโยบายก่อน** ไม่ใช่ไปคิดตอนเกิดข้อพิพาท

### 8.2 หน้าเดียว หลายสายตา — ไม่ต้องมี QR ใบที่สาม

`[มาตรฐานสากล]` GS1-Conformant Resolver Standard 1.2.1 (ให้สัตยาบัน ส.ค. 2026) นิยาม `linkType`
บังคับให้มี `gs1:defaultLink` หนึ่งเดียวต่อ entity และจับคู่ตามภาษา media type และบริบท
⇒ **QR ที่พิมพ์แล้วใบเดียวเสิร์ฟผู้บริโภค โรงงาน และผู้ตรวจได้คนละหน้า**
**R10 ("ไม่มีใบที่สาม") ไม่ใช่ข้อจำกัดที่เราต้องหลบ แต่คือสิ่งที่มาตรฐานผลิตออกมาอยู่แล้ว — R10 ยืนตามเดิม**

### 8.3 สแกนเพื่ออัปเดต โดยรหัสไม่กลายเป็น credential (R14)

**กฎเหล็ก: QR บรรจุแค่ URL · ไม่มี token · ไม่มี capability ที่เซ็นแล้ว · ไม่มีอะไรที่ให้สิทธิ์**
**รหัสคือที่อยู่ ไม่ใช่กุญแจ**

```
GET /P/PK7QM4XR9T
  ├─ ไม่มี session                       → หน้าแปลงสาธารณะ (ไม่มีคำกล่าวอ้างเรื่องสินค้า §2.5)
  ├─ มี session แต่ไม่มีสิทธิ์เขียนแปลงนี้  → หน้าสาธารณะ + "คุณไม่มีสิทธิ์แก้ไขแปลงนี้"
  ├─ มี session + มีสิทธิ์ + แปลงมีรอบเปิดอยู่ → 302 ไปหน้าอัปเดตของรอบนั้น   ← สิ่งที่ operator ต้องการ
  └─ มี session + มีสิทธิ์ + ไม่มีรอบเปิด    → 302 ไปหน้า "เปิดรอบใหม่บนแปลงนี้"
```

`[แนวปฏิบัติที่ดี]` **ไม่สร้างตัวสแกนเอง** — กล้องในตัวของ Android และ iOS ถอด QR แล้วเปิด URL ให้อยู่แล้ว
สร้างเองได้แต่เพิ่ม permission prompt ในสภาพมือเปื้อนดินโดยไม่ได้อะไรกลับมา
(ในโค้ดวันนี้ `jsQR` อยู่ในไฟล์เทสต์อย่างเดียว — ถูกแล้ว ทำให้เป็นนโยบายที่เขียนไว้)

**การมอบสิทธิ์ (`PlotDelegation`)** `[เราเลือกเอง]`:
คนที่ยืนอยู่ในแปลงตอนเก็บเกี่ยว มักไม่ใช่เจ้าของบัญชี (อายุเฉลี่ยเกษตรกรไทย 58 ปีในปี 2561 · สัดส่วน 60+ ขึ้นจาก 13% เป็น 19%)
ถ้าตอบว่า "ห้ามลูกจ้างบันทึก" **ทางออกที่เกิดจริงในโลกคือแชร์รหัสผ่าน ซึ่งแย่กว่ามากสำหรับข้อพิพาท**
⇒ ให้มอบสิทธิ์อย่างเป็นทางการได้: เจ้าของมอบสิทธิ์เขียนแปลงนี้ให้คนชื่อ X ถึงวันที่ D · เป็นเหตุการณ์ ·
ทุกการเขียนบันทึกทั้ง `actorId` และ `onBehalfOfId`
`[แนวปฏิบัติที่ดี]` เทียบเคียง: แคลิฟอร์เนีย 4 CCR §15048 ผูกบัญชี track-and-trace กับเจ้าของที่ระบุชื่อ
และ **ห้ามแชร์ login เด็ดขาด** — ความรับผิดชอบต่อคน ไม่ใช่ต่อเครื่อง

**Step-up สำหรับการกระทำที่มีผลสูง** `[เราเลือกเอง]`: เก็บเกี่ยว (E5) และบรรจุ (E10) ต้องยืนยันตัวตนซ้ำภายใน N ชม.
บันทึกดูแลทั่วไปไม่ต้อง — ถ่วงดุลกับผู้ใช้อายุ 58 ปีที่ยืนอยู่กลางแดด

เว้นแต่ `NEXT_PUBLIC_PWA_ENABLED === 'true'` และ `public/sw.js:11-28` ปลดทะเบียนตัวเองพร้อมล้าง cache

**ทำไมนี่คือปัญหาเชิงหลักฐาน ไม่ใช่ปัญหา UX:** บันทึกที่มีน้ำหนักคือบันทึกที่ทำ ณ ขณะเกิดเหตุ

`[หลักฐานภาคสนาม]` ITU 2025: ช่องว่างเมือง/ชนบทของ 5G ห่างกัน 26 จุดร้อยละ และ population coverage วัดที่ที่คนอยู่ ไม่ใช่ที่ที่คนทำนา

### 9.2 ป้ายแปลงหายหรือพัง

```
รหัสแปลงเก็บที่เซิร์ฟเวอร์ ⇒ พิมพ์ใหม่ฟรี **ไม่สร้างตัวตนใหม่**
เหตุการณ์ `markerReplaced(plotCode, reason, actorId)` → แปลงที่เปลี่ยนป้าย 6 ครั้งใน 1 ปี มองเห็นได้
❌ **ห้ามออกรหัสแปลงใหม่เมื่อป้ายหาย** — การเปลี่ยนรหัสคือการตัดประวัติออกเป็นสองท่อน
```
ถ้าสงสัยว่าป้ายถูก**ถ่ายรูป/คัดลอกไปใช้** → `markerCompromised` → หน้าแปลงขึ้นคำเตือน + แจ้งเจ้าหน้าที่
**แต่รหัสยังไม่เปลี่ยน** เพราะเปลี่ยนแล้วสืบย้อนพัง — ป้องกันด้วยการที่หน้าแปลงไม่มีคำกล่าวอ้างเรื่องสินค้าอยู่แล้ว (§2.5)

**ป้ายที่ทนจริง** `[แนวปฏิบัติที่ดี]`: กลางแจ้ง แดด มรสุม โคลน อาจโดนเครื่องตัดหญ้า
⇒ วัสดุคือเงิน ไม่ใช่รหัส — แผ่นพิมพ์ UV หรือแกะสลักเลเซอร์บนเสา อยู่ได้นานกว่าอิงค์เจ็ตเคลือบหลายปี
แพลตฟอร์มควรส่ง **PDF vector ขนาดตายตัว** ที่ร้านพิมพ์ระดับอำเภอทำได้ ไม่ใช่สมมติว่าเกษตรกรมีเครื่องพิมพ์
⚠️ **ไม่มีข้อมูลราคาจริง** ว่าเกษตรกรไทยจ่ายเท่าไหร่สำหรับสติกเกอร์/ป้าย — ต้องถามเกษตรกรจริง 2-3 รายก่อนออกแบบตาม (§12 ข้อ 10)

## 11. ตรงไหนที่ขัดกับมติ operator — และเหตุผล

### 11.1 ⚠️ R13 — กลไกต้องเปลี่ยน (มติยืน กลไกเปลี่ยน)

**มติ:** "เนื้อหาที่มันชี้คือภาพแช่แข็ง ณ เวลาบรรจุ เปลี่ยนตามภายหลังไม่ได้เด็ดขาด"

**ปัญหา:** วันนี้เราล็อกแค่แถว `Lot` แต่บรรพบุรุษแก้ได้หมด (`harvest-service.js:142,160,311`;
`cultivation-log-service.js:152,163` ที่ **hard delete ได้ด้วย**) ⇒ **มติข้อนี้วันนี้เป็นเท็จ**
ผู้ซื้อคนแรกที่เทียบผลสแกนถุงเดียวกันห่างกันสองเดือน จะได้ข้อพิพาท และเราไม่มีอะไรสู้

**ข้อเสนอ:** แช่แข็งด้วย **snapshot ที่เซ็นแล้ว** (§4.1) — มติของ operator ยืนคำต่อคำและ**เป็นจริงขึ้น**
ข้อดีเพิ่ม: การแก้ข้อมูลที่ผิดจริงยังทำได้ตามกฎหมาย โดยไม่กระทบสำเนาที่ผู้ซื้อถือ

### 11.2 ⚠️ R13 ขัดกับ §4.4 ในสเปกเดียวกัน

R13 บอกแช่แข็ง · §4.4 บอกหน้าสาธารณะแสดง "สถานะจริงเสมอ"
**ทางออก: สองฟิลด์ ห้ามยุบ** (§6.1) — `certStatusAtHarvest` แช่แข็ง · `certStatusNow` สด
ถ้ายุบ บันทึกที่แช่แข็งกลายเป็นเปลี่ยนได้เงียบ ๆ และตกข้อ ม.10

### 11.3 ⚠️ R10/R13 — ขอ serialise ถุง (ปรับ ไม่ใช่กลับมติ)

**ไม่ได้ขอรื้อ R8** — R8 คือความละเอียดฝั่ง**ขาเข้า** ทำไม่ได้จริงในแปลง และ operator ถูก
แต่**ถุงคือฝั่งขาออก และเป็นวัตถุชิ้นเดียวที่คู่พิพาทถือไว้ในมือจริง ๆ**

ถ้าทุกถุงจากการบรรจุครั้งเดียวมี QR เหมือนกันเป๊ะ สามอย่างที่ operator ต้องการจะทำไม่ได้:
1. พิสูจน์ไม่ได้ว่าถุงไหนคือถุงที่พิพาท
2. นับไม่ได้ว่าออกไปกี่ใบ ⇒ ตัวหารของสมดุลมวลตอนออกรหัสหายไป
3. ใครก็พิมพ์ QR นั้นซ้ำหมื่นใบได้ และทุกใบตรวจผ่าน ⇒ **คือ "QR กลายเป็นเครื่องฟอกของนอกระบบ" ที่ §7.4 เตือนไว้เอง**

**ไม่ขัด R10:** ยังเป็น QR หนึ่งใบต่อถุง ตามที่ operator สั่ง แค่ทำให้แต่ละใบ*ไม่ซ้ำกัน*แทนที่จะ*เหมือนกัน*
ถุงมีสติกเกอร์อยู่แล้ว ต้นทุนส่วนเพิ่มคือศูนย์ที่ระดับกระดาษ

**ตรงไปตรงมา:** `[เราเลือกเอง]` — **ไม่พบกฎ GS1 ที่บังคับเรื่องนี้** (ค้นแล้วไม่เจอเกณฑ์ว่าเมื่อไหร่ต้อง serialise)
เป็นดุลพินิจทางวิศวกรรมที่โต้บนฐานการกันข้อพิพาท **ห้ามบอก DTAM ว่า "GS1 บังคับให้ serialise"**
**ข้อเสนอ: default = serialise · มีโหมดสำรองที่ติดป้ายให้เห็น (§2.4) · ให้ operator เคาะ**

### 11.4 ⚠️ R12 — ล็อกตอนตัดอย่างเดียวไม่พอ ขอยกระดับ §7.4 ข้อ 2 เป็นกติกามีเลข

**R12 ยืน** แต่การล็อก**ไม่ได้พิสูจน์อะไรเลยเกี่ยวกับสิ่งที่เกิดก่อนล็อก**
`[กฎหมาย]` ม.11 ให้ศาลชั่งน้ำหนักจาก "ลักษณะหรือวิธีการที่ใช้**สร้าง** เก็บรักษา หรือสื่อสาร"
ถ้าเกษตรกรเขียนทับวันฉีดปุ๋ยได้ตามใจสามเดือนแล้วค่อยล็อก **บันทึกที่ล็อกแล้วแทบไม่มีน้ำหนัก**

**ข้อเสนอ: ตั้ง R17** — *"ทุกการแก้ไขบันทึกก่อนตัด ต้องเป็นการเพิ่มรายการที่มีผู้กระทำ เวลา และเหตุผล
ไม่ใช่การเขียนทับ · บังคับที่ระดับฐานข้อมูล"* — ยกจาก bullet ใน §7.4 ขึ้นเป็นกติกาที่มีเลข
เพราะมันคือเสาหลัก ไม่ใช่ของแถม

### 11.5 ⚠️ R9 — ขอ **เพิ่ม** Hash URI ของ COA (ไม่กลับมติ)

รายละเอียดเต็มใน §7.3 — สรุป: **PII รั่วเท่าเดิม (ศูนย์) แต่กันข้อพิพาทได้มากกว่าอย่างชัดเจน**
ไม่มีไฟล์ ไม่มีค่า ไม่มีคำตัดสิน — เพิ่มแค่ความสามารถให้ผู้ซื้อพิสูจน์ว่า COA ที่ได้รับคือฉบับที่ระบบเห็น
**แนะนำให้ทำ**

### 11.6 ⚠️ R9 กับการเรียกคืน

§9.4 — เสนอให้แสดง *สถานะเรียกคืน* โดยไม่แสดงค่าหรือคำตัดสิน
ถ้ากฎหมายไทยบังคับหน้าที่เรียกคืนต่อสาธารณะ **กฎหมายชนะ R9** — คำถามทนาย ห้ามเดา

### 11.7 ℹ️ บรีฟที่ผมได้รับล้าสมัย — สเปกมีถึง R16 แล้ว

โจทย์บอกว่า "สเปกที่อนุมัติแล้วมี R1-R14" แต่ไฟล์จริงมี **§8 กติกา R15 และ R16** เพิ่มลงวันเดียวกัน:
- **R15** หนึ่งพื้นที่ปลูกมีรอบเปิดได้ครั้งละหนึ่งรอบ บังคับด้วย **partial unique index ที่ระดับฐานข้อมูล**
- **R16** เส้นบังคับกรอกครบย้ายจาก "ตอนสร้างแปลง" เป็น "ก่อนบันทึกการเก็บเกี่ยวครั้งแรก"

**ทั้งสองข้อเข้ากับสถาปัตยกรรมนี้พอดีและผมสนับสนุนทั้งคู่:**
- R15 ทำให้ "รอบปัจจุบันของแปลงนี้" มีคำตอบเดียวเสมอ ⇒ scan-to-update ตาม §8.3 ไม่ต้องให้ผู้ใช้เลือกรอบ
  และ **partial unique index คือเครื่องบังคับจริง ตรงกับหลัก "เครื่องบังคับแทนวินัยคน"**
- R16 ตรงกับหลักฐานภาคสนามที่หนักมาก: `[หลักฐานภาคสนาม]` งาน Amekawa (2013) พบว่าเกษตรกรส้มโอที่ได้ Q-GAP
  **ส่วนใหญ่เลิกทำบันทึกทันทีที่ได้ใบ** และ 34 จาก 64 คนไม่เข้าใจว่า GAP มีไว้ทำไม
  ⇒ ทุกช่องบังคับที่ประตูทางเข้าคือตัวทำนายการเลิกใช้ · การเลื่อนเส้นตายไปที่จุดที่เกษตรกร*ต้องการ*บางอย่างจากเรา
  (คือป้ายถุง) คือการออกแบบที่ถูก · และเงื่อนไข 4 ข้อใน §8.1 ทำให้ยังไม่ลดมาตรฐาน

### 11.8 ⚠️ R6 — ผู้ซื้อไม่มี login ทำให้เส้นทางแจ้งเตือนขาด

R6 บอกว่าเฟสนี้โรงงานเป็นคนสแกนดูอย่างเดียว ไม่มี login ฝั่งผู้ซื้อ
**สิ่งที่ยังทำได้โดยไม่แตะ R6:** PR ดาวน์โหลดได้โดยไม่ต้อง login (เกษตรกรเป็นคนส่งมอบ) และ E13 บันทึกว่า
"เกษตรกรส่งมอบเมื่อ <วันที่> ผ่าน <ช่องทาง> ไฟล์ hash <...>" — **ไม่ต้องมีบัญชีผู้ซื้อ**

**สิ่งที่ยังขาดจริงและผมจะไม่แกล้งว่าไม่ขาด:** เมื่อใบถูกเพิกถอนหรือมีการเรียกคืน (D10, §9.4)
เรา**ไม่มีทางแจ้งผู้ซื้อได้เลย** ถ้าไม่มีตัวตนของผู้ซื้อสักรูปแบบ
ทางเลือกที่เบาที่สุดที่ไม่ล้ม R6: ให้ผู้ซื้อ**เลือกเอง**ว่าจะทิ้งช่องทางไว้ตอนดาวน์โหลด PR (ไม่บังคับ ไม่ต้องสมัคร)
**เสนอให้ operator ตัดสิน · ผมชี้ช่องว่าง ไม่ได้ขอกลับมติ**

### 11.9 ✅ R8 — ไม่ขัด และขอยืนยันด้วยหลักฐาน

การเลิกระดับต้นถาวรคือมติที่มีหลักฐานหนุนหนักที่สุดในเอกสารทั้งฉบับ:
- `[หลักฐานภาคสนาม]` แท็ก RFID ต่อต้น 0.45 USD ต่อบรรจุภัณฑ์ 0.25 USD ใช้ซ้ำไม่ได้ บางกิจการจ่ายถึง 100,000 USD/ปี
  มีคดีฟ้องรัฐโคโลราโดเรื่องต้นทุน และมีคดี whistleblower ปี 2025 กล่าวหาผู้ขายว่าต้านการย้ายไป QR เพราะแท็กทำกำไรดี (ข้อกล่าวหา ยังไม่พิสูจน์)
- `[กฎหมาย, ต่างประเทศ]` แคลิฟอร์เนีย 4 CCR §15049 **ยกเว้น**ต้นที่เก็บเกี่ยวแล้วกำลังตาก/บ่ม/คัด จากการติดแท็ก
- `[กฎหมาย, ต่างประเทศ]` โคโลราโด 1 CCR 212-3-3-805 **ขยับเกณฑ์ติดแท็กจาก 8 นิ้วเป็น 15 นิ้ว** คือหลวมลง ไม่ใช่แน่นขึ้น
- แม้แต่ METRC เองก็ติดตามต้นอ่อนเป็น**ชุดละไม่เกิน 100 ต้นภายใต้ชื่อเดียว** — "seed-to-sale รายต้น" เป็นตำนานในช่วง veg
- ระดับหน่วยใช้ได้จริงในเงื่อนไขเดียว: วัวญี่ปุ่น — สัตว์มูลค่าสูงหนึ่งตัว รหัสรัฐออกให้ตั้งแต่เกิดโดยหน่วยงานรัฐ
  บังคับตามกฎหมายตั้งแต่ 1 ธ.ค. 2546 ทะเบียนเปิดสาธารณะตามกฎหมาย — **สมุนไพร 100 ต้นในแปลงเกษตรกรรายย่อยไม่ใช่แบบนั้น**
- `[มาตรฐานสากล]` ISO 22005:2007 นิยาม lot ว่า "ชุดของหน่วยสินค้าที่ผลิต/แปรรูป/บรรจุภายใต้สภาพการณ์ที่คล้ายกัน"
  และไม่เคยบังคับระดับต้น ⇒ **แปลง/รอบ + lot บรรจุ เป็นคู่หน่วยสืบย้อนที่ป้องกันได้เต็มที่**

### 11.10 ⚠️ ปฏิเสธที่จะสร้างรหัส GS1 ปลอม

ถ้า DTAM อยากพูดว่า "เป็นไปตามมาตรฐานสากล GS1" **ต้องมี Company Prefix จริงจาก GS1 Thailand ก่อน**
ผมจะไม่ออกแบบรหัสที่ดูเหมือน GS1 แต่ไม่ได้ออกโดย GS1 เหตุผลเต็มใน §2.1
**นี่ไม่ใช่การขัดมติ operator** (ท่านไม่เคยสั่ง) แต่เป็นการเตือนล่วงหน้าก่อนที่ใครจะสั่ง

## 12. รายการที่ยังยืนยันไม่ได้ — ห้ามให้ข้อไหนหลุดเข้าไปในสเปกในฐานะข้อเท็จจริง

1. **คำอ้าง "100%"** — ไม่มีใครรับรองได้ ทำได้แค่ออกแบบตามเกณฑ์ที่กฎหมายเขียนไว้แล้วให้ทนายไทยยืนยัน
2. **ร่าง พ.ร.บ.ธุรกรรมฯ ฉบับใหม่** — เรื่องการย้ายภาระการพิสูจน์ไปที่ผู้โต้แย้งเมื่อใช้ "วิธีการอิเล็กทรอนิกส์ที่น่าเชื่อถือ",
   ระบบรับรองแบบสมัครใจ, e-timestamp/e-seal ตามกฎหมาย, และวันมีผล 180 วันหลังประกาศ —
   **มาจากบล็อกสำนักกฎหมาย 2 แห่งเท่านั้น ยืนยันจาก etda.or.th ไม่ได้** สถานะในสภา ณ 2026-08-23 ไม่ทราบ
   ⇒ **ออกแบบให้ได้ประโยชน์ถ้ามันผ่าน แต่ห้ามอ้างเป็นกฎหมาย**
3. **บริการ e-Timestamping ของ ETDA/TEDA** — ยืนยันได้ว่า*มี*บริการและ*มี*มาตรฐาน ขมธอ. 33-2566
   **ยืนยันไม่ได้**ว่า: production หรือ pilot · เอกชนใช้ได้ไหม · โปรโตคอล (RFC 3161 หรือไม่) · ค่าใช้จ่าย · รูปแบบ token · SLA
   ⇒ **ต้องถาม ETDA โดยตรงก่อน commit ว่าจะใช้เป็นสมอเวลา** (บล็อก Phase 6)
4. **CBV ไม่มีค่าสำหรับ ใส่ปุ๋ย/รดน้ำ/ตัดแต่ง/สำรวจโรค** — ค่าที่ถูกต้องที่สุดที่มีคือ `other`
   ยังไม่ได้ตรวจว่ากลุ่มภาคเกษตรของ GS1 มี extension vocabulary หรือไม่ **ควรถาม GS1 Thailand**
5. **DTAM มีสิทธิ์ถือ GS1 Company Prefix ไหม และจัดสรรแทนเกษตรกรได้ไหม** — ไม่ทราบ ค่าธรรมเนียมไม่ทราบ
   **นี่คือความไม่แน่นอนที่ใหญ่ที่สุดที่ล้มแผนรหัสทั้งแผนได้**
6. **เวอร์ชัน EPCIS** — หน้า `ref.gs1.org/standards/epcis/` เสิร์ฟ PDF ที่ทุกหน้าเขียน "Release 2.0, Ratified, Jun 2022"
   แต่หน้า artefacts ระบุว่าปัจจุบันคือ "EPCIS Standard 2.0.1" **ยังไม่ได้ diff** ⇒ **ห้ามพิมพ์เลขเวอร์ชันลงสเปกจนกว่าจะมีคนเปิด 2.0.1**
7. **ระยะเวลาเก็บรักษาบันทึก** — **ไม่พบกฎไทยที่ระบุ** ผู้สมัครที่ต้องตรวจ: มกษ. 3502-2561 ·
   ประกาศ สธ. เรื่องสมุนไพรควบคุม (กัญชา) พ.ศ. 2568 · ประมวลรัษฎากร (5 ปีทั่วไป) · EMA HMPC GACP guideline
   ⇒ **ปฏิบัติต่อเรื่องนี้เป็นมติ operator ที่ยังเปิดอยู่ ไม่ใช่ข้อเท็จจริงทางกฎหมาย**
   ข้อเสนอ `[เราเลือกเอง]` ระหว่างรอ: อายุใบรับรอง + 5 ปี เป็นอย่างน้อย
8. **มกษ. 3502-2561 และเงื่อนไข GACP ของ DTAM เอง** — **ไม่มีใครอ่าน** เป็น PDF ที่เครื่องอ่านไม่ออก
   นี่คือเอกสารของหน่วยงานกำกับเราเองและเป็นสิ่งที่ยังไม่ได้อ่านที่สำคัญที่สุด
9. **สถานะกัญชาไทย ณ 2026** — ประกาศสมุนไพรควบคุม (กัญชา) พ.ศ. 2568 ประกาศ 25 มิ.ย. 2568 มีผลวันถัดมา
   จำกัดการขายเพื่อการแพทย์ต้องมีใบสั่ง และมีระบบอนุญาตการผลิต/แปรรูป/ส่งออก
   **แต่ยังไม่ได้อ่านตัวประกาศ และไม่ได้ตรวจว่าเปลี่ยนอะไรหลังจากนั้น** · กฎหมายกัญชาไทยเปลี่ยนซ้ำหลายรอบตั้งแต่ปลดล็อก 2565
   ⇒ **หน้าที่บันทึก/รายงานเฉพาะกัญชา ห้ามเดาจากเอกสารนี้**
10. **PDPA ม.33** — ตัวบทมาจากแหล่งทุติยภูมิ (siam-legal 403) ต้องตรวจกับราชกิจจานุเบกษา
11. **ยังไม่เคยมีศาลไทยชั่งน้ำหนักบันทึกที่มาจากแพลตฟอร์ม** — เจอคำพิพากษาที่เกี่ยวข้อง 1 คดี (ฎีกา 6757/2560)
    และเป็นเรื่องข้อความแชต ไม่ใช่บันทึกระบบ · **ไม่พบคดีไทยเกี่ยวกับ hash chain, timestamp หรือ audit log ของแพลตฟอร์ม**
    ⇒ ออกแบบนี้ให้เหตุผลจากตัวบทและจากแนวปฏิบัติต่างประเทศ **ไม่ใช่จากบรรทัดฐานไทย** — ต้องบอก operator ตรง ๆ
12. **ไม่มีตัวเลขต้นทุนการพิมพ์จริงในไทย** — ไม่มีข้อมูลว่าเกษตรกรรายย่อยจ่ายเท่าไหร่สำหรับสติกเกอร์
    เครื่องพิมพ์ฉลากความร้อน หรือป้ายแกะสลัก · ทุกอย่างใน §9.2 เป็นการให้เหตุผลเชิงวิศวกรรม **ต้องถามเกษตรกรจริง 2-3 ราย**
13. **ไม่มีข้อมูลจากฐานข้อมูลจริง** — ไม่ได้เชื่อมต่อ ไม่ทราบจำนวนแถวใด ๆ
    ⇒ **ประเมินขนาด migration ไม่ได้ และไม่ทราบว่ามี QR กี่ใบอยู่ในตลาดแล้ว** (แก้ที่ Phase 0)
14. **ไม่พบหลักฐานว่ามีเขตอำนาจใดเคยทำระบบติดตามกัญชาระดับ *แปลง*** (ไม่ใช่ระดับต้น)
    ⇒ ออกแบบนี้ **ไม่มีบรรทัดฐานในวงการกัญชา** แม้จะเป็นเรื่องปกติมากในอาหารและเกษตรอินทรีย์
    เป็นจุดยืนที่ป้องกันได้ **แต่เป็นทางเลือกของเรา ไม่ใช่มาตรฐานที่ชี้ได้**
15. **ไม่ได้ตรวจ `buildTraceIntegrity` ครบทุกบรรทัด** — อ่าน `qrcode-service.js:329-384` แล้วเห็นว่าเรียง key ก่อน stringify
    แต่**ไม่ได้ตรวจว่า `stableStringify` canonical พอสำหรับให้บุคคลที่สามคำนวณซ้ำได้จริงหรือไม่** — สมมติว่าไม่พอ

## 14. สรุปหนึ่งย่อหน้าสำหรับ operator

กติกาที่ท่านเคาะไว้ **R1–R16 ยืนได้เกือบทั้งหมด** สิ่งที่ต้องเปลี่ยนไม่ใช่มติ แต่คือ**กลไกใต้มติ**:
แช่แข็งด้วยเอกสารที่เซ็นแล้วแทนการล็อกแถว (เพราะวันนี้ R13 ยังเป็นเท็จ — บรรพบุรุษของ Lot แก้ได้และลบได้อยู่) ·
แก้ด้วยการเพิ่มรายการตั้งแต่วันแรกไม่ใช่แค่หลังตัด · เก็บสามเวลาแทนสองเวลาพร้อมหน้าต่างเวลาที่ไม่ต้องเชื่อนาฬิกาเครื่อง ·
และ **ส่งไฟล์ใบบันทึกการบรรจุให้ผู้ซื้อถือไว้จริง ๆ** เพราะบันทึกที่มีแต่เราถือ คือบันทึกที่มีแต่เราที่จะถูกกล่าวหาว่าแก้
ผมขอ**เพิ่ม**สองอย่างที่ไม่ได้ลดความเป็นส่วนตัวเลย: hash ของไฟล์ COA (โรงงานพิสูจน์ได้ว่าได้ฉบับจริง โดยไม่มีไฟล์ ไม่มีค่า ไม่มีคำตัดสินขึ้นสาธารณะ)
และ serial ต่อถุง (ยังหนึ่ง QR ต่อถุงตามที่ท่านสั่ง แค่ไม่ซ้ำกัน — ไม่งั้นใครก็พิมพ์ซ้ำหมื่นใบได้)
สิ่งที่ผมทำไม่ได้คือรับรองว่า "ถูกต้อง 100%" — เอกสารสองฉบับที่ชี้ขาดเรื่องนี้ (มกษ. 3502-2561 และเงื่อนไข GACP ของ DTAM เอง)
ยังไม่มีใครอ่าน และคำถามทางกฎหมาย 7 ข้อใน §13 ต้องมีทนายไทยตอบก่อน
