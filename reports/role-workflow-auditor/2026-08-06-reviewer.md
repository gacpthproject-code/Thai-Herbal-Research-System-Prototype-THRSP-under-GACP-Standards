### Findings inside S2

**F-01 — dead status branch in reviewer's own "pendingReview" partition** (severity P2, informational-but-real)
`reviewer.js:99`:
```js
const pendingReview = queue.filter((item) => ['ASSIGNED_FOR_REVIEW', 'DOC_FEE_PAID'].includes(item.workflowState));
```
`queue` is built exclusively from rows matched by `reviewerQueueWhere` (`reviewer-queue-where.js:29-37`), whose `REVIEWER_QUEUE_STATUSES` **does not include `DOC_FEE_PAID`**. `DOC_FEE_PAID` also precedes assignment (no `reviewerId` yet), so it could never satisfy the `reviewerId=owner` predicate even if the status were allowed. Net effect: the `'DOC_FEE_PAID'` branch of this filter is unreachable — `pendingReview` can in practice only ever contain `ASSIGNED_FOR_REVIEW` rows. Not currently harmful (the intended set is a superset that never gets hit), but it is a "ตั้งใจ ≠ ของจริง" mismatch a reader of the code would not expect.

**F-02 — same dead-status pattern in the shared `/provider/applications` list page** (severity P2)
`apps/web-app/src/app/provider/applications/page.tsx:46`:
```ts
const REVIEW_WORKFLOW_STATES = ['SUBMITTED', 'DOC_FEE_PAID', 'ASSIGNED_FOR_REVIEW', 'REVISION_REQUESTED'] as const;
```
used at `page.tsx:112-116` for the "Pending Review" KPI tile. This page is reachable by `document_reviewer` (route gate `apps/web-app/src/lib/provider-role-config.ts:87-88`; the reviewer dashboard's own "ดูทั้งหมด" button links here — `apps/web-app/src/app/provider/reviewer/client-view.tsx:262`). Because the backend list (`GET /api/provider/applications`, `applications.js:173-244`) applies the same `reviewerId=self`-only visibility for `document_reviewer` (`application-visibility.js:86-96`), and `SUBMITTED`/`DOC_FEE_PAID` applications have no `reviewerId` yet, **the "Pending Review" tile can never count a `SUBMITTED` or `DOC_FEE_PAID` row for a reviewer viewer** — the tile silently degrades to counting only `ASSIGNED_FOR_REVIEW`/`REVISION_REQUESTED`. Same root cause as F-01 (reviewerId-narrowed visibility vs. a pre-assignment status literal baked into reviewer-facing UI), two independent occurrences.

**F-03 — the live "assign reviewer" write path bypasses the canonical status writer** (severity P1 — this is *how S2 begins* for the reviewer role)
Two backend endpoints implement the same `DOC_FEE_PAID → ASSIGNED_FOR_REVIEW` transition:
- `POST /api/provider/applications/:id/assign` (`applications.js:321` → `applicationsAssign`, `apps/backend/routes/api/provider/handlers/applications.js:151-230`) — calls the **canonical** writer `writeApplicationStatus` (`applications.js:178-215` in that handler file), which per its own doc comment (`apps/backend/routes/api/provider/handlers/workflow-transitions-handler.js:333-339`) spawns the ADR-016 `WorkActivity` row and runs the in-tx audit hook.
- `POST /api/provider/scheduler/reviewer-assignments` (alias `/assign-reviewer`, `apps/backend/routes/api/provider/scheduler.js:30,32` → `schedulerAssignReviewer`, `apps/backend/routes/api/provider/handlers/scheduler-assign-reviewer-handler.js:35-253`) — builds the transition with `workflowTransitionService.buildTransitionUpdate` (`:113-119`) but writes it with `applicationService.writeAssignmentColumns` (`:146-149`), which is a **plain `prisma.application.update`** (`apps/backend/services/application-service/application-provider-query-methods.js:172-178`, doc comment at `:164-171` explicitly: "the Prisma write itself is a plain row update"). Its own audit log call is post-write, best-effort, and the error is swallowed (`scheduler-assign-reviewer-handler.js:190-210`, `catch (_auditErr) { // non-fatal }`).

**Which one is live**: the frontend Scheduler coordinator UI calls the second path — `apps/web-app/src/app/provider/coordinator/client-view.tsx:185` → `providerApiPaths.schedulerAssignReviewer` = `/api/provider/scheduler/reviewer-assignments` (`apps/web-app/src/lib/services/provider-api.ts:12`). A repo-wide grep for any frontend caller of `POST /:id/assign` (the canonical-writer sibling) found **none** — `applicationsAssign` is currently unreached from the web app.

Consequence for reviewer role: the actual event that populates a reviewer's queue (assignment into `ASSIGNED_FOR_REVIEW`) does **not** spawn a `WorkActivity` row, so the ADR-016 activity timeline the reviewer can see at `GET /:applicationId/activities` (`applications.js:635-677`, described in-code at `:630-634` as "read-only timeline") will show a gap for that transition, and the case's arrival into the queue has no atomic audit-log guarantee (only best-effort, catchable, post-commit). This matches `GAP-MAP.md:64`'s GP-5a note ("assignment bypasses status writer... no WorkActivity, no writer audit") — confirmed still true against current `main`, and it is also a Law-3.6 (single-source-of-truth) violation: two endpoints implement one transition with different integrity guarantees, one of which is dead code.

**View-in-the-loop for F-03**: operator has a scheduler assign a reviewer via the real UI (`/provider/coordinator`), then opens `/provider/applications/<id>` → Activities tab for that case, and separately checks `AuditLog` for a `REVIEWER_ASSIGNED` row timed atomically with the status flip.

## S6 — ออกใบรับรอง (`CERTIFIED`)

1. **เห็นอะไร**: A status badge only. `provider-application-detail-config.ts:209-212` maps `APPROVED`/`CERTIFIED`/`DOC_APPROVED` to the `success` badge tone on the application detail page — that is the **only** S6 surface reachable from a reviewer's own application detail page; grep for `certificate`/`Certificate`/`CERTIFIED` in `apps/web-app/src/app/provider/applications/[id]/page.tsx` returns **no matches** — no certificate number, no download link, no QR is rendered on the page the reviewer actually works from. The tenant-wide certificate dashboard (`GET /api/provider/certificates/dashboard`, `apps/backend/routes/api/provider/handlers/certificates.js:14-16`, gated `requireRole(PROVIDERRoles)` — any provider role) is URL-reachable (`/provider/certificates` admitted to `[ADMIN, AUDITOR, DOCUMENT_REVIEWER]`, `provider-role-config.ts:188`) but its **nav link is deliberately hidden** from `document_reviewer` (`provider-role-config.ts:189`, comment: "the reviewer neither issues nor needs certs"), and it is a tenant-wide aggregate dashboard (counts/expiry lists), not a per-application certificate lookup — there is no way from there to jump straight to "the cert for the case I just approved."
2. **กดอะไรได้**: Nothing — certificate issuance is system/admin-owned (`ROLE_TRANSITIONS.system`, `APPROVED→CERTIFIED` — canonical dictionary §1.3) and auto-fires inside the S5 `APPROVED` transition (`workflow-transitions-handler.js:554-571`, `handleCertificateIssuance`), not a separate reviewer action.
3. **อ้างข้อมูลชุดไหน**: N/A for reviewer (no per-application certificate query reachable from their own working page).
4. **legacy slip**: none.
**View-in-the-loop**: operator, logged in as reviewer, opens an application they approved that later reached `CERTIFIED`, and confirms there is genuinely no in-page link to the issued certificate (only the green "CERTIFIED" badge) — then separately opens `/provider/certificates` to confirm it's a tenant aggregate dashboard, not a per-case view.

## Legacy slip path — consolidated answer for reviewer role

Across all 7 steps, `document_reviewer` has **no reachable route, permission, or menu item** pointing at the slip-upload/slip-review path (`apps/backend/routes/api/finance/payment-slips.js`, `apps/web-app/src/app/provider/accounting/slip-review-modal.tsx`, `slip-queue-summary-cards.tsx`). This was checked at the permission-set level (`canonical-rbac.js:174-179` — no `PAYMENT_SLIP_*`), the API-gate level (`payment-slips.js:44-51` `REVIEW_ROLES` set), and the frontend-route level (`provider-role-config.ts` — no `accounting` area rule lists `R.DOCUMENT_REVIEWER`). This is a clean separation, not a gap — worth recording as a **positive** finding since it's evidence the D2 drain-then-purge boundary (PROMPT-PAYMENT-REWORK.md §4.2/§4.3) is already correctly drawn for this role, independent of whatever legacy-sweeper finds for Account/farmer.
