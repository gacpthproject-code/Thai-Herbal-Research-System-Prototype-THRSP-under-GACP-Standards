# บันทึกออกแบบเส้นเงินหลังยื่น (2026-08-15) — DRAFT จากบทสนทนา operator × auditor

> **สถานะ: ยังไม่ใช่คำวินิจฉัย** — เนื้อหามาจากบทสนทนาของ operator กับ auditor (fresh-context) หลังปิด M2a
> จะกลายเป็น spec ได้ต่อเมื่อ operator ยืนยันใน session หลัก (รอบ grill แบบ M1/M2) · ทุก path เงิน = L3 flag-only + Tier C

## ทิศที่ operator แสดงเจตนา (รอยืนยันเป็น G-ruling)

- จ่ายเงินสำเร็จ (webhook จาก gateway) → ระบบส่งคำขอเข้าคิวทีมจ่ายงาน**อัตโนมัติ** — ไม่มีปุ่มมนุษย์ปลดล็อก
- **บัญชีเปลี่ยนบท**: จาก "ผู้อนุมัติ/ปลดล็อก" → "ผู้กระทบยอด + ผู้ออกเอกสารตามกฎหมาย + คนจับผิดระบบ"
- สอดคล้องกฎเครื่องเดิมที่มีอยู่แล้ว: `settle-webhook-only` / `webhook-idempotent` — **แต่ทั้งคู่ยัง `[MANUAL]`** (มีเครื่องมือ ไม่มีการบังคับอัตโนมัติ — ดู CLAUDE.md L3)

## เงื่อนไขรับของดีไซน์นี้ (auditor — "ถอดมนุษย์ออก = ทุกจุดค้างกลายเป็นค้างถาวร")

พิสูจน์ให้ได้ 6 ข้อก่อนถือว่าปลอดภัย: (1) ลายเซ็น webhook ปลอมปลดล็อกไม่ได้ (2) ยิงซ้ำไม่แจกงาน/ออกใบเสร็จซ้ำ (3) webhook หาย — ใครเจอ จอไหนบอก (4) จ่ายสำเร็จแต่แจกงานพัง — คำขออยู่ไหน มีคิวซ่อมไหม (5) เจ้าของกระบวนการคืนเงิน (6) กระทบยอด + การนำส่งเงินรัฐ (DTAM VAT 0 / PLATFORM VAT 7% — สองเจ้าของเงิน `applications.js:974-978`)

## จอบัญชีต้องตอบ 4 คำถาม (requirement sketch)

1. เงินเข้าวันนี้แยก DTAM/PLATFORM/VAT — ตรงกับ gateway ไหม (ต่าง = เด้ง)
2. จ่ายแล้วแต่ยังไม่ไปต่อเกิน X ชม. — ตัวไหน (จอจับรอยรั่ว "ค้างเงียบ")
3. ยื่นแล้วแต่ไม่มีใบแจ้งหนี้ — ตัวไหน (จอจับเคสประตูที่ 5)
4. เอกสารภาษีครบทุกใบ / ค้างนำส่งเงินรัฐเท่าไร

## รอยรั่วที่มีหลักฐานแล้ว (BACKLOG-FOUND 2026-08-15 — flag-only)

ประตู 5 ยื่นแล้วไม่มีใบให้จ่าย (`application-review-revision-methods.js:97-98`) · early-return บอกไปจ่ายทั้งที่ DB ยัง SUBMITTED (`applications.js:660-661`) · ออกใบเสนอราคา fire-and-forget (`:982-991`) · **ยังไม่ยืนยัน**: มีกลไกออกใบทีหลัง (`ensurePhase1Quotations`?) หรือไม่ — ต้องพิสูจน์บน DB จริง

## 6 ฉากพิสูจน์ (Playwright + Stripe test key เท่านั้น — live key ห้ามตั้งจน G1 เขียว)

1. ยื่น → เห็นหน้า "ต้องชำระ" ยอดตรงใบเสนอราคา
2. จ่าย test → success → คำขอโผล่คิวแจกงานภายในกี่วินาที (ดูด้วยตา)
3. ยิง webhook ซ้ำ → ไม่แจกงาน/ใบเสร็จซ้ำ
4. จ่ายสำเร็จแต่ล้มกลางแจกงาน → ระบบซ่อมตัวเองหรือค้าง
5. คำขอทางประตู 5 → มีใบให้จ่ายไหม
6. หน้าบัญชี: transaction + ใบเสร็จ + ยอดกระทบ Stripe

**เกณฑ์รับ: วิดีโอ + แถว DB ก่อน/หลัง + audit row ครบสามอย่าง — log อย่างเดียวไม่รับ** · ต้องรันบน Postgres จริง (staging)

## คำถามนโยบายค้างที่ operator (ต้องตอบก่อนเขียน spec)

1. จ่ายก่อนตรวจเอกสาร → เอกสารไม่ผ่าน คืนเงินไหม กี่ % ใครอนุมัติ
2. จ่ายแล้วไม่มีเจ้าหน้าที่รับงานใน X วัน — SLA + ผู้รับผิดชอบ
3. ถอนคำขอกลางทาง งวด 1 คืนหรือไม่คืน

## เพิ่มเติมรอบ 4 (grill 4 มุม — "ต้องมี ไม่งั้นใช้จริงไม่ได้")

**เกษตรกร:** รู้เสมอว่า "ถึงไหน + ตาใคร" · ใบเสร็จดาวน์โหลดเองได้ · นโยบายเงินเมื่อตรวจไม่ผ่านต้องประกาศ · เส้นตาย (5 วันทำการ) ต้องมองเห็นบนจอ ไม่ใช่รู้ตอนหมดอายุ
**พนักงาน:** งานมีเจ้าของเสมอ + **ต้องมีทางดึงงานคืน**เมื่อเจ้าของหาย (โค้ดกันคนอื่นตัดสินแทนแล้ว — `application-workflow-handlers.js:98-105` — แต่ยังไม่มีขากลับ) · จอค้างเกินเวลา (ไม่ใช่แค่คิวตัวเอง) · DOC_REVISION กับ FIELD_CAR ต้องไม่ปนจอ
**ผู้บริหาร:** ค้างที่ขั้นไหนนานสุด · **"จ่ายแล้วแต่ยังไม่มีคนรับงาน" = ตัวชี้วัดที่จับรอยรั่วทั้ง 3 ได้เอง** · เงินรับแล้วยังไม่นำส่งกรมเท่าไร
**กระทรวง:** ตรวจย้อนใบ (M2a วางรากแล้ว — stamp กติกา ณ วันยื่น) · แก้กติกาไม่ต้อง deploy + ของเก่าไม่โดนกฎใหม่ (M2a พิสูจน์ระดับ logic แล้ว) · **ข้อมูลในประเทศ vs Stripe — ต้องมีคำตอบเป็นลายลักษณ์อักษรก่อนขึ้นจริง** · audit log ลบไม่ได้ + บันทึกแม้ตอนปฏิเสธ (มีแล้ว)

## คำถามตัดสินของ operator (ปรับเป็น 4 ข้อ)

1. ตรวจไม่ผ่าน → คืนเงินไหม คืนก้อนไหน (รัฐ/แพลตฟอร์ม/VAT) ใครอนุมัติ
2. งานที่มอบหมายแล้วเจ้าของหาย → ใครมีสิทธิ์ดึงคืน
3. Stripe vs "ข้อมูลไม่ออกนอกประเทศ" → ยอมรับความเสี่ยงชั่วคราวเป็นลายลักษณ์อักษร หรือรอ gateway ไทย
4. ใบกำกับภาษี 7% ออกในนามใคร เลขรันอย่างไร

## ลำดับพิสูจน์ที่ตกลงเป็นแนว (auditor เสนอ — รอ operator สั่งใน session หลัก)

1. ยกสแตกจริง (compose + Postgres + migration + seed) — **ด่านแรก ไม่ผ่าน = ที่เหลือคือการเดา**
2. เส้นทองเส้นเดียว: สมัคร → ยื่น → จ่าย (test mode) → webhook → คิวเจ้าหน้าที่ → ตรวจ → ส่งกลับแก้ → แก้ → กลับคนเดิม → ลงพื้นที่ → ออกใบ — วิดีโอ + trace + dump แถว DB ทุกจุดเปลี่ยนสถานะ
3. กดซ้ำ 3 รอยต่อเป็นการเฉพาะ (ประตู 5 → จ่ายได้ไหม เป็นข้อแรก)
4. แดชบอร์ดทำหลังสุด — "แดชบอร์ดบนข้อมูลที่ยังไหลไม่ครบ คือการวาดภาพให้ผู้บริหารเชื่อในสิ่งที่ยังไม่จริง"

**เกณฑ์ผ่านต่อทุกการเปลี่ยนสถานะ: คอลัมน์เปลี่ยน + audit row เกิด + จอฝั่งที่เกี่ยวข้องเปลี่ยน — ครบสามพร้อมกัน ขาดข้อเดียว = ไม่ผ่าน**

## รอบ 5 — มุมมอง ERP เต็มระบบ (ชิ้นสรุปของเธรด)

**Scorecard: แกน ERP ที่มีแล้ว (ยืนยันด้วยโค้ด):** workflow engine ปฏิเสธเส้นผิดกฎ (`workflow-transition-service.js:47-91`) · SoD เบื้องต้น (`application-workflow-handlers.js:98-105`) · dated master data (M2a) · append-only (ตารางกฎ) · audit แม้ตอนปฏิเสธ (submit-guard) · field-level ownership (`form-data-ownership.js`) · **payment gate ก่อนแจกงานมีจริง** (`scheduler-assign-reviewer-handler.js:86-91`)

**สามชั้นที่ขาด:** (1) **Exception/Aging layer** — ไม่มีใครถามระบบว่า "อะไรค้างอยู่ นานเท่าไร" — รอยรั่วทั้ง 3 คืออาการของโรคนี้ (2) **Financial reconciliation layer** — สายโซ่ quotation→invoice→รับชำระ→ใบกำกับ→กระทบยอด payout→นำส่งกรม มีแต่ต้นทาง ปลายทางยังไม่มี (3) **Control matrix** — SoD กระจายในโค้ด ไม่มีตารางเดียว (สถานะ×บทบาท×ทำอะไรได้) ที่เป็นเทสรันได้ — กระทรวงจะขอดูตาราง ไม่ใช่โค้ด

**โปรแกรม Phase 0–4 (เรียงตามความเสี่ยง):**
- **Phase 0 — พิสูจน์ท่อ** (ห้ามงานอื่นแซง): ยกสแตกจริง + เส้นทองเส้นเดียว + กด 3 รอยต่อ · เกณฑ์: คอลัมน์+audit row+จอ ครบสามต่อทุก transition · **ไม่ผ่าน = หยุดทุกงานใหม่**
- **Phase 1 — รายงานของค้าง 5 ตัว**: จ่ายแล้วไม่ถูกแจก / แจกแล้วเกิน SLA / ใกล้หมดเวลาแก้ / จ่ายค่าตรวจแล้วยังไม่นัด / **ค้างในสถานะที่ไปต่อไม่ได้** (ตัวจับบั๊กเชิงระบบ — รันเป็น cron แจ้งเตือน)
- **Phase 2 — การเงินปิดงานตามกฎหมาย** (Tier C ทั้งชุด · L3 = agent เสนอ diff เท่านั้น): เลขเอกสารเรียงไม่ขาด · หน้ากระทบยอด + **หน้ารายการที่กระทบไม่ได้** · แยกยอดนำส่งกรม/รายได้/VAT · คืนเงิน = ใบลดหนี้ append-only
- **Phase 3 — Control matrix + four-eyes**: ผู้ตรวจพื้นที่ ≠ ผู้อนุมัติ · ผู้ตรวจเอกสาร ≠ ผู้ตรวจพื้นที่ · รายงานการใช้ประตูพิเศษ
- **Phase 4 — แดชบอร์ดรายบทบาท (หลังสุดเสมอ)**

**คำถามตัดสินของ operator (ฉบับรวม 6 ข้อ):** 1) คืนเงิน (ก้อนไหน ใครอนุมัติ) 2) ใบกำกับภาษีในนามใคร+เลขชุดใคร 3) Stripe vs ข้อมูลในประเทศ (รับความเสี่ยงเป็นลายลักษณ์อักษร หรือรอ gateway ไทย) 4) SLA ตัวเลขจริงรายขั้น 5) เกณฑ์แจกงาน+เพดานงานต่อคน 6) ใครดึงงานคืนจากคนที่หาย

**ประโยคสรุปของเธรด:** "ระบบไม่ได้ออกแบบผิด แต่ยังไม่ถูกพิสูจน์ว่าเดินได้จริงทั้งเส้น และยังเงียบเกินไปเวลามีอะไรค้าง — แก้ด้วย Phase 0+1 ก่อนทุกอย่าง"
