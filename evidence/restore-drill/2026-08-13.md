## 2. คำสั่งที่รัน

```bash
LATEST=$(ls -t /opt/gacp-platform/backups/gacp_staging_*.dump | head -1)

docker run -d --name gacp-restore-drill \
  -e POSTGRES_USER=gacp -e POSTGRES_PASSWORD=<throwaway> -e POSTGRES_DB=drill \
  postgres:15-alpine
sleep 12

docker cp "$LATEST" gacp-restore-drill:/tmp/test.dump
docker exec gacp-restore-drill pg_restore -U gacp -d drill \
  --no-owner --no-privileges /tmp/test.dump 2>&1 | tail -20

docker exec gacp-restore-drill psql -U gacp -d drill -c "<นับแถว 3 ตาราง>"
docker exec gacp-postgres      psql -U gacp -d gacp_staging -c "<นับแถวชุดเดียวกัน>"

docker rm -f gacp-restore-drill
```

## 4. สิ่งที่พิสูจน์แล้ว

1. ดัมป์ของวันที่ 13 ส.ค. **อ่านออกและกู้กลับได้จริง** — cron ยังผลิตไฟล์ที่ใช้การได้อยู่
2. รูปแบบ `pg_dump -Fc` กู้ด้วย `pg_restore` ได้โดยไม่ต้องแก้อะไร
3. จำนวนแถวของ `applications` / `invoices` / `users` ตรงกับฐานที่ใช้งานอยู่ทุกตัว
4. cron ยิงจริงทุกวัน — ไฟล์ของ 8–13 ส.ค. **รอบอัตโนมัติ** ลงเวลา 03:17 ตรงกับตาราง cron `17 3 * * *` · หมายเหตุ: ไฟล์ที่ใช้กู้ในรอบนี้คือ `gacp_staging_20260813_053534.dump` ซึ่งลงเวลา **05:35 UTC ไม่ใช่รอบ cron** (เป็นการรันเพิ่มด้วยมือวันเดียวกัน) — ตัวมันเองจึงไม่ใช่หลักฐานว่า cron ยิง หลักฐานนั้นมาจากอีก 6 ไฟล์
5. สคริปต์ดัมป์ **ทั้งสองฐาน** (`scripts/ops/gacp-backup.sh:30` `for DB in gacp_db gacp_staging`)
   และไฟล์บนเครื่องยืนยันว่าเป็นจริง — มี `gacp_db_*.dump` คู่กับ `gacp_staging_*.dump` ครบทั้ง 7 คืน

## 5. สิ่งที่ยังไม่พิสูจน์ — ห้ามอ้างเกินนี้

1. ตรวจแค่ **3 ตาราง** จากทั้ง schema · การซ้อม 2026-08-08 ครอบ 25 ตาราง ซึ่งกว้างกว่ารอบนี้
   ⇒ รอบนี้เป็นการยืนยันความสด ไม่ใช่การยืนยันความครบ
2. ไม่ได้ยืนยัน referential integrity, constraint, หรือ sequence
3. ทดสอบเฉพาะดัมป์ของ `gacp_staging` · ดัมป์ `gacp_db` ของวันที่ 13 ยังไม่ได้ลอง
4. **การกู้บนเครื่องเดียวกันพิสูจน์ว่า "ไฟล์ดี" ไม่ได้พิสูจน์ว่า "กู้ได้ตอนเครื่องหาย"**
5. ไม่ได้จับเวลา — ยังไม่มีตัวเลข RTO (`GOALS.md:50` ยังค้างข้อนี้อยู่จริง)
