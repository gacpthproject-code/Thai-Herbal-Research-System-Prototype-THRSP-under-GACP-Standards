# "ทำไมออกเซอร์ไม่ได้" — ตอบพร้อมหลักฐาน 2026-09-05

**สรุปก่อน: ของจริงไม่ได้พัง** ปัญหาอยู่ที่กุญแจของเครื่อง dev ใบเดียว และตอนนี้แก้แล้ว
พร้อมพิสูจน์ว่าออกใบรับรองได้และลายเซ็นตรวจผ่านจริง

## 1. ของจริงเป็นอย่างไร

| สภาพแวดล้อม | กุญแจ | `RSA_PRIVATE_KEY_PASSPHRASE` | ใบรับรองที่เซ็นแล้ว |
|---|---|---|---|
| production (`gacp-backend`) | โวลุ่ม `gacp_signing_keys` | ตั้งไว้ | — |
| staging | โวลุ่ม `gacp_staging_signing_keys` | ตั้งไว้ | **10 ใบ ลายเซ็น RSA จริง 512 ไบต์** |
| demo | โวลุ่ม `gacp-signing-keys` (อ่านอย่างเดียว) | ตั้งไว้ | — |

ทั้งสามใช้กุญแจของตัวเองคนละใบกับในรีโป การที่เครื่อง dev เปิดกุญแจไม่ได้จึงไม่แตะของจริงเลย

`keys/private.pem` (fingerprint `f6034bc1…`) ถูกเข้ารหัสด้วย passphrase รุ่นก่อนหน้าที่หายไปแล้ว —

## 3. พิสูจน์ว่าออกได้จริง

บนฐาน PostgreSQL ใหม่จากศูนย์ (migrate ทั้งประวัติ) ด้วยกุญแจที่ระบบสร้างใหม่ให้:

- `npm run seed` **จบด้วย exit 0 เป็นครั้งแรก** — ตัว seed เองออกใบรับรองผ่าน `generateCertificate` จริง
- ใบที่ได้: `GACP-TH-2569-1082DD` · `signature len 512` · `RSA-SHA256` · `keyId rsa:gacp-certificate` ·
  เก็บ documentHash และ public key ไว้ในแถว
- ประตูสาธารณะ `GET /api/public/verify/GACP-TH-2569-1082DD` ตอบ:
  **`hashValid: true` · `signatureValid: true` · `sealed: true`** — `public-verify-signature-valid.json`

## 4. ปิดต้นเหตุไม่ให้เงียบอีก

`validateSigningKeyAtBoot` ปฏิเสธการบูตให้อยู่แล้วเมื่อกุญแจใช้ไม่ได้ — **แต่เฉพาะที่ที่บังคับให้มีกุญแจ**
ฝั่ง development มันคืน `{ok:true, skipped:true}` แล้วเงียบสนิท ซึ่งคือช่องที่ทำให้เรื่องนี้ไม่มีใครรู้
จนถึงวินาทีที่เจ้าหน้าที่กดผ่านการตรวจ แล้วคำขอถูกย้อนกลับต่อหน้า

ตอนนี้ฝั่ง dev **ตรวจและรายงาน** โดยไม่ปฏิเสธการบูตและไม่แตะไฟล์ · "ยังไม่มีกุญแจ" ยังเงียบตามเดิม
เพราะนั่นคือการใช้ครั้งแรกตามปกติ · พิสูจน์ด้วยกุญแจใบที่กักไว้จริง: ร้อง `KEY_UNUSABLE` พร้อมชี้ทางแก้
