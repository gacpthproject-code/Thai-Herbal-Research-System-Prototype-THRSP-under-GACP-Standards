## กล่องจดหมายเกษตรกรตอนจบ — สามใบ สามระดับ

```
DOCUMENT_APPROVED   prio=2   ✅ เอกสารผ่านการตรวจสอบ
REVISION_REQUESTED  prio=3   ⚠️ ใบสมัครของท่านต้องการการแก้ไข
INFO                prio=0   ✅ ส่งคำขอสำเร็จ
```

ตรงกับสามชั้นที่ออกแบบไว้: priority ≥ 2 = ต้องทำ · 0 = แจ้งให้ทราบ

## รอบที่สอง — เดินครบไม่มีขั้นไหนถูกข้าม (หลังแก้ F-UAT-04)

รอบแรกข้ามขาชำระเงินและข้ามขั้นผู้จัดตารางด้วย SQL · รอบนี้ไม่ข้ามอะไรเลย
ทุกขั้นผ่านประตู HTTP จริง และใช้บัญชีเจ้าหน้าที่จริงสี่บทบาท

```
เกษตรกร           สมัคร → กรอก กทล.๑ → แนบ 9 ใบ → ยื่น
                                        → PENDING_DOC_FEE · QT-PRD-2026-000001 ยอด 35,310
เกษตรกร           ยอมรับใบเสนอราคา → ยอมรับเงื่อนไขการชำระเงิน
                  → checkout → ใบแจ้งหนี้ INV-CO-…-M1 ยอด 5,885
เกษตรกร           แนบสลิปโอนเงิน      → PHASE_1_SLIP_UNDER_REVIEW
account_platform  อนุมัติสลิป ยอด 5,885 → DOC_FEE_PAID          ← F-UAT-04 แก้แล้ว
scheduler         มอบหมายผู้ตรวจ       → ASSIGNED_FOR_REVIEW    ← รอบแรกข้ามด้วย SQL
document_reviewer ขอเอกสารเพิ่ม 1 ใบ   → REVISION_REQUESTED
เกษตรกร           แก้ใบเดียว → ส่งกลับ  → ASSIGNED_FOR_REVIEW
document_reviewer ติ๊กรับ 9/9 → รับทั้งหมด → DOC_APPROVED
```

**บทบาทที่ใช้จริง**: `health` · `account_platform` · `scheduler` · `document_reviewer`

การแจ้งเตือนที่เกิดตลอดเส้น 5 ใบ — ยื่นสำเร็จ · สลิปได้รับอนุมัติ · ขอแก้ไข · เอกสารผ่าน

## ที่ยังไม่ได้เดิน

- ~~ขาชำระเงินจริง~~ — **เดินแล้วในรอบที่สอง** ผ่านการโอนเงินแนบสลิป ซึ่งไม่ต้องมี provider ภายนอก
  · ขาบัตรเครดิต (ยืนยัน PaymentIntent + webhook) ยังไม่เดิน — ต้องผ่านหน้า Stripe จริง
  และการยืนยัน PaymentIntent เป็นการแตะเงินซึ่ง L3 สงวนไว้
- หน้าจอที่ต้องรัน JS จริง — curl ได้แค่ SSR shell · การพิสูจน์ที่ทำแทนคือยิง API **ผ่าน proxy**
  ด้วยคุกกี้ ซึ่งเป็นเส้นทางเดียวกับที่เบราว์เซอร์ใช้
