# เดินฝั่งพนักงานจริง — 2026-09-05

ฐาน PostgreSQL ตั้งใหม่จากศูนย์ · เข้าระบบด้วยบัญชีพนักงานจริงสี่บทบาทผ่านประตู
`POST /api/auth/provider/login` · ทุกบรรทัดมาจากการยิง HTTP จริง

## ประตูของแต่ละบทบาท ตอบครบ

| บทบาท | ประตู | ผล |
|---|---|---|
| ผู้ตรวจเอกสาร | `/provider/reviewer/dashboard` · `/provider/work/my` · `/provider/work/queue` | 200 · 200 · 200 |
| ผู้จัดตาราง | `/provider/scheduler/reviewers` · `/scheduler/auditors` · `/ledger/fairness` | 200 · 200 · 200 |
| ผู้ตรวจแปลง | `/provider/auditor/dashboard` · `/provider/work/my` | 200 · 200 |
| การเงิน | `/provider/work/my` | 200 · (`/ledger/fairness` ตอบ 403 ถูกต้อง — สมุดภาระงานเป็นของผู้จัดตาราง) |

> 404 ชุดแรกที่เจอ เกิดจากผมเดา URL เอง ไม่ใช่ฟีเจอร์หาย · อ่านทะเบียนเส้นทางจริงแล้วยิงใหม่

## สองข้อบกพร่องที่การเดินจับได้

### 1. seed วางคำขอไว้ในที่ที่ไม่มีพนักงานคนไหนแตะได้

`APP-68-001` ถูก seed เขียนเป็น `ASSIGNED_FOR_REVIEW` **โดยไม่มีผู้ตรวจ** ⇒ ตันทั้งสองทาง:
ผู้ตรวจเอกสารมองไม่เห็น (การมองเห็นผูกกับ "ถูกมอบหมายให้ฉัน" ซึ่งถูกต้อง) และผู้จัดตาราง
มอบหมายไม่ได้ (ประตูต้องการ `DOC_FEE_PAID` แต่คำขอเลยจุดนั้นไปแล้ว — **409**)

เครื่องจริงสร้างสภาพนี้ไม่ได้: state machine มีทางเข้าทางเดียวคือ `DOC_FEE_PAID →
ASSIGNED_FOR_REVIEW` และตัวเดินตั้งผู้ตรวจในจังหวะเดียวกัน · **มีแต่ seed ที่เขียนข้ามหน้างาน**
⇒ ให้ seed หยุดที่ `DOC_FEE_PAID` แล้วปล่อยให้ผู้จัดตารางมอบหมายจริง

### 2. งานถูกมอบหมายให้คนที่มองไม่เห็นมัน  ← บั๊กของสินค้า

ผู้จัดตารางมอบหมายสำเร็จ (**200**, `reviewerId` ถูกเขียน, สถานะขยับจริง) แต่คนที่ถูกมอบหมาย
เปิด `/provider/applications` แล้วได้ **0 รายการ** — เปิดคำขอได้ก็ต่อเมื่อรู้ id

รายชื่อผู้ตรวจเอกสารที่ผู้จัดตารางเลือกได้ **ตั้งใจ**รวมผู้ตรวจแปลงไว้ด้วย
(`reviewerRoles = [DOCUMENT_REVIEWER, AUDITOR]`) แต่สาขา AUDITOR ของตัวกรองการมองเห็น
ดูแค่ `auditorId` / `headAuditorId` / `(sameReviewerAuditor && reviewerId)` และการมอบหมาย
ปล่อยธงนั้นเป็น `false` — ธงไม่ได้ผิด มันแปลว่า "คนเดียวกันทำทั้งสองบทบาท" ซึ่งยังไม่จริง
ณ เวลามอบหมาย · **สาขาการมองเห็นต่างหากที่แคบไป**

แก้ด้วยกฎเดียวกับที่สาขาผู้ตรวจเอกสารใช้อยู่แล้ว: *คุณเห็นสิ่งที่มอบหมายให้คุณ* ·
รั่วไม่ได้เพราะแสดงให้เฉพาะคนที่ถูกมอบหมายเท่านั้น

| | ก่อนแก้ | หลังแก้ |
|---|---|---|
| ผู้ที่ถูกมอบหมายเห็น | **0 รายการ** (`assignee-sees-nothing-before.json`) | **1 รายการ APP-68-001** (`assignee-sees-it-after.json`) |

### หมายเหตุเรื่องเทสที่เกือบหลอกตัวเอง

เทสฉบับแรกของข้อ 2 แผ่ `OR`/`AND` ออกมาแล้วถามว่ามีเงื่อนไข `reviewerId` อยู่ไหม —
**มันผ่านทั้งที่ยังไม่ได้แก้อะไร** เพราะการแผ่ทำให้เงื่อนไขที่ถูกครอบด้วยธงดูเหมือนเงื่อนไขเดี่ยว ·
เขียนใหม่ให้ **ประเมินตัวกรองกับแถวจริง** แล้วมันแดงทันที — คำถามว่า "แถวนี้ผ่านไหม"
โกหกแบบนั้นไม่ได้

## การเดินนี้เป็นของเครื่องแล้ว (เพิ่ม 2026-09-06)

การพิสูจน์ข้างบนเป็นการเดินด้วยมือของคนคนเดียว ครั้งเดียว — ครั้งหน้าที่ใครแก้ตัวกรอง
การมองเห็นหรือประตูมอบหมาย จะไม่มีอะไรจับได้จนกว่าจะมีคนเดินอีกรอบ

`__tests__/integration/staff-chain-assign-then-see.test.js` ทำให้มันรันซ้ำได้:
ยิงผ่านตัวกรองจริงและรูปร่างข้อมูลจริงที่ประตูมอบหมายเขียน บน PostgreSQL จริง
ข้ามอย่างสุภาพเมื่อไม่มีฐานข้อมูล (`describeIfTestDatabase`) และ**ไม่ผ่านแบบเงียบ ๆ**

- รันจริงบนฐานทิ้ง (`TEST_DATABASE_URL`): **4/4 ผ่าน**
- **Mutation-proved**: ถอดเงื่อนไข `{ reviewerId }` ออกจากตัวกรอง → แดงตัวที่ถูกต้องหนึ่งตัว ·
  ใส่คืน → เขียวทั้งสี่ · เทสนี้จับบั๊กเดิมได้จริง ไม่ใช่ผ่านเพราะบังเอิญ

**ข้อเท็จจริงของสคีมาที่สะดุดระหว่างเขียน และบันทึกไว้ในเทส** เพราะคนถัดไปจะพลาดเหมือนกัน:
`applications.healthId` **ไม่ได้** ชี้ไปที่ `users.healthId` — FK จริงคือ
`REFERENCES users("canonicalId")` · และ `users_auth_type_identity_ck` บังคับว่า
บัญชีพนักงานต้องมี `providerId` (healthId ต้องเป็น null) ส่วนบัญชีเกษตรกรกลับกัน
