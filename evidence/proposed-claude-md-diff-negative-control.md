## ปัญหาที่กติกานี้แก้

ทุก pin/probe ในรีโปวันนี้ทดสอบ**ทิศทางเดียว**: เขียนโค้ดที่ผิดแล้วดูว่าแดง (positive control)
ไม่มีตัวไหนทดสอบทิศตรงข้าม: เขียนโค้ดที่**ถูกต้องและใกล้เคียงที่สุดกับสิ่งที่ห้าม** แล้วดูว่าเขียว

ผลที่เกิดจริง — **#746 ผ่าน CI ครบ 24 checks ทั้งที่ pin ในนั้นจะจับผิดโค้ดที่ถูกต้อง**
เป็นไปได้เพราะ **โค้ดที่จะโดนจับผิดยังไม่มีในทรี** มันคือโค้ดของ*ขั้นถัดไป*
⇒ gate ที่ตรวจ "ทรีวันนี้" บอกไม่ได้ว่ามันจะขวางงานพรุ่งนี้ไหม

ถ้ามี negative control ตั้งแต่แรก จะจับได้ในรอบแรก แทนที่จะต้องใช้ audit สามรอบ

### นิยาม "ใกล้เคียงที่สุด" — ส่วนที่ต้องเขียนให้ชัด ไม่งั้นกติกาจะถูกตีความหลวม

negative control ที่ **ไม่นับ**:
- โค้ดที่ไม่เกี่ยวข้องกับ pin เลย (เช่น pin เรื่อง identity แต่เขียน negative control เป็นฟังก์ชันคำนวณภาษี) — ผ่านแน่นอนโดยไม่ได้พิสูจน์อะไร
- โค้ดที่มีอยู่แล้วในทรี — ถ้ามันอยู่แล้วและ suite เขียว ก็แค่บอกว่า "วันนี้ไม่มี false positive" ไม่ได้บอกว่า**พรุ่งนี้**จะไม่มี

negative control ที่ **นับ**:
- โค้ดที่ **ใช้ token เดียวกัน / โครงเดียวกัน** กับสิ่งที่ห้าม แต่เป็นการใช้ที่ถูกต้อง
  ตัวอย่างจริง: pin ห้าม*เขียน* `identity_links` ⇒ negative control คือโค้ดที่ **อ่าน** `identity_links`
  (ใช้ชื่อ model เดียวกัน อยู่ในไฟล์เดียวกับ `prisma.user.update` ที่ไม่เกี่ยวข้อง)
- โค้ดที่มาจาก **งานขั้นถัดไปที่วางแผนไว้แล้ว** — ถ้าตอบไม่ได้ว่าขั้นถัดไปหน้าตาอย่างไร
  แปลว่ายังไม่ควรเขียน pin นี้

## ประเมินการเติม negative control ย้อนหลังให้ pin ที่มีอยู่ (ตามที่ operator สั่งให้เสนอ)

รายการนี้มาจากผลสำรวจ scanner ทั้งรีโป (74 จุดเลือกไฟล์ 5 ตระกูล) — เรียงตาม **คุ้มค่าที่สุดก่อน**

| pin/probe | ความเสี่ยง false positive วันนี้ | negative control ที่ควรเขียน | แรง |
|---|---|---|---|
| `identity-provider-naming-collision` | **สูงมาก — พิสูจน์แล้วว่าเกิดจริง** | โค้ดอ่าน `identity_links` + โค้ดที่ใช้ `providerId` ใน `select`/`where` | **S** (มีตัวอย่างพร้อมแล้วใน `evidence/AUTH-01/A/audit-round3-verdict.md`) |
| `status-writer-canonical-vocabulary` | สูง — โครงเดียวกันเป๊ะ และมีบั๊ก `.mjs` แบบเดียวกัน (`:179`) | writer ที่เขียน status ผ่าน helper ที่ canonical แล้ว | **S** |
| `soft-delete-registry-drift` | กลาง — เป็น registry check ไม่ใช่ pattern match | model ใหม่ที่มี `isDeleted` และถูกจัดประเภทถูกต้อง | **M** |
| `tenant-scope-drift` | กลาง | model ใหม่ที่มี `organizationId` และอยู่ใน registry ถูกต้อง | **M** |
| `check-data-sovereignty` | กลาง — แต่ปัญหาหลักคือ **false negative** (`.html` หลุด) | ไฟล์ที่อ้าง CDN ในบริบทที่อนุญาต (ถ้ามี) | **M** |
| `check-ai-style-smells` | ต่ำ — pattern แคบและชัด | คอมเมนต์ที่มีเครื่องหมายคล้าย banner แต่ไม่ใช่ | **S** |
| `check-thai-copy-style` | **สูง** — `isSkipped()` ที่ `:76-83` คือ negative control ที่ซ่อนอยู่แล้ว แต่ไม่มีเทสต์ยืนยัน | ไฟล์ `.spec.*` ที่มีข้อความไทยเป็น assertion label | **S** |
| `check-orphan-api-routes` | **สูงมากถ้าขยาย scope** — จำลองแล้วได้ orphan ปลอม 15 เส้นทาง | route ที่ mount ผ่าน `createLazyRouter(ตัวแปร)` | **M** — ต้องแก้ mount detection ก่อน |
| `probes/*.sh` (14 ตัว) | ต่ำ–กลาง | ไฟล์ที่มี token ใกล้เคียงในบริบทที่ถูกต้อง | **L** — เป็น bash + operator-owned ต้องออกแบบวิธี fixture ก่อน |
| `check-banned-terms` | ต่ำ | เอกสารที่*อธิบาย*ว่าคำไหนต้องห้าม (meta) | **S** |

**แรง**: S = ≤1 ชั่วโมง เขียน fixture ตรง ๆ · M = ครึ่งวัน ต้องออกแบบ fixture ที่ไม่กระทบ suite เดิม · L = ต้องออกแบบกลไก fixture ใหม่ทั้งชุด

### ข้อเสนอลำดับ
1. **ทำทันทีในงานที่กำลังทำอยู่แล้ว** — `identity-provider-naming-collision` (มีตัวอย่างพร้อม) และ `status-writer-canonical-vocabulary` (จะแก้บั๊ก `.mjs` อยู่แล้ว เติมพร้อมกันได้)
2. **ทำเมื่อแตะ pin นั้นครั้งหน้า** — ตัวที่เหลือในกลุ่ม S/M · **ไม่เสนอให้ทำเป็นงานกวาดรวดเดียว** เพราะ fixture ที่เขียนโดยไม่มีบริบทของงานจริงจะกลายเป็น fixture ที่ผ่านง่ายเกินไป ซึ่งแย่กว่าไม่มี
3. **กลุ่ม L (`probes/*.sh`) รอ** — ต้องมีวิธี fixture สำหรับ bash probe ก่อน · เสนอให้ผูกกับงาน shared file-walker ที่เสนอไว้แล้ว

### สิ่งที่กติกานี้ **ไม่** แก้ — เขียนไว้กันเข้าใจผิด
negative control จับได้เฉพาะ false positive ที่**คนเขียนนึกออก** · ถ้านึกไม่ออกว่าโค้ดที่ถูกต้องหน้าตาอย่างไร
ก็จะเขียน fixture ที่ไม่ตรงจุด · มันยกพื้นขึ้น ไม่ใช่ด่านที่กันได้ทุกกรณี
ตัวที่จะกันได้จริงกว่าคือ **auditor ที่เขียนโค้ดของขั้นถัดไปแล้วลองรัน** ซึ่งเป็นสิ่งที่ audit รอบ 3 ทำและได้ผล
