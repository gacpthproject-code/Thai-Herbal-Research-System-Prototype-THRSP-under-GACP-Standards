# การอัปเดตข้อมูลของเกษตรกร — กดจริงผ่าน API จริง (2026-09-06)

คำถามข้อ 2 ของ operator มีคำว่า "ออกแบบการอัพเดตข้อมูล" อยู่ด้วย · นี่คือส่วนนั้น วัดจากของจริง

## กติกาที่มีอยู่ และทำงานถูกต้อง

รอบปลูกจะ **แช่แข็ง** เมื่อเก็บเกี่ยวแล้ว (`HARVESTED`/`COMPLETED`) หรือมีรุ่นเก็บเกี่ยวเกิดขึ้นแล้ว
สี่ฟิลด์ที่แช่แข็งคือฟิลด์ที่ **หน้าสแกนสาธารณะประกาศออกไป**: `seedSource` `varietyName`
`irrigationType` `soilType` · ส่วน `notes` แก้ได้ตลอด เพราะไม่เคยถูกเผยแพร่ — เป็นบันทึกที่
เกษตรกรเขียนถึงตัวเอง

| ทดสอบ | ผล |
|---|---|
| รอบที่เก็บเกี่ยวแล้ว → ขอแก้ `varietyName` | **409 `CYCLE_FROZEN`** พร้อมประโยคไทยที่บอกว่าทำไม |
| รอบเดียวกัน → แก้ `notes` | 200 · บันทึกถูกแก้จริง |
| ส่ง `varietyName` + `notes` มาพร้อมกัน | **ปฏิเสธทั้งคำขอ** และ `notes` ไม่ถูกแก้แม้แต่ค่าเดียว |

ข้อสุดท้ายคือสิ่งที่ `harvest-service` เรียนไว้ก่อนแล้วและเขียนไว้ในโค้ด: *"A farmer editing
notes and a weight in one request must not be told the whole edit succeeded when half of it
was discarded."* — ตรวจแล้วว่าเป็นจริงบนเส้นนี้ด้วย

ข้อความปฏิเสธบอกเหตุผลที่ถูกต้อง ไม่ใช่แค่บอกว่าไม่ได้:
> รอบปลูกนี้ปิดแล้ว จึงแก้ varietyName ไม่ได้ — ข้อมูลเหล่านี้แสดงอยู่บนหน้าตรวจสอบย้อนกลับ
> ที่ผู้ซื้อสแกนดูได้ หากต้องแก้ไข กรุณาติดต่อเจ้าหน้าที่

## ที่แก้ในรอบนี้

บริการเขียนการปฏิเสธไว้ครบสามส่วน — `code: 'CYCLE_FROZEN'` · `statusCode: 409` · `fields` —
แต่ route ตกไปที่กิ่งสุดท้ายที่ตอบ **400 เสมอ** และทิ้ง `code` กับ `fields`

- 400 แปลว่า "คำขอผิดรูป" · 409 แปลว่า "ชนกับสถานะของข้อมูล" ซึ่งเป็นเรื่องที่เกิดขึ้นจริง
- หน้าจอที่ต้องเลือกคำอธิบาย ควรอ่านจาก **ชนิด** ของการปฏิเสธ ไม่ใช่จับคู่ข้อความ —
  บทเรียนเดียวกับที่ประตูยื่นคำขอเรียนไปเมื่อ 2026-09-05

ยิงซ้ำหลังแก้: `409` · `{"code":"CYCLE_FROZEN", ...}` · `notes` เดิมยังอยู่ครบ
