## สิ่งที่พิสูจน์

บั๊ก: tarball ของ volume ถูกสร้างโดยคอนเทนเนอร์ในนาม root โหมด 644 · บรรทัด
`chmod 600 ... 2>/dev/null || true` ที่ตามมารันในนาม cron user จึงแก้ไฟล์ของ root ไม่ได้
และ `|| true` ทำให้มัน**ล้มเงียบทุกคืน** · เห็นของจริงบนเครื่อง 2026-08-14:

```
-rw------- ubuntu ubuntu    1406790  gacp_staging_20260813_234609.dump
-rw-r--r-- root   root     55778407  gacp-uploads-data_20260813_234609.tgz
```

การแก้: `install -m 600 /dev/null` สร้างไฟล์ไว้ก่อนที่คอนเทนเนอร์จะเขียน — `tar czf` เปิด
path ที่มีอยู่ด้วย `O_TRUNC` inode จึงคงอยู่ พร้อมโหมดและเจ้าของ

## ความพยายามครั้งแรกที่ล้มเหลว — บันทึกไว้เพราะสำคัญกว่าผลที่ผ่าน

รอบแรกของ assertion นี้ **ผ่านกับสคริปต์ที่มีบั๊ก** (`PASS=11 FAIL=0`, `RED exit=0`) ⇒ เท่ากับ
ไม่มี assertion เลย · สาเหตุ: stub จำลองผิดตัวแปร — ผมโมเดล `umask 022` ของคอนเทนเนอร์
แต่สิ่งที่ทำให้ของจริงล้มคือ **ความเป็นเจ้าของไฟล์** ในเทสต์ไฟล์เป็นของผู้ใช้ที่รันเทสต์ `chmod`
จึงสำเร็จ

แก้สองจุด: fake docker แยก "สร้างไฟล์ใหม่" ออกจาก "เขียนทับไฟล์ที่มีอยู่" เหมือนที่ของจริงแยก ·
และ stub `chmod` ที่ตะเข็บเดียวกับที่ stub `docker` อยู่แล้ว ให้ปฏิเสธไฟล์ที่คอนเทนเนอร์สร้าง
เพราะเทสต์ไม่ได้รันเป็น root จึงสร้างไฟล์ที่ตัวเองแก้สิทธิ์ไม่ได้ไม่ได้เลย

**บทเรียนที่เอาไปใช้ต่อ: stub ที่ปลอดภัยกว่าของจริง ทำให้เทสต์โกหกในทิศทางเดียวที่อันตราย**
เขียนไว้เป็นข้อบังคับใน `docs/superpowers/plans/2026-08-14-runtime-deploy-drift.md` §5 แล้ว

## สิ่งที่ใบนี้ยังไม่ครอบ

- **ไฟล์ `.tgz` เดิมบนเครื่องยังเป็น 644** จนกว่าจะรัน `sudo chmod 600 /opt/gacp-platform/backups/*.tgz` —
  การแก้สคริปต์มีผลกับไฟล์ที่สร้างใหม่เท่านั้น
- **สำเนาบน `/usr/local/bin/gacp-backup.sh` ยังเป็นตัวก่อนแก้** จนกว่าจะ `sudo install` ใหม่หลัง merge
- ไม่เคยซ้อมกู้ tarball — `docs/operations/runbooks/backup-and-restore.md` บันทึกไว้เองว่ายังไม่เคยทำ
